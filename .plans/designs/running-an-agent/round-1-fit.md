REVISE

Grade 4 out of 10.

This is a cross-vendor review of the Claude-authored draft by a Codex worker. I reviewed draft commit `3e00db5d` and traced the checks through the current source by reading. The draft has the right first user journey, but leaves gaps between the deployed website, the link, and the agent lifecycle that can stop that journey.

## Findings

The draft says the screens stay as they are and the two new services replace their data. The deployed website starts in the contract-backed app's sample-seeded mode. In that mode, creating a project synthesizes the project, lead and first answer, and a lead's conversation address opens the end-result view or the command center. The separate legacy mode can render `ChatTab`, but it calls the old engine and skips the Go server startup. ### fit 3 — BLOCKER — The state table omits starts with no event and permits stale turn commands

The draft moves an agent out of `starting` only on an agent event. The server can persist the start command just before the machine goes offline. A later expired or unsupported result can end that command without any harness having opened. The state stays `starting` because no `AgentStartFailed` event exists. The `Prompt` rule has the opposite problem. It reports that the message did not reach the agent even when an interrupted result or a server-side expiry means the effect is unknown. Finally, `CancelTurn` names only the agent. A delayed cancel for a completed turn can hit the next turn. The client-restart report also needs an ordering rule so it cannot fail a new start dispatched after reconnect. [Draft, state table, results and AgentsRunning](../../../docs/specs/2026-11-27-running-an-agent-design.md#L145) · [Draft, link commands and reports](../../../docs/specs/2026-11-27-running-an-agent-design.md#L168) · [commands.proto, CommandOutcome](../../../src/contracts/proto/lgtm/link/v1/commands.proto#L83) · [server link, AcceptResult and SweepCommands](../../../src/server/internal/link/outbox_result.go#L11) · [server link, SweepCommands](../../../src/server/internal/link/outbox_sweep.go#L50)

Give each start and turn a durable identity. Define how successful, definitely unstarted and unknown outcomes of start, prompt, cancel and stop settle, including a bounded startup deadline and reconciliation of unknown effects. Apply terminal command outcomes, agent state and notes through the owning part in the same store transaction, including finalization by the sweeper. Bind cancellation and completion to the intended turn. Make the startup inventory precede acceptance of new agent work, or have it identify exactly which client process's runs it reconciles. Define the point where a prompt is pending and where its output and end may first be emitted. Apply a link-safe size limit to the first goal as well as later messages. In the scout, a normal Agent Client Protocol (ACP) prompt returns at turn end, after updates may already have arrived. Treating that response as acceptance would leave the first answer streaming while the agent still appears to be starting. ### fit 4 — BLOCKER — Credential handling falls short of foundation rule 9

The runner gets an environment allowlist, and the draft says it receives none of the client's state. The approved design currently runs the client and harness under the same machine user. ### fit 9 — MAJOR — Server restart, client restart and buffered output lack separate guarantees

The draft says that a full client buffer stops harness reads and drops nothing, and that a new client process finds no harness running. The current outbox returns a full-buffer error. If the runner stops reading the entire ACP connection, the same connection also carries prompt responses and permission requests. A brief outage can then postpone cancellation or completion, and a crash can lose text still in the 300-millisecond batch. An unexpected client death cannot run its orderly process-group cleanup. A restart report can therefore mark an agent failed while an old process still exists. The draft also promises “a few hundred kibibytes” per long answer while limiting only the size of a single item, and promises the same thread on reload while retaining only the newest 500 items in the snapshot.
