## Findings in the second draft

### logic 1 | BLOCKER | A failed start can release a checkout while its lead is still running

**Draft.** `starting` becomes `failed` 150 seconds after the start command expires. A project with a failed lead no longer counts against the one-project limit. A late `AgentStarted` for a final agent causes a separate `StopAgent` command. [Checkout rule](../../../docs/specs/2026-11-27-running-an-agent-design.md#L286) · [State table and late starts](../../../docs/specs/2026-11-27-running-an-agent-design.md#L324)

**Scenario.** The client writes the first goal and buffers `AgentStarted`, then the link goes down. Claude continues working in the main checkout. The server's deadline marks the first lead failed, so another project can be created for that folder and its start can be stored before the link returns. The reconnect has the same run. When the old `AgentStarted` arrives, its cleanup stop gets a later command number than the second start. Both leads can touch the same files before cleanup finishes. The three send permits do not serialize process effects. An expired stop has the same ownership problem, and a stop that misses the retry window may never reach a surviving process.

**Evidence.** By reading, the cursor visits commands in number order and the writer's permit ends at dispatch. A stop with a 23-hour lifetime stops being offered 23 hours *after* expiry, and the existing hourly sweep settles it only after 24 hours *after* expiry. The draft's “did not return for a day” is therefore not the meaning of its timed-out stop row. [Command cursor and retry cutoff](../../../src/server/internal/link/outbox_claim.go#L58) · [Writer turn](../../../src/server/internal/link/stream.go#L99) · [Expiry grace](../../../src/server/internal/link/outbox.go#L15) · [Sweep schedule](../../../src/server/internal/link/outbox_sweep.go#L147) · [Stop lifetime](../../../docs/specs/2026-11-27-running-an-agent-design.md#L353)

**Smallest repair.** Keep the visible start deadline, but keep a durable checkout reservation until there is proof that the old start never ran or proof that the process is gone and cannot spawn. Use the owning parts' interfaces to change that reservation in the same write as the confirming lifecycle change. Keep an unconfirmed stop pending across expiry and confirm it on a later link or after verified process cleanup. Exercise a same-run reconnect with a late start and a second project attempt. State the stop delivery and settlement deadlines separately. [Foundation rules 3, 4 and 7](../../../docs/specs/2026-11-25-go-rewrite-foundation-design.md#L358)

### logic 2 | BLOCKER | A fast first reply can end before the server knows the agent started

**Draft.** `StartAgent` writes the goal before it is done. `AgentStarted` changes `starting` to `working`, and only a `working` agent consumes `TurnEnded` as a transition to `idle`. [State table](../../../docs/specs/2026-11-27-running-an-agent-design.md#L320) · [Start command](../../../docs/specs/2026-11-27-running-an-agent-design.md#L353)

**Scenario.** A stand-in sends its whole answer and final prompt reply immediately after reading the goal. The output reader numbers `ThreadOutput` and `TurnEnded` while the start handler is still appending `AgentStarted`. The server commits the end while the lead is `starting`, then applies the start and leaves it `working` forever. A lost acknowledgement or server restart cannot repair the order. Replay preserves those same numbers.

**Evidence.** By reading, `ApplyEvent` applies the next number and commits its effect with the mark. The client event store assigns a number when append commits. The scout saw the Agent Client Protocol (ACP) prompt reply report the end of the turn. The draft orders the text before that end but allows the first start event to follow both. [Server `ApplyEvent`](../../../src/server/internal/link/inbox.go#L49) · [Client append](../../../src/client/internal/link/outbox.go#L35) · [Scout, prompt replies](../../../.foundry/go-rewrite/results/w2-scout-agent-run.md#L141) · [Output order](../../../docs/specs/2026-11-27-running-an-agent-design.md#L386)

**Smallest repair.** Hold first-turn reports until the goal write succeeds and `AgentStarted` is durably numbered. Then number first-turn output and its end through the same ordered publisher. Record the start with the run that produced it, including when a replacement process replays it. Make a repeated `done` receipt leave the lifecycle unchanged. Give a `failed` receipt without a start event the existing bounded timeout and a safe fallback reason. Test an immediate reply and a crash after the start event is appended but before the receipt is finished.

### logic 4 | MAJOR | The restart barrier can strand a command on an otherwise healthy stream

**Draft.** After `Open`, the server holds agent commands until it has applied all event numbers below the new run's boundary. [Run barrier](../../../docs/specs/2026-11-27-running-an-agent-design.md#L84)

**Scenario.** A replacement opens with boundary 101 while the server's mark is 99. The first send turn sees a pending, unstarted `StartAgent` at the head. If the claim path skips it while the barrier is closed, it has already moved `lastSeq` past it. Event 100 opens the barrier and the writer takes another turn, but the same stream cannot see that start again. A restart whose mark already equals 100 can wait forever if the transition only runs when applying an event, since there need be no new event.

**Evidence.** By reading, `claimNext` advances `lastSeq` before filtering, and subsequent pages use `seq > lastSeq`. The stream takes a command turn after dispatching an inbound frame and releases the shared permit after the send attempt. On admission `Welcome` already carries the committed mark. [Claim cursor](../../../src/server/internal/link/outbox_claim.go#L58) · [Stream turns](../../../src/server/internal/link/stream.go#L93) · [Welcome](../../../src/server/internal/link/handshake.go#L234)

**Smallest repair.** Evaluate the barrier against the committed mark at authenticated admission and again as that mark advances. Reconcile old runs once and make the next command turn see the opening commit. Preserve the cursor position of held work, and leave the shared permits available while a stream waits for its past. Replay an old start and reply from disk while a new unstarted command is queued. Verify that the replacement gets the new command on that same stream and that old output lands before old agents are failed.

### logic 5 | MAJOR | The website deadline cannot produce the operation result R7 requires

**Draft.** A folder command expires at 20 seconds, its call waits 25 seconds, and R7 requires a failed operation when the machine disconnects before taking the command. [Operation table](../../../docs/specs/2026-11-27-running-an-agent-design.md#L167) · [R7](../../../docs/specs/2026-11-27-running-an-agent-design.md#L225)

**Scenario.** The server stores the operation and the client goes offline before any send. The server can also spend the admission window waiting for one of the three shared permits. At second 25 the call can time out, but no client can return `expired` while it is away. On the existing link, the command is still eligible to be offered until 23 hours after expiry, and the sweep records `timed_out` still later. The draft would then call the outcome unknown, even though R7 requires a failed operation. A server restart between storage and the wait has the same durable state.

**Evidence.** By reading, the command expiry is checked by the client before a new receipt starts. The server retries past expiry and its sweep uses the 24-hour grace. `Forget` can also settle a pending command as `removed`, which has no folder-operation row. A false `dispatched` flag alone cannot prove no effect because the frame is sent before that flag is committed. [Client `Begin`](../../../src/client/internal/link/receipts.go#L64) · [Server `sendClaimed`](../../../src/server/internal/link/outbox_send.go#L131) · [Shared permits](../../../src/server/internal/link/outbox_send.go#L17) · [Command sweep](../../../src/server/internal/link/outbox_sweep.go#L50) · [Machine removal](../../../src/server/internal/link/presence.go#L245)

**Smallest repair.** At the operation deadline, use a durable rule under the machine lock to fail an expired operation with proof it was never offered. Return pending or unknown where a frame might have reached the client. Include removal and distinguish those cases in R7. Keep late authenticated answers eligible to resolve uncertainty.

### logic 6 | MAJOR | A late folder answer can leave two callers with different outcomes for one creation

**Draft.** The numbered folder event finishes the operation. A failed result uses the reason of the event, an interrupted result makes the operation unknown, and a retry with the same key returns its result. R6 tests a lost creation reply and one row. [Operation outcomes](../../../docs/specs/2026-11-27-running-an-agent-design.md#L167) · [R6](../../../docs/specs/2026-11-27-running-an-agent-design.md#L224)

**Scenario.** `MakeRepository` initializes the folder and appends its successful event. The client dies before finishing the command receipt. On reconnect, the stored receipt yields `interrupted`. Folder commands are outside the run barrier, and the client may send the interrupted result before its buffered answer. A same-key wait can return unknown while the successful answer is still in transit. If `unknown` is final, the repository never registers. If the row can change but the ordinary website receipt saved the error, the same-key retry never gets the repository. A failed result can similarly arrive before its reason. Restarting the server can discard any in-memory coordination between those paths. The same event/result ordering affects `AddRepository`.

**Evidence.** By reading, the client has separate commits for events and receipts and prioritizes results. The server independently commits a result or an event. `WriteOnce` replays the original saved byte reply. R3 also says a repeat canonical folder lookup succeeds, while the error table says an already added folder is refused. [Client receipt lookup and finish](../../../src/client/internal/link/receipts.go#L116) · [Client send priority](../../../src/client/internal/link/session.go#L633) · [Server result settlement](../../../src/server/internal/link/outbox_result.go#L11) · [Website receipt replay](../../../src/server/internal/store/receipts.go#L71) · [R3](../../../docs/specs/2026-11-27-running-an-agent-design.md#L221) · [Refusals](../../../docs/specs/2026-11-27-running-an-agent-design.md#L518)

**Smallest repair.** Save the operation identifier in the initial keyed receipt and read the current durable operation after that transaction. Bind the event to the operation, its command and its machine. Let that event resolve pending or unknown exactly once and keep the canonical folder upsert in the same write. Replay a committed success for the same folder and repository, and reserve a conflict for a different requested repository. Extend R6 to kill the client between append and receipt commit and restart the server while the website waits.

### logic 7 | MAJOR | A cancellation can return done before the turn it names starts

**Draft.** `SendMessage` makes the agent `working` when it stores `Prompt`. The website then shows “Stop this reply.” `CancelTurn` returns `done` if the turn no longer runs, and its watchdog applies after a cancellation. [State table](../../../docs/specs/2026-11-27-running-an-agent-design.md#L329) · [Command table and watchdog](../../../docs/specs/2026-11-27-running-an-agent-design.md#L353) · [Reply control](../../../docs/specs/2026-11-27-running-an-agent-design.md#L475)

**Scenario.** The client receives `Prompt`, records a started receipt, and queues the frame write to the adapter. With that write still pending, `CancelTurn` sees no running harness turn and returns `done`. The pending prompt then starts and runs with no cancellation. If the cancel command instead expires because the link drops after the website stores it, neither the turn table nor the watchdog records that the cancellation was missed.

**Evidence.** By reading, the link's send permit is released after sending and dispatching the command. It provides no order between client handler effects. The already built scan handler starts long work outside its command turn. A3 exercises a cancellation of a running turn and a stale cancellation after one ends. [Server writer turn](../../../src/server/internal/link/stream.go#L99) · [Client command handler](../../../src/client/internal/link/commands.go#L193) · [A3](../../../docs/specs/2026-11-27-running-an-agent-design.md#L542)

**Smallest repair.** Serialize the decision to submit or cancel for the named turn. A cancel before submission must suppress the pending write and end the turn with a recorded outcome. After submission, cancel that turn and run the ten-second watchdog. Report a missed or uncertain cancellation without clearing a genuinely active turn. Test cancellation after the website accepts the message but before the adapter receives it.

### logic 8 | MAJOR | A command result can falsely return an agent to idle or leave its turn waiting

**Draft.** `Prompt` returning `failed`, `expired` or `unsupported` marks the lead idle and says the message never reached the agent. The table has no `interrupted` or `timed_out` row for a prompt. [Prompt state rows](../../../docs/specs/2026-11-27-running-an-agent-design.md#L329)

**Scenario.** A prompt write reaches the adapter and the client dies before finishing its receipt. On replacement the run barrier must fail the old agent, but any prompt settlement or replayed turn end needs to respect that lifecycle and record the delivery uncertainty. In a same-run outage, a frame-write error can also leave submission uncertain, or the server can sweep an accepted prompt whose result never arrived. Marking it idle can let another prompt overlap the first. Ignoring the settlement entirely can leave the owner looking at a pending message when there is no known live turn or end event.

**Evidence.** By reading, a started receipt becomes `interrupted` after a client restart and an old result cannot settle a newer attempt. The server's sweep knows whether there is a result but does not know whether a prompt reached a harness. The scout found that Claude queues overlapping prompts, so a mistaken second admission has a visible effect. [Client receipt decisions](../../../src/client/internal/link/receipts.go#L116) · [Attempt check](../../../src/server/internal/link/outbox_result.go#L25) · [Sweep settlement](../../../src/server/internal/link/outbox_sweep.go#L117) · [Scout, overlapping prompts](../../../.foundry/go-rewrite/results/w2-scout-agent-run.md#L141)

**Smallest repair.** Define `failed` at the client as definite non-submission if it is to move the agent to idle. Give ambiguous prompt submission a separate resolution, including `interrupted` and server timeout. Leave the current turn fenced until the client proves the session ready or the process is confirmed gone. Make every such outcome conditional on the matching start, run and active turn. Test a prompt whose submission succeeds just before the receipt or connection is lost.

### logic 9 | MAJOR | The reserved event space cannot both preserve order and finish a stop during a full queue

**Draft.** The runner finishes putting output in order before `TurnEnded`. A reserve lets it report a stop while output waits. A12 requires a complete thread after a stop with the server away. [Output order and reserve](../../../docs/specs/2026-11-27-running-an-agent-design.md#L386) · [A12](../../../docs/specs/2026-11-27-running-an-agent-design.md#L551)

**Scenario.** The normal queue fills and the runner holds the last fragment of the answer. The owner had queued a stop just before the disconnect. Killing the group can discard text still in the harness pipe. Numbering `AgentEnded` in the reserve before the held fragment can show `stopped` before the last text is admitted. Waiting to number the end behind ordinary output means the reserve by itself provides no early stop report. If the client dies while it waits, the fragment can have been in memory for far longer than 300 milliseconds, and unread text can still be in the pipe.

**Evidence.** By reading, `appendContext` checks byte and count limits before it assigns the next number. `Ack` frees room. The server has to receive numbered events in order. The same ACP connection carries output and permission requests, so pausing reads can delay handling the request as well. [Client `appendContext`](../../../src/client/internal/link/outbox.go#L23) · [Client `Ack`](../../../src/client/internal/link/outbox.go#L84) · [Server `ApplyEvent`](../../../src/server/internal/link/inbox.go#L49) · [Scout, permission requests](../../../.foundry/go-rewrite/results/w2-scout-agent-run.md#L153)

**Smallest repair.** Define what a stop preserves. Budget enough reserved bytes and event slots for the accepted pending tail and its terminal events, and append them in that order. Keep the process kill independent of a blocked output writer. Say which unread output can be lost on a forced stop or client crash, and remove the time bound on a batch blocked by a full queue. Make A12 compare the accepted text through the recorded cutoff and observe the process exit as well as the eventual ordered thread.

### logic 13 | MINOR | A freshly numbered repeat is reported as missing text

**Scenario (conditional).** After a complete item is stored, the same logical chunk for that item is submitted a second time with a new link number. ## How the state rows behave across interruptions

A server restart after a committed change preserves it. A restart before that commit leaves the command or numbered event eligible for its normal retry. The rows below apply that distinction and call out where a client process restart changes what can be proved. [Server result rules](../../../src/server/internal/link/outbox_result.go#L11) · [Server event rules](../../../src/server/internal/link/inbox.go#L27) · [Client receipts](../../../src/client/internal/link/receipts.go#L64)

|---|---|---|
| Creation to `starting` | A committed keyed write returns the same project and lead after a lost reply. An uncommitted write has started no client work. | An unstarted command can run before expiry once reconciliation opens the gate. A started receipt is interpreted as interrupted. See logic 4 and logic 11. |

It must precede the first output and end. | Old start events must be applied as old-run events before reporting the run change. The same start receipt cannot submit the goal twice. See logic 2 and logic 4. |

A buffered start may already have proved submission before run reconciliation. See logic 1 and logic 2. |
| Start deadline to `failed` | The sweep can recover the deadline after a server restart. | `AgentEnded` to `stopped` or `failed` | The numbered event proves what ended when it is applied. A stop receipt or mere offline status does not prove process exit. | Old `working` or `idle` agent to `failed` on a new run | A lost link or a server restart alone retains the run. ## Checks that held

- The existing inbox commits the effect and sequence mark together. A server restart after that commit and before the acknowledgement can replay the exact event without duplicating the effect. This supports A6 and the same-number repeat case in the thread. [Server inbox](../../../src/server/internal/link/inbox.go#L49) · [Client replay](../../../src/client/internal/link/replay.go#L23)
- The client checks receipts before expiry. An expired new start does not send the first goal. An interrupted receipt does not submit it again. A completed receipt can return `done` again on a new attempt, while the server accepts a settlement only once for the current dispatched attempt. [Client `Begin`](../../../src/client/internal/link/receipts.go#L64) · [Client result handling](../../../src/client/internal/link/commands.go#L193) · [Server `AcceptResult`](../../../src/server/internal/link/outbox_result.go#L11)
- The server store can commit the project, lead, goal, command and browser receipt in one write. The Machines code demonstrates passing a store transaction to the Link part. The draft's rule 3 boundary can use the same pattern for Agents. [Store `WriteOnce`](../../../src/server/internal/store/receipts.go#L41) · [Machines `queueConnectedAction`](../../../src/server/internal/machines/commands.go#L42) · [Foundation rules 3 and 4](../../../docs/specs/2026-11-25-go-rewrite-foundation-design.md#L358)
