REVISE
Grade 4/10

Cross-vendor review. A Codex worker reviewed the draft written in a Claude session at commit `3e00db5d` on `sprint-0`.

The findings are based on reading the draft, the approved foundation and the current source. The scenarios exercise the proposed behavior against the existing link. The proposed sprint was not run.

## Findings

### logic 1 | BLOCKER | A start can stay `starting` after the link has finished the command

**Draft.** The agent leaves `starting` when the client reports that it accepted the first message or that the start failed. `StartAgent` carries the goal. [State rows](../../../docs/specs/2026-11-27-running-an-agent-design.md#L149) · [Start command](../../../docs/specs/2026-11-27-running-an-agent-design.md#L177)

**Scenario.** The server commits the project and loses the connection before the client receives the start. If the client reconnects after expiry but within the retry window, it can answer `expired` without ever running the handler that would emit `AgentStartFailed`. If it stays away past the 23-hour cutoff, the command is no longer offered. The sweep eventually stores `timed_out`. Neither path takes the agent out of `starting`. In a second window, the client sends the goal and crashes before finishing its receipt. The next attempt returns `interrupted` and cannot safely send the goal again. A buffered `AgentStarted` might still arrive. The next client can also replay a completed `done` receipt after the server has already applied `AgentStarted`. That result confirms delivery of the same start. Treating it as a second start would replay a state change after the first turn may already have ended.

**Evidence.** By reading, `Store.Begin` checks the receipt before expiry. A started receipt becomes `DecisionInterrupted` after the client process dies. `AcceptResult` settles only the current dispatched attempt once. The sweep records `timed_out` separately, at least 24 hours after expiry. None of those paths currently applies an agent transition. [Client receipts](../../../src/client/internal/link/receipts.go#L64) · [Server result handling](../../../src/server/internal/link/outbox_result.go#L11) · [Retry cutoff](../../../src/server/internal/link/outbox_claim.go#L58) · [Sweep](../../../src/server/internal/link/outbox_sweep.go#L138)

**Smallest repair.** Persist the start command identifier with the lead and tie the start events to it. Define a durable transition for every final outcome, including server timeout and machine removal. An expired start with proof it never ran can fail with that reason. Interruption or server timeout leaves delivery of the goal uncertain until reconciled and must never automatically submit it again. Make success depend on the matching start event and make repeated results harmless in the same transaction that settles the matching command or its durable follow-up.

### logic 2 | BLOCKER | The restart report can fail a start that belongs to the new client

**Draft.** `AgentsRunning` is sent once per process. Its list fails every other nonterminal agent on the machine. [Event and reconciliation rules](../../../docs/specs/2026-11-27-running-an-agent-design.md#L197)

**Scenario.** The previous client leaves numbered text or lifecycle events on disk. A `StartAgent` is also pending, with no receipt. The replacement client queues an empty inventory behind the old events. The server can send the pending start before it has applied that inventory. The replacement starts the agent, and its `AgentStarted` is numbered after the empty inventory. The inventory then fails the new start. A strict state machine leaves the live process attached to a failed agent. Allowing a late `AgentStarted` to revive terminal rows would also allow an old event to revive a dead process.

**Evidence.** By reading, the client sends persisted events in sequence, while the server has a separate command turn immediately after stream admission. Its command cursor checks approval, expiry and the stream assignment. It has no event replay or process inventory barrier. [Client replay](../../../src/client/internal/link/replay.go#L23) · [Server stream loop](../../../src/server/internal/link/stream.go#L50) · [Command selection](../../../src/server/internal/link/outbox_claim.go#L38)

**Smallest repair.** Give the client process a stable identity across reconnects and associate it with process-owned agents and lifecycle events. Append the inventory after the old events. Hold new agent work until the server has committed that inventory. Reconcile only agents owned by an older process. Leave an undispatched or unstarted command to its normal expiry or admission rule. Preserve old thread text in sequence and keep terminal lifecycle transitions guarded.

### logic 3 | BLOCKER | The proposed revision 2 files cannot carry the new commands and events

**Draft.** Revision 2 adds `agents.proto` and `folders.proto` beside the frozen files, whose contents stay the same. The server refuses revision 1 with `link_revision_mismatch`. [Part contracts](../../../docs/specs/2026-11-27-running-an-agent-design.md#L68) · [Link revision 2](../../../docs/specs/2026-11-27-running-an-agent-design.md#L161)

**Scenario.** A builder adds the two files and updates the revision constants. The deployed stream still carries the original `Command` and `Event`. Their `oneof` declarations cannot select a message in either added file. The freeze test also rejects a revision 2 entry while the two revision declarations in `link.proto` still say 1. Putting the service in a different package would change the procedure the old client calls and needs an explicit refusal path at the old procedure.

**Evidence.** By reading, `OpenRequest` and `OpenResponse` carry the fixed envelopes, and the existing mismatch runs inside `Open`. `TestLinkIsFrozenAtItsRevision` checks all current link files and both revision declarations against the latest entry. The shell gate compares prior revision lines at their original line numbers. [Stream envelopes](../../../src/contracts/proto/lgtm/link/v1/link.proto#L224) · [Command actions](../../../src/contracts/proto/lgtm/link/v1/commands.proto#L41) · [Event reports](../../../src/contracts/proto/lgtm/link/v1/events.proto#L45) · [Generated procedure](../../../src/contracts/gen/go/lgtm/link/v1/linkv1connect/link.connect.go#L62) · [Mismatch check](../../../src/server/internal/link/handshake.go#L190) · [Freeze test](../../../src/contracts/freeze_test.go#L57) · [History gate](../../../scripts/check-go.sh#L20)

**Smallest repair.** Keep the current `Open` procedure and evolve the current envelopes with new field numbers. Preserve the revision 1 files at their frozen commit and the revision 1 record line in the current tree. Append the complete revision 2 hashes and update both handshake declarations and programs together. Check the revision 2 freeze against the revision 1 base during review. Advance the base after that cross-check passes. Include an upgrade case with outstanding revision 1 reports and receipts in the existing client store.

### logic 4 | MAJOR | Waiting for the first prompt reply can turn a healthy answer into a failed start

**Draft.** The agent becomes `working` when the client reports that the session is open and the first message is accepted. The runner gives startup, session setup and sending that message 120 seconds in total. [Starting state](../../../docs/specs/2026-11-27-running-an-agent-design.md#L149) · [Runner deadline](../../../docs/specs/2026-11-27-running-an-agent-design.md#L227)

**Scenario.** Claude begins answering within seconds and takes three minutes to finish. If the client waits for the Agent Client Protocol (ACP) version 1 `session/prompt` reply as proof of acceptance, the website can show `starting` while text arrives, then declare a start timeout. The reply is the end-of-turn result. Conversely, declaring delivery as soon as the frame is sent gives the server a weaker fact than harness acceptance.

**Evidence.** By reading, the scout saw Claude's prompt replies report `end_turn` or `cancelled`. The previous runner treated a successful frame write and the later turn outcome separately. [Scout, overlapping prompts](../../../.foundry/go-rewrite/results/w2-scout-agent-run.md#L141) · [Previous runner's prompt path](../../../packages/engine/src/runner/AcpRunner.ts#L998)

**Smallest repair.** Name the observable boundary that ends startup. For the probed adapter, use a confirmed prompt frame write as submission, with a separate event for the eventual reply or refusal. Commit the matching start report to the client queue before publishing that turn's output. Keep the 120-second startup deadline off the already-submitted turn.

### logic 5 | MAJOR | A late prompt result or cancellation can affect a different turn

**Draft.** A non-successful `Prompt` puts the agent back to `idle` and says the message did not reach it. `TurnEnded` and `CancelTurn` carry only the agent identifier and, for `TurnEnded`, its outcome. [Commands and result rule](../../../docs/specs/2026-11-27-running-an-agent-design.md#L172) · [Event fields](../../../docs/specs/2026-11-27-running-an-agent-design.md#L194)

**Scenario.** The adapter accepts a prompt before the client crashes and leaves an unfinished receipt. The server later receives `interrupted`. The message may already have run, so the promised thread note would be false. Also, a `TurnEnded` can commit while its separate result is still outstanding. The owner starts the next turn, then the old command can be settled by the server sweep. A handler that applies the reset to the agent alone can mark the new turn idle. Independently, a tab that still shows the old turn can send `CancelReply` while a second tab has already started the next one. An agent-only request gives the server no way to distinguish those turns.

**Evidence.** By reading, a started receipt survives the client process, and a final command result and a numbered event are committed independently. The previous runner distinguished the accepted prompt from the terminal outcome and scoped cancellation to the active reply. [Receipt lookup](../../../src/client/internal/link/receipts.go#L116) · [Server result write](../../../src/server/internal/link/outbox_result.go#L11) · [Event application](../../../src/server/internal/link/inbox.go#L27) · [Scout, sessions and cancellation](../../../.foundry/go-rewrite/results/w2-scout-agent-run.md#L27)

**Smallest repair.** Persist one active turn identifier, using the user item number if desired. Include it in `CancelReply`, `CancelTurn`, turn events and the command correlation. Admit `SendMessage` and change its state inside the same checked transaction. Settle only the matching turn. Distinguish confirmed non-delivery from uncertainty and keep an uncertain session fenced until there is evidence of readiness or termination.

### logic 6 | MAJOR | A stop can finish too early or remain unresolved

**Draft.** `StopAgent` is allowed from `starting`, `working` and `idle`. It moves the agent to `stopped` after the client reports process exit. `CancelTurn` is done once the harness was told to cancel. [State table](../../../docs/specs/2026-11-27-running-an-agent-design.md#L147) · [Control command results](../../../docs/specs/2026-11-27-running-an-agent-design.md#L177)

**Scenario.** `StopAgent` arrives while the adapter download for `StartAgent` is still running. There is no process group to kill yet. If the stop reports success, the pending start can still spawn a process after the agent is `stopped`. If it fails, the table gives the owner no defined stop outcome. A disconnect before delivery can also leave the stop expired without an exit report. A late `TurnEnded` from a cancellation can then race the stop or a spontaneous crash. A forced client exit is a different case from orderly teardown. A process group identifies the children to terminate but does not itself guarantee cleanup when the client dies.

**Evidence.** By reading, the shared permit is released when a command send and dispatch write finish. It does not serialize the client-side effect of that command with the next send. The existing client runs a long command outside the stream loop. The draft provides a startup deadline and a graceful shutdown statement but no rule for these races. [Server send loop](../../../src/server/internal/link/stream.go#L99) · [Client asynchronous scan](../../../src/client/internal/link/commands.go#L230) · [Runner lifecycle](../../../docs/specs/2026-11-27-running-an-agent-design.md#L227) · [Client teardown](../../../docs/specs/2026-11-27-running-an-agent-design.md#L268)

**Smallest repair.** Store a pending stop intent with the command. Process it against the agent's startup reservation as well as its process group, and block new prompts while it is pending. Confirm a stop only after no further spawn is possible and the group is gone. Define what happens on an expired stop, a cancel that never produces a turn end, and a competing exit. Make `stopped` and `failed` terminal for lifecycle events. Specify how the supported service setups reap the process group on a forced restart, and exercise that case in S7.

### logic 7 | MAJOR | Full event storage can block replay and lose the uncommitted tail

**Draft.** The runner pauses harness reads when the event buffer is full, drops nothing, and sends `AgentsRunning` once after process start. S6 expects uninterrupted text across a server restart. [Output limits](../../../docs/specs/2026-11-27-running-an-agent-design.md#L203) · [S6 and S7](../../../docs/specs/2026-11-27-running-an-agent-design.md#L343)

**Scenario.** A long answer fills the disk queue while the server is away. If the replacement client's startup waits synchronously to append `AgentsRunning`, it must wait for acknowledgements that its stream loop has yet to process. Dropping the report on the full-buffer error would leave old agent state unreconciled. If the client process itself dies while holding a 300-millisecond batch or waiting for a free slot, that tail has never been written to disk and will not replay. The same full queue can delay control events produced by stop or cancel.

**Evidence.** By reading, `Store.Append` rejects an append at the count or byte limit and allocates no event number. The defaults are 10,000 events and 64 mebibytes. `Ack` frees capacity. The existing link loop processes acknowledgements and can flush pending reports after them. The persisted event guarantee begins at a successful append. [Buffer defaults](../../../src/client/internal/link/store.go#L149) · [Append and acknowledgement](../../../src/client/internal/link/outbox.go#L23) · [Client acknowledgement path](../../../src/client/internal/link/session.go#L656)

**Smallest repair.** Keep the link and its acknowledgement handling independent of an output producer waiting for space. Retry the same pending record when space is freed, and let startup replay proceed while the inventory is waiting. Hold new work behind the inventory barrier. Define orderly flushes before terminal events and state explicitly that a client crash can lose text that never reached disk. Exercise reconnect and restart with a deliberately full buffer.

### logic 8 | MAJOR | The folder calls can time out after creating a repository

**Draft.** `AddRepository` and `CreateRepository` wait up to 20 seconds. `LookAtFolder` reports its answer in an event. The `MakeRepository` row defines `done` but no payload with the canonical folder or repository metadata. [Website calls](../../../docs/specs/2026-11-27-running-an-agent-design.md#L94) · [Folder commands and events](../../../docs/specs/2026-11-27-running-an-agent-design.md#L172)

**Scenario.** All three shared send permits are busy, or the machine disconnects before the send. The website call times out. A command with a longer expiry can still start later. Even with a 20-second expiry, a create started at second 19 can make the directory after the browser has received an error. If the server restarts after the directory is initialized, an in-memory waiter is gone. A replayed `done` can beat a numbered folder result to the server. A fresh submission can create duplicate database records or report failure for a directory that already exists. The existing dialog also supports adding a known repository to another machine. A request with only machine and path loses the selected repository's identity.

**Evidence.** By reading, the permits cover claim and send across streams, and the claim cursor retries up to the 23-hour cutoff. The client sender gives command results priority over buffered numbered events. `State.Enqueue` currently returns an error only, so callers have no command identifier to use for a durable lookup. The dialog's `AddRepository` action already receives the known repository. [Shared permits](../../../src/server/internal/link/outbox_send.go#L17) · [Retry selection](../../../src/server/internal/link/outbox_claim.go#L58) · [Result priority](../../../src/client/internal/link/session.go#L623) · [Enqueue interface](../../../src/server/internal/link/outbox.go#L21) · [Dialog submit](../../../src/frontend/src/screens/service.tsx#L456)

**Smallest repair.** Store a request-keyed operation and its command identifier in a short transaction. Carry the existing repository identifier when the owner is attaching another folder to it. Release the transaction before waiting. Use the 20-second deadline for initial admission and return a Connect deadline error that says the outcome is pending or unknown if execution may have begun. Give both folder commands a correlated, durable answer with the canonical folder and metadata. Finalize registration idempotently on the server even when the caller is gone, and have a retry read or wait for that same operation. After an interrupted create, use a new command to reconcile only the directory the operation owns.

### logic 9 | MAJOR | One transaction can still leave a lower-numbered start command behind the cursor

**Draft.** Projects calls Agents in the same write that stores the project, lead, first item and `StartAgent`. [Server data write](../../../docs/specs/2026-11-27-running-an-agent-design.md#L298)

**Scenario.** Two valid project creates for different repositories on one machine use the same link. The first transaction inserts command sequence 41 and pauses. The second inserts 42, commits and wakes the stream. The cursor reads 42 and advances. When 41 commits, its wake leaves the cursor above 41, so the first project can stay `starting` on a healthy link. If the first create commits but loses its website reply, a retry also needs to recover the original project and lead. A duplicate-project refusal cannot identify the result of that submission.

**Evidence.** By reading, the outbox allocates `seq` on insert. `readClaimPage` reads only numbers above the current cursor. The feed lock only orders feed rows at the end of the transaction, and an outbox feed wake does not reset the cursor. The built Machines path already locks the machine before it enqueues. `WriteOnce` can save a reply in the same transaction. [Command sequence](../../../src/server/internal/link/migrations/0002_link_commands.sql#L1) · [Claim cursor](../../../src/server/internal/link/outbox_claim.go#L62) · [Feed lock](../../../src/server/internal/store/feed.go#L131) · [Outbox wake](../../../src/server/internal/link/run.go#L246) · [Existing enqueue pattern](../../../src/server/internal/machines/commands.go#L42) · [Request receipts](../../../src/server/internal/store/receipts.go#L41)

**Smallest repair.** Use one keyed `WriteOnce` transaction. Take the same machine lock before allocating any command sequence and before locking agent rows. Pass that transaction to the owning Go interfaces for Agents and Link, and have each record its own changes. Persist the original project and lead identifiers in the reply. Enforce the one-project rule transactionally on a machine and canonical repository folder, so concurrent submissions and path aliases cannot start two leads in the same checkout.

### logic 10 | MAJOR | Thread batching does not define a replay-safe item boundary

**Draft.** The server appends text only when its position equals the stored length. A tool update may carry status alone. The runner closes an item at 32 kibibytes and continues in another. [Output event and append rule](../../../docs/specs/2026-11-27-running-an-agent-design.md#L194) · [Item limits](../../../docs/specs/2026-11-27-running-an-agent-design.md#L203)

**Scenario.** An item has 32,767 bytes and the next character takes four bytes. Cutting at the byte ceiling breaks the string. Carrying the old item position into the continuation makes the server reject its first chunk. If a status-only repeat is freshly numbered, its position can still equal the stored length and restore an older tool status. The numbered link handles a resent copy with the same event number. It cannot infer that two differently numbered events represent the same update. A 300-millisecond tail can also arrive after `TurnEnded` if the runner queues the end before flushing it.

**Evidence.** By reading, `ApplyEvent` suppresses a repeat by event number and commits the next number with the report effect. The link requires valid Unicode Transformation Format 8-bit (UTF-8) strings. The draft defines neither a position unit nor how items from the runner share thread identity and order with website messages. [Event application](../../../src/server/internal/link/inbox.go#L49) · [String value rules](../../../src/contracts/proto/lgtm/link/v1/link.proto#L14) · [Thread item numbering](../../../docs/specs/2026-11-27-running-an-agent-design.md#L134)

**Smallest repair.** Use byte offsets into the exact text sent, after redaction. Split at complete character boundaries and start a new runner item at offset zero. Let the server map each stable runner item identifier to one thread number on its first committed event. Define how to compare status revisions and handle gaps or conflicting overlaps explicitly. Flush every part of an answer in numbered order before queuing its `TurnEnded`.

### logic 11 | MAJOR | One oversized report can pin the numbered inbox

**Draft.** The message limit motivates a 32-kibibyte prompt and 16-kibibyte text batches. The other fields of commands and events have no stated encoded size bound. [Message limit](../../../docs/specs/2026-11-27-running-an-agent-design.md#L119) · [Command and report fields](../../../docs/specs/2026-11-27-running-an-agent-design.md#L172)

**Scenario.** A harness supplies a tool title over 64 kibibytes, or a choices report accumulates enough model labels to exceed the limit. The client disk queue can accept the encoded report. When the report reaches the head, the server rejects the frame before it can acknowledge the number. Reconnect retries that head and every event behind it, including lifecycle events, remains blocked. An oversized `StartAgent` can similarly be retried after a read failure if the server only checks the goal length and leaves the rest of the envelope unbounded.

**Evidence.** By reading, both readers limit the whole link message to 64 kibibytes. The default disk store allows one mebibyte per event. The receiver can consume an invalid decoded report, but an undecodable or oversized frame ends the stream before the event-number check. [Server limit](../../../src/server/internal/api/server.go#L28) · [Client limit](../../../src/client/internal/link/session.go#L54) · [Disk defaults](../../../src/client/internal/link/store.go#L149) · [Event rules](../../../src/contracts/proto/lgtm/link/v1/events.proto#L13)

**Smallest repair.** Budget the encoded envelope, including the event number, command metadata and all fields. Validate before a write can enqueue a command or number an event. Set bounds for paths, titles, notes, choice lists and inventory lists. Define how to split, shorten or refuse values while preserving the report sequence.

### logic 12 | MINOR | The stated website traffic limit has no corresponding bound

**Draft.** A `WatchThread` change sends the whole current item. One long answer supposedly costs at most a few hundred kibibytes. [Thread snapshot](../../../docs/specs/2026-11-27-running-an-agent-design.md#L121) · [Traffic claim](../../../docs/specs/2026-11-27-running-an-agent-design.md#L203)

**Scenario.** An answer produces 64 items of 32 kibibytes. Even one final copy of each item is two mebibytes before framing. Streaming a growing item also sends prefixes repeatedly. The 500-item snapshot bounds the reload by item count and does not bound any one answer to the stated figure.

**Evidence.** By reading, the draft allows a new item every time one closes and sets no total answer limit. The shared `watch` serves the current record for each matching feed row. [Output limits](../../../docs/specs/2026-11-27-running-an-agent-design.md#L203) · [Watch change delivery](../../../src/server/internal/watch/watch.go#L119)

**Smallest repair.** Describe the bounds per event, per item and per snapshot. Drop the per-answer traffic claim unless the design adds a total limit or a bounded update policy.
