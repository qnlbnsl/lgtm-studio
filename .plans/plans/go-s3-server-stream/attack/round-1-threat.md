REVISE

The handshake must reject weak registered Ed25519 keys before it can rely on a signature as proof that the machine holds a private key.

## Findings

### threat-r1 01 · MAJOR · D7 · The handshake needs to validate the registered key

The plan checks the proof before admission but gives no rule for rejecting a weak registered key. Enrollment checks that the public key is 32 bytes long and persists those bytes. By reading the local Go 1.26 verifier, its public-key constructor checks that the encoded point is on the curve, and verification checks the signature equation. The plan needs to establish the stronger key property required for proof of possession. `.plans/plans/go-s3-server-stream/plan.md:139`, `src/server/internal/link/rules.go:13`, `src/server/internal/machines/join.go:124`, `src/server/internal/machines/migrations/0001_machines.sql:3`, `src/contracts/proto/lgtm/link/v1/link.proto:115`.

A third-party enrollment client can use a valid join token to register a low-order public key. If the owner approves that record, the signature check alone can accept a proof without a machine private key. Admission can then displace the current stream and give the admitted peer authority over the record's durable reports and event mark.

Require a vetted Ed25519 public-key validation check for canonical encoding and membership in the non-identity prime-order subgroup before admitting an Open. Apply it to keys already in PostgreSQL and use the existing `unauthenticated` result at the proof decision. Ask the enrollment owner to reject the same invalid key class before creating new records. Name the validator and any pinned dependency before dispatch. Freeze a rejection test against a seeded existing row and verify that no admission, mark or feed change occurs.

Category is security, identity and integrity. The Server team owns the Open check. The plan omission is confirmed by reading. The exact image behavior remains to be checked. Risk score is 60. Severity is 6 for loss of control of a machine record, fallout is 5 for recovery by removal and enrollment, and probability is 2 because the shipped client generates ordinary keys and the case needs a weak key enrollment.

### threat-r1 02 · MAJOR · C8 · One cleanup backlog can delay offline for other machines

The plan routes disconnect through one worker, allows five seconds per attempt and projects online status from rows awaiting deletion. Its retry checks cover one failed identifier and replacement of that identifier. By reading the store, the row wait is bounded by the caller's write context, and independent writes can use separate pool slots. `.plans/plans/go-s3-server-stream/plan.md:199`, `.plans/plans/go-s3-server-stream/plan.md:239`, `.plans/plans/go-s3-server-stream/plan.md:241`, `src/server/internal/store/pool.go:301`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:385`.

Several machines can end while their individual rows are locked. Their serial cleanup attempts can consume more than 30 seconds before a later disconnect for another machine is tried. The owner can see that machine online past the promised cutoff even though PostgreSQL would accept its own delete and its live handle is gone.

Specify how fresh disconnects for unrelated machines make progress while retries wait. Give fresh work precedence over retries and use bounded concurrent attempts across machine identifiers, within the store's write budget. Keep exact-identifier deletion and cancellation independent of all cleanup. Set a healthy-path budget for the first attempt and test an unlocked machine behind a staged retry backlog. Keep the accepted stale display for a row whose own deletion fails.

Category is timing and availability. The Server team owns the worker. The missing isolation is confirmed by reading. Risk score is 48. Severity is 4 for stale status, fallout is 3 because retry repairs it, and probability is 4 because a shared outage or lock backlog can produce it.

### threat-r1 03 · MINOR · D7 · Forwarded addresses need a trusted immediate peer

The plan uses the private-stack option as `BehindProxy` and trusts the last forwarded address whenever that option is set. By reading, the option permits private or unspecified listeners. The composed application listener binds on all its interfaces and the service joins the application, database and vault networks. The option identifies a deployment mode and does not verify that a given request came from Caddy. `.plans/plans/go-s3-server-stream/plan.md:240`, `.plans/plans/go-s3-server-stream/plan.md:248`, `src/server/internal/app/start.go:399`, `deploy/compose.yaml:166`, `deploy/compose.yaml:194`, `deploy/Caddyfile:23`.

An enrolled machine with a path to the application listener that bypasses Caddy can report a valid-looking forwarded address on its direct connection. The owner can see that value as the machine's observed address while deciding whether to approve it, and disconnect can preserve the value. Proof still limits changes to that machine.

Have Server and Stack name the immediate proxy peer or enforce a Caddy-only ingress boundary. Accept the forwarded address only across that boundary. On other accepted connections use the transport peer. Specify how repeated or malformed forwarded header values are handled and test both the real Caddy path and the direct path under the same private-stack setting.

Category is security, metadata integrity. The Server team owns extraction, and the Stack team owns proxy isolation. The configuration gap is confirmed by reading. Reachability from an unprivileged host process depends on the deployment. Risk score is 12. Severity is 2 for a misleading display field, fallout is 3 for a value a later connection can correct, and probability is 2 because it requires a bypass path and a registered key.

### threat-r1 04 · MINOR · R9 · Open needs an explicit no-store response policy

The new Welcome response carries a connection credential. The plan limits application logs and storage but leaves response caching implicit. By reading, the built router sets `no-store` on session routes, and the existing Join and token creation handlers opt in explicitly. `.plans/plans/go-s3-server-stream/plan.md:66`, `.plans/plans/go-s3-server-stream/plan.md:122`, `.plans/plans/go-s3-server-stream/plan.md:139`, `src/server/internal/api/server.go:191`, `src/server/internal/link/join.go:43`, `src/server/internal/machines/records.go:33`.

A deployment that records successful responses because caching or response retention was enabled for the application has no explicit no-store direction on Open. It can retain the approved Welcome beyond the connection that produced it. Wave 1 has no consumer for the token, which limits the immediate consequence.

Set `Cache-Control: no-store` on Open before the Challenge writes headers and prove the header survives the real proxy under both protocols. Specify that app, proxy and client diagnostics omit frame bodies, with a test marker for the connection credential.

Category is security, credential confidentiality. The Server team owns the response, and the Stack team owns the proxy gate. The missing plan rule is confirmed by reading. Risk score is 6. Severity is 2 for retention of a credential with no current consumer, fallout is 3 for a credential that dies with its stream, and probability is 1 because the current proxy has no response cache.

### threat-r1 05 · MINOR · R9 · Machine metadata needs an at-rest decision

The plan stores workspace text, inventory, and current and last observed addresses, and it adds presence to the saved approval reply. By reading, those are plain application data. The stack provisions a named PostgreSQL data volume with restricted file permissions and no documented encryption requirement for that volume. The foundation's OpenBao protection applies to signing material. `.plans/plans/go-s3-server-stream/plan.md:104`, `.plans/plans/go-s3-server-stream/plan.md:121`, `.plans/plans/go-s3-server-stream/plan.md:123`, `.plans/plans/go-s3-server-stream/plan.md:199`, `src/server/internal/machines/project.go:32`, `deploy/compose.yaml:249`, `deploy/stack-prepare.sh:62`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:215`.

A copy of an unencrypted data volume can disclose workspace names and machine addresses, including those in an approval receipt retained for replay. The protected signing key remains separate.

Have the Stack team state the at-rest protection for the PostgreSQL volume and document how the supported installation supplies it, or record the specific owner-approved exception for machine metadata. Include the saved approval reply and retain the foundation's one-day receipt rule.

Category is security, confidentiality. The Stack team owns the volume, and Server owns the receipt inventory. The missing deployment policy is confirmed by reading. Risk score is 42. Severity is 6 for disclosure of private machine metadata, fallout is 7 because a disclosure cannot be undone, and probability is 1 because the scenario needs access to the data volume.

## Post-build checks

- **TH1 · Machine proof.** Through the pinned server image and both link protocols, compare a normal registered key, a seeded invalid or low-order key, and a proof from a different stream. Only the valid proof admits a stream. Refusals leave the connection, event mark and feed unchanged. The Server team owns the protocol capture and database evidence.
- **TH2 · Ingress and address provenance.** Use the real Caddy route and an authorized disposable direct fixture with private-stack mode enabled. Observe the transport-derived peer on the direct route and the address vouched for by Caddy on the proxy route. Check missing, repeated and malformed forwarding headers. Confirm the released host publishes only loopback and the application port is unpublished. Server and Stack own the watch observation and deployment evidence.
- **TH3 · Credential retention.** Observe two approved Welcomes, a waiting Welcome, a canceled stream and a reconnect. Expect unique approved tokens, an empty waiting token, no response storage permission and no token in application records, watch replies, or client, proxy and server logs. Check logs and fixed status messages on malformed frames and failed writes, using disposable markers. Server, Client and Stack own the captured headers, records and redacted diagnostics.
- **TH4 · Website authorization.** Open a signed-in machine watch, sign out, and commit a report after revocation. The expired watch receives no new data, and a new unsigned or disallowed-origin watch receives no machine records. An unsigned Open can obtain Challenge and still needs machine proof to admit. The Server team owns the protocol observations.
- **TH5 · Cleanup and removal.** Hold several cleanup writes while a different machine disconnects and inspect its authorized watch. The unlocked machine goes offline within the deployed check C8 deadline, and held rows lose their live handles immediately. During a removal or a replacement, a later frame on the old stream makes no durable change or new acknowledgement. The Server team owns the timed watch and database observations.
- **TH6 · Inherited installer credential.** When Stack integrates the planned standard-input form, observe the installed client invocation with a disposable join token. Expect the automated invocation to keep the token out of process arguments, diagnostics and files. Stack and Client own the installer observation.
