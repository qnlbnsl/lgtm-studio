# The server accepts machine streams and saves their reports

## Overview

The server will accept a connection from a machine that has already joined. It will prove both identities, replace any older connection from that machine, and save the reports that drive the Machines page. A machine can reconnect after either program restarts and continue from the last report the server saved.

A lost connection normally makes the page show the machine offline. If the database refuses the cleanup, the page can temporarily retain the last saved presence while the server retries. The server still stops treating that connection as live immediately.

The machines plan already owns joining and approval. This plan supplies the stream. A later plan sends approval notices and handles the page actions that ask a machine to do work.

## Key decisions

The frozen revision 1 link determines what the server accepts and what it sends. The machine proves its identity with a signed challenge. A waiting machine can report its facts, which the owner can see before approving it. The stack's private network carries the hop from the web server to the application in wave 1.

The database commit that admits a new stream replaces the old stream immediately. The new stream starts with the event number the server has committed. The process keeps a small record of which streams it can still use and checks that an older stream has not been replaced before it starts sending its first reply.

The page shows a machine offline once its connection row is deleted. If PostgreSQL refuses the delete, the page can temporarily show the last saved presence while the server retries. A page action that needs a live stream must check that the server still holds the exact stream. The command plan will use that check.

Full log → [decisions.md](decisions.md)

## Workstreams

### A machine proves its identity and replaces its old connection

The server proves its identity before it checks whether the machine is registered. It then checks the machine's proof and admits it in a database transaction. Tests pause competing streams at admission, during removal and before the first reply to verify which one can continue.

### A connected machine reports its facts and its load

The server saves each report and its number together. A check replays a report after a lost acknowledgement and counts its committed effect. The page shows joining until the current stream has reported both facts and harnesses while approved.

### The server clears disconnected streams and starts cleanly

The server ends silent streams and closes open streams when it shuts down. Tests hold a failed cleanup while another stream shuts down, then restart the server and check that it keeps the machine records and event numbers.

## Rollout order

1. Land the machine registry and the application wiring from the machines plan. Run their join and watch checks to establish the starting behavior.
2. Add the stream tables, the admission and the report writes. Exercise these with the scripted machine and real PostgreSQL before attaching a stream to the production router.
3. Install the stream in the server and its test fixture. Start clears old connection rows before listening. The migration ledger then requires a server that knows the new link migration, so recovery after that point goes forward with a corrected build.
4. Run the deployed checks with the sprint's client and installer. Run the orchestrator's combined checks to count committed reports and prove replay across a restart. The later command plan adds approval notifications and page actions that send commands.

Hold the machine row through `Registry.Lock` before a link write. A token write takes the token row first. Removal takes the machine row by deleting it and then deletes the link rows in the same write. The durable fence is the database row and its stream identifier. The first proposed cause wins. Log only fixed event names and the named fields. Use `link_stream_opened` with `machine_id` and `generation`, `link_stream_closed` with `machine_id` and `code`, and `link_event_applied` with `machine_id` and `sequence` after a committed mark advance. | Open decision | Code and reason | Sentence |
|---|---|---|
| Machine absent or removed | `failed_precondition`, `unknown_machine` | The server does not know this machine. Join it again. |
| Other revision | `failed_precondition`, `link_revision_mismatch` | The server speaks revision 1 of the link. |
