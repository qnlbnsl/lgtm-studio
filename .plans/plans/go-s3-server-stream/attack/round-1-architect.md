REVISE

The combined replay check lacks a way to stop the real client’s stream on each side of a durable event commit, so it cannot prove both recovery paths.

## Findings

### architect-r1 01 — MAJOR — C11

Design. Confirmed by reading. The Server team and orchestrator own this required gate.

The combined outage test has no assigned way to hold the selected write before commit or suppress its acknowledgement after commit. The PostgreSQL driver tracer in the plan belongs to a separately constructed item fixture. The combined server fixture adds only proof and admission callbacks. The client fixture has no transport injection. See `.plans/plans/go-s3-server-stream/plan.md:62`, `.plans/plans/go-s3-server-stream/plan.md:246`, `.plans/plans/go-s3-server-stream/plan.md:347`, `src/server/servertest/server.go:67`, and `.plans/plans/go-s3-client-link/plan.md:291`.

If the combined test observes a new audit row and then severs the stream, the real client may already have accepted its acknowledgement. The test can pass without exercising the case in which the client still has a report that the server already committed. Assign the pre-commit barrier to the combined test using the disposable database and identify the exact event write it blocks. Assign a test-only, context-aware post-commit, pre-acknowledgement barrier to the server fixture, or specify an equivalent frame-aware test proxy. Require evidence that the first cut left the mark unchanged and that the second cut preceded acknowledgement delivery. Reconnect with the same client store and assert that the second report produces exactly one audit row and leaves the outbox through the mark in `Welcome`.

### architect-r1 02 — MAJOR — C10

Timing bug. The plan gap is confirmed by reading and the runtime consequence remains to be tested by the Server team. The risk score is 48 (4 × 3 × 4) because a slow lookup can refuse one connection that can retry.

The handshake specifies a Proof deadline and a delayed registry lookup without saying how to preserve a timely Proof while the lookup is still running. It explicitly buffers a premature receive error but provides no arrival-time rule for a successful receive. See `.plans/plans/go-s3-server-stream/plan.md:137`, `.plans/plans/go-s3-server-stream/plan.md:139`, `src/contracts/proto/lgtm/link/v1/link.proto:108`, and `src/server/internal/store/pool.go:234`.

A known revision-1 machine can send a valid Proof immediately after Challenge while the database lookup is held past ten seconds. A handler that checks the expired timer after lookup or selects between the queued Proof and the ready timer can reject the timely Proof. Start the Proof read and its deadline at Challenge completion. Preserve the receive result and its monotonic completion time while the independent lookup runs. Apply lookup and revision refusals first, then decide whether Proof was timely from that recorded result. Test a timely valid Proof with a slow successful lookup and a late Proof under the same lookup schedule.

### architect-r1 04 — MAJOR — C11

Design. Confirmed by reading. The Stack team and orchestrator own this required gate.

The Stack team's current gate still consumes the server event log as evidence of order and uniqueness. The stream plan expects the gate to read `link_machines.event_mark` and explicitly allows diagnostic logs to be reordered or incomplete. See `.plans/plans/go-s3-server-stream/plan.md:66`, `.plans/plans/go-s3-server-stream/plan.md:347`, `.plans/plans/go-s3-server-machines/handoff-stream-and-commands.md:68`, `.plans/plans/go-s3-stack-client/plan.md:318`, and `deploy/test/checks.sh:586`.

The current deployed assertion can fail on the log order even when the database committed the reports correctly. If only forward progress replaces that assertion and the combined suite stays absent, the full gate can pass without checking whether a report's effect repeated. Name the Stack work item that changes the script, its documentation and gate G4. ### architect-r1 05 — MAJOR — C8

Timing bug. The plan gap is confirmed by reading and the runtime consequence remains to be tested by the Server team. The risk score is 24 (4 × 3 × 2) because several contended cleanups can temporarily misreport one otherwise healthy row.

The cleanup plan gives each attempt a five-second bound but gives a newly disconnected stream no bound on time spent behind other machines in the queue. The same plan makes each machine's visible offline transition depend on the successful delete. See `.plans/plans/go-s3-server-stream/plan.md:123`, `.plans/plans/go-s3-server-stream/plan.md:239`, `.plans/plans/go-s3-server-stream/plan.md:346`, and `docs/specs/2026-11-25-go-rewrite-foundation-design.md:385`.

If several older retries each reach their attempt timeout, a single serial worker can leave a newly disconnected machine's uncontended row online past 30 seconds without attempting its delete. The degradation approved for a failed delete then spreads to other machines. Specify how fresh disconnects get service independently of the retry backlog, with bounded work and fair retry scheduling. Add a test that keeps an older cleanup blocked while a different, uncontended stream closes, then observes that second machine go offline through `WatchClients` while the first attempt is still held.

### architect-r1 07 — MINOR — R4

The plan refreshes `last_heard_at` on a heartbeat and takes `Client.last_seen` from it. A successfully applied report updates the mark and readiness without refreshing `last_heard_at`. See `.plans/plans/go-s3-server-stream/plan.md:123`, `.plans/plans/go-s3-server-stream/plan.md:182`, `.plans/plans/go-s3-server-stream/plan.md:199`, and `src/contracts/proto/lgtm/v1/clients.proto:64`.

Advance `last_heard_at` in the existing transaction for an applied valid report and copy it on disconnect. Keep repeats and consumed reports free of side effects. Keep the nonce and connection token as the separate random byte values specified by the plan.

## Post-build checks

- **ARCH-P1.** The Server and Stack teams should hold a generated client's request side open while the server ends an idle link. For Connect and Google Remote Procedure Call (gRPC), observe that the receive worker exits before handler return and that the client sees the expected terminal code and reason when the transport remains writable. Repeat through the production proxy and leave an authorized website watch running to detect a shared transport regression.
- **ARCH-P2.** The Server team should rehearse migration 1 against a copy of a Part A database containing a waiting machine and a valid keyed receipt. Observe that the old binary refuses startup after the ledger changes and that the new binary can start again, serve the earlier receipt, and retain the registry and event marks. Verify this with both startup logs and database reads.
- **ARCH-P3.** The Server team and orchestrator should stage a new admission, then replace it while its first response is held before and after the underlying response write begins. Capture the first frame and final status under both protocols, including when the replacement has already closed. Only a frame whose send started before replacement may arrive.
- **ARCH-P4.** The Stack and Server teams should compare the address in a projected `Client` with the peer actually observed at the web hop. With proxy mode enabled, a supplied forwarded field must leave the proxy-observed peer as the displayed address. With proxy mode disabled, the same field must leave the direct peer address in place. Check that no change to the forwarding path affects Join or website sessions.
