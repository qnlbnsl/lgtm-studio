## Findings

### logic2-r1 1 — MAJOR — R4 — Retention can expire before a full day after commit

Both tables default `written_at` to the time of insertion. The receipt is inserted before the writer waits for the feed lock. The feed is inserted before commit. The sweep uses those two timestamps to decide what to delete. The design defines the feed timestamp as the commit time and gives receipts one day of retention. `.plans/plans/go-s1-server-store/plan.md:147`, `.plans/plans/go-s1-server-store/plan.md:163`, `.plans/plans/go-s1-server-store/plan.md:248`, `.plans/plans/go-s1-server-store/plan.md:259`, `.plans/plans/go-s1-server-store/plan.md:321`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:136`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:176`.

A receipt is stamped at noon, and the transaction commits a minute later after waiting for the feed lock. A sweep at 12:00:30 the next day can remove the receipt while the committed result is still less than a day old. A caller that lost the original reply can then run the mutation again with the same key. A delay at commit can also make the first retained feed row eligible for deletion early and cancel a subscriber that still needs it.

Define both retention periods from committed visibility and use a durable age source that cannot make an uncommitted row eligible. The planner can specify commit metadata with a conservative fallback when it is unavailable, or keep a durable timestamp from the first observation of each committed row for pruning. Record any conservative delay to cleanup in the decision log and state the PostgreSQL wall-clock assumption. Keep the state, receipt and feed insertions atomic. Add a gated test where insertion is older than the sweep cutoff and commit is newer. The sweep must preserve both rows, and the retry must replay once. [PostgreSQL 16 transaction information functions](https://www.postgresql.org/docs/16/functions-info.html)

### logic2-r1 2 — MAJOR — R5 — One stalled page read can suspend the two-second recovery path

The reader advances after a successful page and resumes on a later wake or poll after a failed page. The plan gives tests a bounded read deadline and names the ticker and listener as production defaults. It leaves the production time allowed for connection acquisition and a page query unspecified. `.plans/plans/go-s1-server-store/plan.md:383`, `.plans/plans/go-s1-server-store/plan.md:385`, `.plans/plans/go-s1-server-store/plan.md:387`, `.plans/plans/go-s1-server-store/plan.md:392`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:154`.

If a connection stalls during a page query after the last applied position, subsequent timer ticks and notification wakes cannot advance the one reader. Every subscriber stops receiving updates and lag checks stop as well. The test that injects an acquisition deadline can pass with this production behavior.

Require a finite production deadline for each page attempt, including pool acquisition, query and transaction cleanup. Give listener connection and registration attempts a separate finite budget. Keep the last successfully applied cursor on timeout and let a later poll or wake resume from it. Add a test that stalls an already-acquired connection and exercises the production deadline without injecting a replacement one.

### logic2-r1 3 — MAJOR — R4 — A retained receipt can reject the same request after an upgrade

The adapter hashes deterministic Protocol Buffers serialization of its parsed request, and the receipt stores only the resulting digest and reply. A mismatch refuses a retry. The reopening test uses the same request encoder on both sides of the restart. `.plans/plans/go-s1-server-store/plan.md:163`, `.plans/plans/go-s1-server-store/plan.md:293`, `.plans/plans/go-s1-server-store/plan.md:295`, `.plans/plans/go-s1-server-store/plan.md:299`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:178`.

An older binary can serialize an unknown lower-numbered field after its known fields. After an upgrade that recognizes the field, the new binary can serialize it before a higher-numbered field. The exact same request can now hash differently while the old receipt is still valid. The caller that lost the original reply gets a conflict instead of that reply.

Define a stable request fingerprint at the service boundary. Use an explicit encoding of the mutation's semantic fields and specify how unknown fields and schema changes are handled. Store a fingerprint format version and retain its verifier for as long as a receipt made with it can survive. Require a cross-version fixture that replays the same request and still refuses a changed semantic field. [Protocol Buffers guidance on fingerprints and deterministic serialization](https://protobuf.dev/programming-guides/serialization-not-canonical/)

### logic2-r1 4 — MAJOR — R4 — Deferred domain checks can reverse the final lock order

The store takes the feed lock after the callback and receipt, then commits. The plan allows a part to own its table constraints and does not place deferred domain checks before the feed lock. `.plans/plans/go-s1-server-store/plan.md:142`, `.plans/plans/go-s1-server-store/plan.md:246`, `.plans/plans/go-s1-server-store/plan.md:248`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:146`.

Writer B holds an update lock on an existing parent row. Writer A inserts a child with an initially deferred foreign key, takes the feed lock and reaches commit. Its deferred check tries to acquire a key-share lock on B's parent row. B tries to flush its own changes and waits on A's feed lock. PostgreSQL aborts one otherwise valid write to break the cycle. Until then, an unrelated third feed writer waits as well.

Run deferred domain checks before taking the feed lock. For example, set constraints to immediate after the callback and before the feed flush. Keep production feed inserts free of deferred work that can acquire domain locks. Keep the test-only commit gate after allocation by deferring its constraint through a test seam immediately before the feed insert. The mutation then still exercises a writer stalled during commit. Add the two-writer constraint case and require both valid writes to finish. [PostgreSQL 16 constraint timing](https://www.postgresql.org/docs/16/sql-set-constraints.html) [PostgreSQL 16 row locks and deadlocks](https://www.postgresql.org/docs/16/explicit-locking.html)

### logic2-r1 5 — MAJOR — R5 — The frozen snapshot test admits a second transaction

The required test commits a competing write after the snapshot loader's first read. It catches a split that reads records first and the head second. The specified mutation says to split the two reads and does not require probing the opposite order. `.plans/plans/go-s1-server-store/plan.md:381`, `.plans/plans/go-s1-server-store/plan.md:474`, `.plans/plans/go-s1-server-store/plan.md:478`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:165`.

A builder can read head 10 in one transaction, read the old record in a second transaction, then pass the stated test because the test commits position 11 after both those reads. In production, a commit between the head read and the record read yields the new record in the snapshot at position 10 and sends position 11 again as a live update. The other split direction can lose position 11 altogether.

Freeze a test that proves the two reads share a database snapshot and mutate each split direction. For the head-first direction, gate before the loader's first query after the head has been read, commit position 11, and assert that an old head cannot be paired with new records. Keep the existing post-read barrier for the records-first direction. [PostgreSQL 16 transaction isolation](https://www.postgresql.org/docs/16/transaction-iso.html)

### logic2-r1 6 — MINOR — R2 — The Watch draft and store plan disagree on lag status

The store plan assigns `resource_exhausted` and lists the three response variants, the position range and the empty snapshot as comparison points. The current, unfrozen contract draft assigns `aborted`. It also uses an unsigned wire value, while the internal store and the plan's comparison use a signed value. The existing browser reconnects on either status. `.plans/plans/go-s1-server-store/plan.md:448`, `.plans/plans/go-s1-server-store/plan.md:468`, `.plans/plans/go-s1-server-store/plan.md:470`, `.plans/plans/go-s0-contract/draft/common.proto:17`, `.plans/plans/go-s0-contract/draft/common.proto:30`, `src/frontend/src/server/sync.ts:56`.

A caller that follows the draft and treats `aborted` as its specific reopen signal could stop after receiving `resource_exhausted`. A later adapter could omit the position on an empty stream because its numeric value is zero. Carry the lag status, explicit zero-position presence and numeric conversion into the sprint comparison before the contract freezes. Require the adapter to send the agreed status on a writable transport and to encode the full nonnegative store range, including zero with a present position message.

### logic2-r1 7 — MINOR — R5 — The subscription has no rule for a second Next before Ack

The exported interface specifies one in-flight row and rejects invalid acknowledgments, but it does not define a second `Next` before that row is acknowledged. `.plans/plans/go-s1-server-store/plan.md:400`, `.plans/plans/go-s1-server-store/plan.md:420`, `.plans/plans/go-s1-server-store/plan.md:422`.

A consumer calls `Next` twice while position 41 is outstanding. An implementation that searches after the acknowledged cursor can hand out position 41 twice. An implementation that advances its search can replace the outstanding row and reject the first acknowledgment. Define `Next` before `Start` and `Next` with an outstanding row to return a state error without changing the cursor or the outstanding row. Add a fixture that rejects the second call, accepts `Ack(41)` and then returns the next row.

## Answers to the attack questions

The primary key prevents ties, PostgreSQL defaults to no wrap, and the durable head includes the pruning floor after restart. The migration ledger orders contiguous versions per part and rolls back with the schema.
