### States for one machine

| State | Durable and observed behavior |
|---|---|
| No stream | A disconnected machine retains its mark, runs, command ledger, stages, and warning. A server restart clears stale connection rows. A removed machine has no enrolled identity or Link history. |
| Stream waiting at the barrier | The latest admitted stream receives Welcome with the committed mark, processes replay and heartbeats, and claims no commands. It becomes ready when the required mark is committed. Its writer sends the final acknowledgement before it can claim. |
| Ready stream | The ready run is durable. The exact current stream can claim after Welcome or the final acknowledgement, subject to the existing approval and command rules. |
| Refused new run | Refusal leaves the incumbent and ledger in place. Only an unseen run behind the committed mark updates the warning fence. A later ready admission with a higher generation or removal clears it. |
| Result waiting for an event | This state can coexist with any connection state. The saved first result stays outside claims and sweeps. An eligible event that covers its watermark settles it in the event write. Removal settles it as `removed` if it is still pending. |

### Ordering of competing events

The table assumes an eligible next event, a result initially matching the dispatched attempt, and a sweep with a due ordinary command. A machine lock orders durable writes. Stream frame acceptance additionally depends on the exact current stream.

| Pair | Both orders and their outcome |
|---|---|
| Reconnect and applied event | If the old event commits first, its mark is in Welcome. If replacement commits first, the old stream is fenced and the new stream can replay the event. The eventual effect is once. For an unseen announcement at the contested mark, the updated mark can instead cause a behind-mark refusal. |
| Reconnect and result | If the old result commits first, its stage or terminal row survives and is ineligible for resend. If replacement wins, the old frame is ineligible. An otherwise eligible resend can take the same saved result on a new attempt. The interim state and attempt can differ. |
| Reconnect and sweep | If sweep wins, a timed-out command is ineligible to send. If reconnect wins, admission alone does not protect it. A stage or settlement between admission and the sweep changes eligibility. An existing stage is protected in either order. |
| Reconnect and removal | If admission wins, removal fences it and forgets the identity. If removal wins, admission fails. Both end removed. A Welcome may have started in the first order. |
| Reconnect and restart | A committed admission before restart leaves durable run data and loses its live handle. Reconnecting after restart creates the handle from that data. A write interrupted before commit requires fresh admission. A lost Welcome is recoverable by presenting the admitted pair. |
| Applied event and result | If the event covers the result watermark, event first settles directly when the result arrives. Result first stages, then the event applies the report and settles. Both leave the report applied before settlement. For a result already covered by earlier history, a later report can lose the Projects open-state race. |
| Applied event and sweep | An event that reaches a pre-existing stage settles it regardless of sweep order. With an unstaged overdue folder command, a report first can close the operation successfully before timeout. A timeout first can close it with failure. The late event is still consumed and acknowledged on a current stream. |
| Applied event and removal | Event first can finish a report or covered result before cleanup removes the folders. A terminal result is preserved. Removal first ends unfinished work and fences the event. The final machine and folder state is the same, while the retained operation and outcome can differ. |
| Applied event and restart | A committed mark, report, and settlement survive. A replay of that number is acknowledged as a repeat. An interrupted transaction leaves all three unchanged and the event applies on replay after restart. |
| Result and sweep | Result first either settles or stages and survives the sweep. Sweep first can settle the unanswered command as `timed_out`, so the result cannot change it. A staged command is immune to a later sweep. |
| Result and removal | A covered result that settles first keeps its terminal outcome. A result that stages first is ended as `removed`. Removal first fences the result and ends the unfinished command as `removed`. |
| Result and restart | A committed stage or settlement survives. An uncommitted result must be replayed on a current dispatched attempt. No stale frame is accepted from the old stream. |
| Sweep and removal | Sweep first can preserve `timed_out` for an ordinary command. Removal first makes it `removed`. A staged command is `removed` in either order. |
| Sweep and restart | A committed timeout survives. An interrupted write leaves the command eligible for the next due sweep, including the startup sweep. Matching results arriving in between can win. A previously committed stage survives in either order. |
| Removal and restart | A committed removal survives and leaves no identity to reconnect with. If removal did not commit, restart leaves the registration and cleanup can be retried. Startup clearing of connections alone never removes the machine. |
