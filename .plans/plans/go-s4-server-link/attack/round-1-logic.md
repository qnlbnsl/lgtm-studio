### logic-r1 02 · MAJOR · Sprint 4 R8 · Two folder commands can repeatedly disconnect one healthy client

**Consequence and evidence.** Hold folder inspection A in the single Client Folders worker and commit B on the same approved machine. The proposed Link claim changes add readiness and staging predicates, but the existing cursor defers only scans and sends a second ordinary action on the next turn. Client Folders adopts the existing busy retry behavior on a different command, which exits the receive loop and reconnects. While A stays busy, B can trigger the same cycle on each new stream. This can interrupt other traffic and leave B to expire without an inspection. If busy is instead ignored locally, the existing per-stream assignment prevents retry on the still-current stream. The Link ordering test uses restart commands and the Projects ordering test only checks delivery order. Both can pass while neither demonstrates two actual inspections. [Link plan](../plan.md#L127) · [Link eligibility](../plan.md#L229) · [Claim cursor](../../../../src/server/internal/link/outbox_claim.go#L62) · [Client Folders plan](../../go-s4-client-folders/plan.md#L161) · [Client receive loop](../../../../src/client/internal/link/session.go#L557) · [Reconnect loop](../../../../src/client/internal/link/retry.go#L46) · [Projects test](../../go-s4-server-projects/plan.md#L99)

**Required change.** Agree on an independent folder-command queue discipline. For example, defer the next folder command on the server until the current folder command stages, settles, or stops blocking under the agreed expiry and reconnect rules. Recheck and wake the queue in the same durable write. Keep the existing scan behavior. Hold A in the real client, enqueue B, observe a heartbeat on the same stream and no premature B delivery, then release A before expiry and require both to inspect once in order. Repeat with two paths for the same checkout and verify both calls return the same stored folder.

### logic-r1 03 · MAJOR · Sprint 4 R12 · A machine with many repositories cannot be removed

Logic. Risk 72 (6 for an unusable removal action × 4 for an owner who needs help to remove the machine without losing other work × 3 for a large installation on one machine). Confirmed by reading. Owners are Store and Projects with Server Link.

### logic-r1 04 · MAJOR · Foundation R6 · Removal callbacks can create commands for a deleted machine

**Consequence and evidence.** The hook contract permits callbacks to enqueue for the locked machine. Removal runs settlement hooks and then removal hooks after the registry row has been deleted in the same transaction. Existing enqueue can insert a command with just the identifier because the Link ledger deliberately has no machine foreign key. An added part that enqueues a follow-up in either removal callback can therefore commit an unfinished command after the selected set was settled. No stream can claim it, and the existing sweep skips unfinished rows for absent machines. Projects currently has no such follow-up, but sprint 5 requires callbacks that can enqueue follow-up commands in other lifecycle paths. An unconditional helper shared by those paths can expose the gap. [Link enqueue contract](../plan.md#L78) · [Link removal](../plan.md#L230) · [Machine removal](../../../../src/server/internal/machines/records.go#L60) · [Enqueue](../../../../src/server/internal/link/outbox.go#L22) · [Ledger schema](../../../../src/server/internal/link/migrations/0002_link_commands.sql#L1) · [Sweep](../../../../src/server/internal/link/outbox_sweep.go#L117) · [Sprint 5](../../../../docs/specs/2026-11-27-running-an-agent-design.md#L493)

State explicitly that settlement callbacks with `OutcomeRemoved` and machine-removal callbacks cannot queue work for that machine. Keep enqueue available in admission, readiness, and ordinary settlement while the registry row exists. Use a test part that attempts enqueue from a removal-origin callback and observes rejection and no unfinished row or wake. Also prove that a live settlement can enqueue in its own transaction.

Logic and integrity. Risk 30 (6 for persistent invalid state × 5 for database repair × 1 for requiring a future callback that attempts the forbidden enqueue). Confirmed by reading. Owner is Server Link.

### One machine’s link and command states

| State | Permitted work and durable transition |
|---|---|
| No stream | The mark, latest admitted and ready runs, warning, and staged results survive. A valid admission creates a stream. A sweep can still time out ordinary unfinished commands. |
| Stream waiting behind the barrier | Valid replay and heartbeats proceed without command permits, claims, or cursor changes. The exact current stream may advance the mark. With approval still waiting, only valid Facts apply and other eligible numbers are consumed. The last committed replay acknowledgement precedes that stream’s first command. |
| Ready stream | The admission or prefix transaction makes the run ready. The writer may claim after Welcome or the final replay acknowledgement, subject to approval and existing standing-notice rules. Results still need the exact stream, assignment, and attempt. |
| Refused new run | This is a candidate outcome alongside any incumbent state. The candidate gets no Welcome and leaves the prior stream, ledger and run pair intact. A qualifying behind-mark refusal can write the warning and feed together. |
| Result waiting for an event | This is a command state that can coexist with any stream state. Its first eligible result keeps its payload and watermark. Claim and timeout skip it. A covering event settles it in the same write, or removal settles it as removed. |

### Pairs of events that can arrive in either order

In this table, reconnect means a replacement admission attempt. An event or result from the incumbent remains eligible only while the incumbent is current. A timeout sweep means the command has reached the existing cutoff and has no staged result.

| Pair | First order and reverse order |
|---|---|
| Reconnect and event | Reconnect first can fence the old frame and leave the new writer gated until replay. Event first advances the mark and can open the new stream immediately. A new boundary equal to the old mark plus one can admit first but be refused behind the mark if that event commits first. Same-run replay converges without duplicate effects. |
| Reconnect and result | Reconnect first fences the old attempt. If the ledger is eligible, a reoffer under the new attempt lets the client return its saved receipt. Result first can stage or finish and suppress the reoffer. An intervening cutoff or removal can make the difference permanent. |
| Reconnect and sweep | Reconnect alone does not protect an ordinary command from its cutoff. A sweep that wins can end it before the new attempt is assigned. A claim that wins can change its attempt or dispatch state, but a later eligible sweep can still end it. A stage present on either side blocks timeout. |
| Reconnect and removal | Admission first may get as far as publication or Welcome before removal ends it. Removal first refuses the attempt as an unknown machine. Both end with the machine removed. |
| Reconnect and server restart | A committed admission keeps its pair but loses its stream during startup cleanup. If startup finishes first, the subsequent admission can stay connected. A lost commit reply can change whether another pair is eligible. Durable history governs retry. |
| Event and result | For an eligible result covering a valid folder report, result first stages and the event settles in its report transaction. Event first applies the report and the result settles immediately when it arrives. The final rows agree. A result with a watermark already covered before that report can close the operation before a late report arrives. |
| Event and sweep | If a result is staged, sweep cannot settle it in either order. For an unstaged command, report first can finish the operation before the ledger times out. Sweep first can close the operation as unknown so that the later report advances only the mark. |
| Event and removal | Event first can finish an operation whose durable reply is preserved through removal, although its folder is then deleted. Removal first fails the open operation and leaves the former stream unable to apply or acknowledge that frame. |
| Event and server restart | If the write commits first, its report effect and mark survive even if the acknowledgement is lost. Restart before commit leaves both absent and requires actual replay. Successful replay reaches the same state once. |
| Result and sweep | Result first stages or records the real client outcome. Sweep first can record `timed_out` on an eligible unstaged row and later results are inert. A selection made before staging must recheck and skip after staging commits. |
| Result and removal | A covered result first can keep its original terminal outcome. A stage first still ends as `removed` if its event has not arrived. Removal first rejects the stale result and records `removed` for unfinished commands. |
| Result and server restart | A committed stage or terminal result survives. If restart wins before commit, the old stream is stale and a fresh eligible assignment and receipt replay are required. An already staged command stays blocked from resend and sweep. |
| Sweep and removal | Sweep first can leave an earlier `timed_out` terminal outcome. Removal first settles unfinished rows as `removed`, after which the timeout sweep skips them. In both orders the removal hook runs once and a committed terminal operation stays closed. |
| Sweep and server restart | Committed timeouts persist. A sweep interrupted before commit leaves eligible rows for startup or a later tick. The final outcome can differ if a result or removal wins before the later sweep. |
| Removal and server restart | Committed removal survives restart. Startup clears stale connections without deleting the machine or replacing the removal transaction. If removal was interrupted, the same request key must resolve through the stored receipt or execute one fresh removal on retry. |
