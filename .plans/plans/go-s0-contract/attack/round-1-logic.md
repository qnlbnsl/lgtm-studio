REVISE

The event rules can permanently delete a buffered report when a higher-numbered event reaches the server first and its acknowledgement covers the missing report.

## Findings

### logic-r1 01 — BLOCKER — C11 — An acknowledgement can delete an unapplied event

This is a confirmed design and data integrity gap for the Contract, Server and Client teams. Risk is 224 (8 for permanent report loss, 7 because the deleted report cannot be replayed, and 4 for a reconnect or scheduling fault).

The stream permits post-handshake frames in any order and orders replay only at reconnect. The inbox treats every higher event number as applicable and its acknowledgement covers all lower numbers. The local outbox rejects new appends when full without assigning them a number, so ordinary overflow cannot explain a gap in assigned numbers. If replay has event 41 pending and a live producer's event 42 gets sent first, applying and acknowledging 42 lets the client delete 41. Waiting for 41 after 42 gives the same loss because the server drops 41 as old. [Stream and acknowledgement rules](../plan.md:252) [Post-handshake ordering](../draft/link.proto:32) [Local outbox and deletion](../../go-s1-client-local/plan.md:585) [Required replay](../../../../docs/specs/2026-11-25-go-rewrite-foundation-design.md:288)

Give the active stream one event sender, with replay and live reports passing through the same numbered queue. For wave 1, accept exactly the next number, re-acknowledge a duplicate at the durable mark, and end the stream on a gap so the client can replay from the first missing number. Commit the report and mark in one transaction and acknowledge only after commit. Treat a supported but unusable report as invalid without advancing the mark. Specify how an unknown report under a compatible future revision is durably skipped and counted in that same mark, or negotiate a revision that cannot send it. Use the same committed mark in `Welcome` and `EventAck`. Make a full outbox retry or coalesce an unnumbered snapshot after space opens. If deliberate holes are kept, give them an explicit authenticated skip message or range and test that the sender can never skip a numbered record it still owes.

### logic-r1 02 — MAJOR — R6 — The server and client disagree on when a command expires

This is a confirmed design gap for the Contract, Server and Client teams. Risk is 120 (6 for unwanted or missed machine work, 5 for manual recovery, and 4 for a clock fault).

The draft says to use the client's wall clock. The plan leaves clock correction optional. If the client's clock is two minutes slow, a previously queued restart can run after its server expiry. A fast clock can refuse a valid restart. A completed command replayed after its expiry can also receive either its saved success or a fresh expired outcome under the two unqualified rules. [Expiry and replay](../plan.md:252) [Clock assumption](../plan.md:562) [Local receipt order](../../go-s1-client-local/plan.md:642) [Design expiry rule](../../../../docs/specs/2026-11-25-go-rewrite-foundation-design.md:283)

Make the deadline immutable and define an exclusive deadline in server time. For example, have the server take `Welcome.server_time` after receiving `Proof` and immediately before sending `Welcome`. The client can add its elapsed monotonic time since sending `Proof` as a conservative upper bound, with an agreed allowance for clock drift and a rule for invalidating stale samples. The server must stop issuing fresh executions at expiry. The client must replay a durable result first, even after expiry, and reject a fresh execution if it cannot establish that it is still valid. Specify the server's disposition of an in-flight command at expiry so expiry alone cannot overwrite a valid completion. Use a fresh timing sample if the teams cannot maintain the bound from `Welcome.server_time`.

### logic-r1 03 — MAJOR — R6 — A command can finish after its attempt was replaced

This is a confirmed design gap for the Contract, Server and Client teams. Risk is 120 (6 for a stuck command or incorrect result, 5 for manual recovery, and 4 for a disconnect during work).

Attempt 1 starts a scan. After reconnect, attempt 2 arrives while it is still running. The client's receipt plan returns `DecisionRunning` without sending a result. If the original worker finishes under attempt 1, the server ignores the only completion it receives. An interrupted receipt after a crash has no named wire outcome. For restart, a crash between recording success and exiting can also leave a receipt that confuses accepting a restart with observing that it happened. [Retry and restart](../draft/commands.proto:18) [Result and outcomes](../draft/commands.proto:34) [Local receipt states and replay](../../go-s1-client-local/plan.md:628) [Local running receipt rule](../../go-s1-client-local/plan.md:643)

Assign attempt 1 on first dispatch, persist each increase before send, and accept only the current attempt from the current stream with one conditional terminal write. Ignore identical duplicate results, reject future attempts and conflicting terminal results, and stop at the largest supported attempt without wrapping. Bind the waiting attempt to a durable command identifier. On completion, send the receipt under the newest attempt offered on the current stream. Add `COMMAND_OUTCOME_INTERRUPTED` or explicitly map it to a terminal `FAILED` that cannot rerun the identifier. Record that a crash between intent and effect leaves the effect uncertain. Reconcile state from `Welcome`, and use a fresh identifier for a new action after an interruption. Define the restart result as a durably accepted restart, then exit, with a receipt that can be replayed if sending the result fails. Keep command identifiers and receipts valid for the full retry window.

### logic-r1 04 — MAJOR — D7 — Removal depends on delivery to a stream that may already be gone

This is a confirmed design gap for the Contract, Server and Client teams. Risk is 120 (6 for a machine removal that needs manual recovery, 5 for support intervention, and 4 for removal during a connection fault).

The draft forgets the machine key after it sends `APPROVAL_REMOVED`. An offline machine has no stream to receive that command. A connected machine can also disappear after the owner removes it, before the notice reaches it. It then receives the same `unauthenticated` as any unknown machine, while the client brief expects removal to stop `run` cleanly. Equal revision with different names or approval values is also unspecified. [Removal and state revision](../draft/commands.proto:64) [Unknown machine status](../draft/link.proto:133) [Client stop condition](../../go-s3-client-link/plan.md:48) [Design removal rule](../../../../docs/specs/2026-11-25-go-rewrite-foundation-design.md:254)

Make revocation and the active-stream fence effective when removal commits. Treat a removal notice on the outgoing stream as best effort. Define a terminal, recognizable removal result on an authenticated server connection, for example a distinct code backed by a tombstone for the machine identifier without its key. Document how a client stops when it cannot securely distinguish removal from an unknown identity. Validate state and apply it only at a greater revision. Treat an equal, identical revision as a no-op and reject an equal, conflicting revision. Install the authoritative `Welcome.state` before processing commands. Start revisions at 1 and fail closed on exhaustion.

### logic-r1 05 — MAJOR — C5 — Join has conflicting single-use and retry rules

This is a confirmed design gap for the Contract and Server teams. Risk is 108 (6 for an enrollment that requires a new attempt, 3 for repair by the owner, and 6 for an ordinary retry or cancellation).

The same used token and key can both return success and receive `permission_denied`. If the insert commits and the reply is lost, the wrong interpretation leaves a waiting machine with no usable enrollment at the client. If two requests or a cancellation race, neither token ownership nor the presence of a still-valid waiting row is stated as a condition for replay. The current pairing dialog calls revoke on close and the mock removes a still-waiting machine on that path. [Join rules](../plan.md:348) [Single-use acceptance](../../../../docs/specs/2026-11-25-go-rewrite-foundation-design.md:382) [Pairing dialog cleanup](../../../../src/frontend/src/screens/service.tsx:371) [Mock cancellation and approval](../../../../src/mock-server/src/engine.ts:195)

Reconcile the retry exception with C5 explicitly. A workable rule is to replay the exact committed request for the same valid secret and key before expiry and revocation, without a second registration. Refuse a different request, mismatched proof, unknown token, or a cancelled or expired record. Serialize consume, replay, cancellation and approval against the same durable enrollment, with token use, machine creation and its feed row committed together. Define cancellation after consumption but before approval, plus approval followed by dialog cleanup. Save the same key on the client before its first request and reuse it through retry. Specify that an outage before commit returns a retryable error and writes nothing.

### logic-r1 06 — MAJOR — C8 — Presence can be overwritten by the superseded stream

This is a confirmed design gap for the Contract, Server and Client teams. Risk is 72 (4 for stale displayed presence, 3 for an app-repairable state, and 6 for an ordinary connection replacement).

Stream B authenticates and replaces stream A. A's deferred close handler can run after B's first heartbeat and mark the machine offline. In the other direction, the server can mark a quiet stream offline after 30 seconds but leave it open, so a client waiting for a transport error can remain disconnected from work without attempting a new connection. [Replacement](../draft/link.proto:30) [Heartbeat and timeout](../draft/events.proto:60) [Required stream-close and timeout behavior](../../../../docs/specs/2026-11-25-go-rewrite-foundation-design.md:294) [Retry requirement](../../../../docs/specs/2026-11-25-go-rewrite-foundation-design.md:310)

Activate a replacement only after successful proof and give it a server-owned generation. Gate close, timeout, event, command result and connection token handling on that generation. Define presence from the current generation and the server's monotonic time since opening or receiving its last valid heartbeat. On a current-stream timeout, mark offline and close it. Give the client a bounded missing-ack timeout and require the next retry within 15 seconds. Define `HeartbeatAck` as a liveness response to a valid heartbeat on the active stream. It needs no sequence field if the client uses it as a last-contact signal rather than to match samples.

### logic-r1 07 — MAJOR — D16 — The existing Machines page offers the call only when the Go server will refuse it

The site only renders `Try to reconnect` for an offline machine. The mock also accepts only offline machines. The plan changes the operation to accept only a connected machine. On the Go server, every click offered by the current website is refused, and an online machine has no restart action. Decide explicitly how an older website learns about the behavioral change, using a revision bump when shipping the changed service without preserving the old caller behavior. Keep the additive sprint 0 generation and field change separate from that rollout.

### logic-r1 08 — MAJOR — C6 — The command the page tells the owner to run differs from the planned client

This is a confirmed handoff gap for the Website, Client and Stack teams. Risk is 300 (6 for a blocked enrollment, 5 for a coordinated fix, and 10 because the displayed command is the normal path).

The page advertises installation through the old package and renders `lgtm client join` with `--token`. The Go design uses `lgtm-client join` with two positional arguments. ### logic-r1 09 — MAJOR — R8 — The handshake specifies only half the deadlines and leaves invalid frames ambiguous

This is a confirmed design gap for the Contract, Client and Server teams. Risk is 120 (6 for a stuck connection or divergent retry, 5 for a fix by the teams, and 4 for a half-open or malformed exchange).

The server has a deadline for `Hello` and `Proof`, but the client has no corresponding bound for `Challenge` and `Welcome`. A peer that keeps the socket open and sends neither can prevent the required retry. An empty or unknown-case envelope before authentication also matches both the general ignore rule and the out-of-order refusal. The design's general web-session gate would reject both link calls if it were applied globally. [Phase and error rules](../plan.md:406) [Session exception in the draft](../draft/link.proto:18) [General session rule](../../../../docs/specs/2026-11-25-go-rewrite-foundation-design.md:230)

Write the legal frame for each phase and both peers' deadlines from stream open and the previous handshake frame. Validate nonempty canonical identifiers, exact key, nonce and signature lengths, revision 1, and a valid `Welcome` before application traffic. Refuse any wrong phase or empty handshake envelope. Define the rule for genuinely unknown fields after authentication separately from malformed known payloads. Scope the web-session gate to website procedures and define each retryable and terminal link failure, including the meaning of `aborted` for a superseded process. Preserve the retry interval for a connection that times out.

### logic-r1 10 — MINOR — C7 — The heartbeat cannot distinguish an idle machine from unavailable load

This is a confirmed design gap for the Contract and Client teams. Risk is 32 (4 for a temporarily incorrect load, 2 for limited display impact, and 4 for a sampling fault).

The client-local plan can return a load read error. The heartbeat's two plain scalars make an absent sample read as zero. An idle machine and a machine that could not measure its load therefore appear identical. Omitting the heartbeat altogether turns a sensor error into a presence failure. [Heartbeat fields](../draft/events.proto:60) [Client load reader](../../go-s1-client-local/plan.md:403) [Optional website load fields](../../../../src/contracts/proto/lgtm/v1/clients.proto:52)

Make the two heartbeat percentages optional at their existing draft field numbers, use absent for unavailable, and accept a heartbeat with absent load as evidence of presence. Define the valid range as 0 through 100 and set the website record's optional load fields accordingly. A genuine zero must remain distinguishable at the link and website record.

### logic-r1 11 — MINOR — R5 — The first watch response lacks a defined empty-feed position

This is a confirmed design gap for the Contract and Server teams. Risk is 36 (4 for inconsistent snapshot handling, 3 for recovery by resubscription, and 3 for the empty-feed case in a future position-aware reader).

The draft requires the snapshot to carry the highest visible position but gives no meaning to a present zero or an absent position. On a clean database one implementation can send `all` without a position, while another can send a position holding zero. A later reader that treats absence as an unsupported server cannot distinguish the first implementation from the mock. [Position comment](../draft/common.proto:25) [Snapshot ordering](../../../../docs/specs/2026-11-25-go-rewrite-foundation-design.md:161) [Mock watch handler](../../../../src/mock-server/src/engine.ts:164)

Require a present position on each Go server watch frame. Define 0 to mean no feed position is visible to the snapshot and reserve positive numbers for real changes. Leave absence meaningful for older or sample producers. Require increasing positions within one stream and permit gaps. Reconnect from a fresh snapshot, with no comparison across database replacements. Stop allocation before the storage counter exhausts its range.

## Answers to the attack questions

1. Feed positions are ordered by the database at commit and may have gaps. Events start at 1 and need a single durable sequence and mark per enrollment. Attempts count persisted sends for one command. Revisions count committed changes of machine state. Findings 01–04 and 11 give the missing gap, duplicate, tie, restart and exhaustion rules. Use the server's clock for token validity, report time only as metadata, and monotonic elapsed time for stream deadlines and presence. A wall clock jump must never reorder events or feed changes. Do not wrap any counter.
2. A durable transaction must bind token use to machine creation and bind an event to its acknowledgement mark. During a database outage withhold success and the mark, then retry after reconnect. Persist receipt intent before work and return a terminal interrupted result after a crash. Reuse the durable key and command identifiers on retries, and refuse expired or revoked joins. Findings 02, 03, 05, 06 and 09 give the missing crash, deadline, duplicate and clock rules.
3. The empty or contradictory cells are these. **Join:** unused and valid registers once, used with the same request and key is both success and refusal, used with other data is refused, and revoked after use needs a stated pending-machine policy. **Command:** a fresh valid command runs, an expired fresh command is refused, a running command at a newer attempt has no delivery rule, and completed replay past expiry is ambiguous. **Stream:** waiting can report and take state, approved can take work, removed with no stream has no terminal notification, and closing a replaced stream has no presence rule. **Envelope:** expected in-phase frames advance, an unknown frame during proof is both ignored and refused, and unknown reports after proof have no watermark policy.
4. Both new enumerations use an `UNSPECIFIED` zero. It must never grant approval or settle a command, and unrecognized enumeration integers need the same fail-closed handling. An empty approved name, machine or command identifier, proof, key or required token is invalid. A waiting name, a loopback certificate pin and a successful result's detail may be empty under their stated rules. Attempt and event number start at 1, and link revision 0 is refused. A zero replay mark means none, while a zero feed position and absent position need distinct meanings. Missing state, expiry, clock sample, report and load need the handling in findings 01–04 and 09–11. The local harness scan reports a usable version for every result it marks installed, so an absent version can represent its other results. ## Post-build checks

- **Join retry and cancellation.** Drop the reply after committing join, then retry with the same persisted key. The client receives the original identifier and one waiting row is visible. Competing keys and expired or revoked requests receive the agreed refusal. Race cancellation with approval and verify the final row and feed.
- **Replay through a crash.** Buffer reports 41 and 42, produce 43 during reconnect, and interrupt the inbox before commit and again after commit but before acknowledgement. Each committed report appears once in ascending order. The client deletes exactly the acknowledged prefix.
- **Stream handoff and presence.** Authenticate a replacement, then release an old close handler and old heartbeat callback. The replacement stays online. Stop the replacement's heartbeats without closing the transport and observe the offline transition and retry.
- **Receipt and expiry.** Reconnect while attempt 1 is running, then finish after the server offers attempt 2. The result closes attempt 2 once. Crash during restart and exercise replay and interruption. Advance or roll back the client clock and verify that a fresh expired command never starts.
- **Website journey.** Install the Go client using the instruction shown on the page, run the displayed enrollment command against the Go server, approve the resulting waiting machine, and restart it using the online machine's action. The restart survives a dropped result without running twice.
