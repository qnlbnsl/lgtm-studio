REVISE

The Machines page copies a command for a different executable and argument format than the Go installer provides, so the owner cannot use the displayed command to enroll a machine in wave 1.

## Findings

The review covers commit `3ef69e50` and the draft files beside the plan. The reference D denotes a design decision, R denotes a design rule, and C denotes a wave 1 check. Risk factors are severity, fallout, and probability, in that order.

### critic-r1 1 — MAJOR — C6 — The website copies an enrollment command for a different program

Design. Confirmed by reading. Responsible area is Stack and Client, with the orchestrator owning the website handoff. Risk is 180 (6 × 3 × 10) because normal enrollment through the page fails and the owner needs a corrected command.

The page tells the owner to install the old command and shows `lgtm client join <address> --token <code>`. Its address comes from a display label that strips the scheme. The Go brief ships `lgtm-client join <address> <token>`, and `JoinToken.address` already carries a complete address. The decisions log records the mismatch while the Server brief still promises that the page works without a screen change. `src/frontend/src/screens/service.tsx:401`, `src/frontend/src/screens/service.tsx:410`, `src/frontend/src/server/address.ts:45`, `.plans/plans/go-s3-client-link/plan.md:24`, `.plans/plans/go-s0-contract/draft/link.proto:50`, `.plans/plans/go-s0-contract/decisions.md:43`, `.plans/plans/go-s3-server-machines/plan.md:32`.

A person installs the Go client and pastes the page's command on that machine. It invokes the wrong program or returns a usage error, and no waiting record appears. Assign the rollout a prerequisite that aligns the installed program, the page's copy command, and the client parser. Use the token address as the dial authority and specify how an explicit address is normalized and checked against it. Make the wave 1 test paste the literal page command against the real stack and wait for the new record without a reload. The existing token field is sufficient.

### critic-r1 2 — MAJOR — D16 — The website offers restart only when the Go server will refuse it

Design. Confirmed by reading. Responsible area is the orchestrator's website handoff with Server and Client. Risk is 180 (6 × 3 × 10) because every attempt to use the existing menu action against the Go server follows the refused path.

The approved behavior restarts a connected client. The plan offers an offline refusal and freezes the same method name. The current page renders the method's action only when the machine is offline, and the sample server explicitly accepts only that state. `.plans/plans/go-s0-contract/plan.md:134`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:41`, `src/frontend/src/screens/service.tsx:351`, `src/mock-server/src/engine.ts:236`.

On the Go server, selecting the only visible action produces a toast and then `failed_precondition`. A connected machine offers no action. Keep `Restart` and the owner’s connected-client rule. Give the orchestrator an explicit prerequisite to update the page and sample behavior together before the Go cutover. Test an online action, one observed restart, continued presence after reconnect, and an offline refusal. Record the behavior change in the revision decision even though the schema change is additive.

### critic-r1 3 — MAJOR — C5 — The join retry describes the same used token as both accepted and refused

Design. Confirmed by reading. Responsible area is Contract with Server and Client. Risk is 72 (6 × 3 × 4) because one lost join reply can leave the owner with a waiting record and a client that needs manual enrollment repair.

The same-key retry is allowed through expiry, and the next sentence refuses a used token. The approved check refuses a used or expired token. The client brief says the client creates a key and keeps the server key, but gives no shared recovery input for a crash following a committed join. `.plans/plans/go-s0-contract/draft/link.proto:24`, `.plans/plans/go-s0-contract/plan.md:349`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:382`, `.plans/plans/go-s3-client-link/plan.md:43`.

If the server consumes the token and its reply is lost, it can refuse the client's retry as used. If the client starts the retry with a new key, even the replay rule refuses it. Define a first use and an exact replay of the same enrollment as distinct cases. Define which request fields are compared, and keep the first response and token consumption in the machine-creation transaction. Require a persisted pending key that survives a lost reply, and specify the user-visible result for an expired replay or a replay after removal. Amend C5 to test a refused second enrollment and a successful replay of the first. `token_id`, `token_secret`, and `machine_public_key` already identify the enrollment.

### critic-r1 4 — MAJOR — D17 — The pinned certificate identity has no agreed source at enrollment

Design. Confirmed by reading. Responsible area is Stack and Server with Contract. Risk is 108 (6 × 3 × 6) because enabling a public deployment can leave all new enrollments blocked until its configuration is corrected.

The design says the client pins the certificate and presents its own certificate. The draft pins the public key of the front end's certificate and uses only the signed challenges for the machine's identity. The planner guidance anticipates the second choice, and issue 1633 leaves ownership of the server pin open. The server or its token command issues both kinds of join token. `docs/specs/2026-11-25-go-rewrite-foundation-design.md:316`, `docs/issues.md:7524`, `.foundry/go-rewrite/common-planner.md:74`, `.plans/plans/go-s0-contract/draft/link.proto:54`, `.plans/plans/go-s3-stack-client/plan.md:41`.

A public deployment that holds its certificate in the web service can emit an empty pin or one computed from a different key. A client then rejects the token or the connection before `Join`. Assign the Stack and Server handoff a single configured public URL (Uniform Resource Locator) and a digest of the actual certificate key seen at that URL. Both token issuers must use the same source and refuse to mint a public token when the pin is unavailable. Record the change from certificate pin to certificate-key pin, the challenge-only client identity, and the behavior on a same-key renewal or key replacement in the approved design before freezing. The draft's `certificate_key_sha256` and `server_key_sha256` can carry the two pins.

### critic-r1 5 — MAJOR — C11 — The two cursors give different answers about a dropped event

Design and data integrity. Confirmed by reading. Responsible area is Contract with Server and Client. Risk is 96 (8 × 3 × 4) because the client can delete a retained event based on one acknowledgement and recover a different acknowledgement after a connection fault.

`EventAck.through` allows the server to report applied or dropped events, while `Welcome.last_event_number` only reports the highest applied event. The plan also says to ignore unknown kinds, and it does not specify when mutation of the machine record and advancement of the cursor become durable together. The local outbox persists an acknowledgement and then deletes its files. `.plans/plans/go-s0-contract/draft/events.proto:14`, `.plans/plans/go-s0-contract/draft/events.proto:28`, `.plans/plans/go-s0-contract/draft/link.proto:140`, `.plans/plans/go-s0-contract/plan.md:415`, `.plans/plans/go-s1-client-local/plan.md:587`.

If the server acknowledges terminally dropped event 11 after applying event 10, the client can delete 11 and subsequently receive 10 in `Welcome`. A crash after committing a report but before recording its number can also apply that report twice. Define both fields as one durable consumed-through watermark. Commit a valid event's record change and watermark in one transaction before acknowledgement. Specify which future reports may be deliberately consumed and which invalid reports close the stream without advancing the mark. Specify ascending send order for replay and newly appended events, and tie acknowledgements to the active stream. Keep the local outbox's policy of refusing a full append before assigning a number. State how the producer retries or coalesces that report, so an outbox refusal is neither a fabricated gap nor an acknowledged report. The existing two cursor fields suffice.

### critic-r1 6 — MAJOR — R6 — A finished receipt and its retry can disagree about the command outcome

Design. Confirmed by reading. Responsible area is Contract with Server and Client. Risk is 72 (6 × 3 × 4) because a connection fault can leave an otherwise successful command pending or give the owner a wrong outcome.

The expiry rule says to answer `EXPIRED` after the deadline. The replay rule says to send the recorded result, and the server ignores the old attempt. The local receipt plan applies expiry only to commands without receipts, retains the first attempt in a running receipt, and recovers a half-finished receipt as `interrupted`. `.plans/plans/go-s0-contract/draft/commands.proto:18`, `.plans/plans/go-s0-contract/draft/commands.proto:34`, `.plans/plans/go-s0-contract/draft/commands.proto:46`, `.plans/plans/go-s1-client-local/plan.md:642`, `.plans/plans/go-s1-client-local/plan.md:648`.

A scan can finish after the stream closes and after attempt 2 arrives. An implementation can report attempt 1 and be ignored, or return expiry in place of the recorded result. Specify that expiry gates the first start and that an existing terminal result takes precedence thereafter. While a command is running, keep its latest valid delivery attempt and use it when sending the result. Require the server to accept terminal results only for its current attempt, and define when it stops resending and when the client can prune the receipt. Map an interrupted receipt to `FAILED` with a sentence that says the outcome is unknown, or add `COMMAND_OUTCOME_INTERRUPTED` if the server needs to distinguish it programmatically. Require a durable scan report before success and specify how `Restart` records its result and exits under supervision. The existing identifier and attempt fields can support replay.

### critic-r1 7 — MAJOR — C8 — Presence and removal leave the client without a terminal rule

Design. Confirmed by reading. Responsible area is Contract with Server and Client. Risk is 72 (4 × 3 × 6) because routine disconnections and removals can leave stale status or a process that keeps reconnecting.

The draft sends an empty `HeartbeatAck` and gives the server a 30-second limit without specifying a client-side read limit. It also says the server forgets the machine's key after sending `REMOVED`. The design forgets the key on removal, and the client brief requires a clean stop when removed. `.plans/plans/go-s0-contract/draft/events.proto:60`, `.plans/plans/go-s0-contract/draft/commands.proto:74`, `.plans/plans/go-s0-contract/draft/link.proto:30`, `.plans/plans/go-s0-contract/draft/link.proto:133`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:254`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:296`, `.plans/plans/go-s3-client-link/plan.md:45`.

For an offline machine, the server cannot send `REMOVED`. On the next dial it returns `unauthenticated`, which a retry loop can treat as a temporary outage. An old stream's close can also overwrite the online state of its replacement. Define the terminal enrollment refusal after a response from the pinned transport, with one sentence telling the owner to re-enroll. Preserve the key and local state on a transport failure, and give link-revision refusal its own terminal repair message. Close a live removed stream and invalidate its active state even if the final command is lost. Allow only the active verified stream to write presence or process a heartbeat. Set a client-side read deadline and a reconnect ceiling of 15 seconds for temporary failures. No additional heartbeat or presence field is needed. If precise removal diagnostics are required, use a typed error detail with a documented trust rule.
