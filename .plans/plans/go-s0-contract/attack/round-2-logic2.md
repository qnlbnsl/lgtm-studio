# Round 2, seat logic2, lens logic: the plan `go-s0-contract`

Task identifier: review-go-s0-contract-r2-logic2. Nonce: 680874.

**Top finding:** `Hello.acked_event_number` is read from an unsigned message, the plan does not say that the raise waits for the verified proof, and one forged or altered claim makes the server skip every later report of a machine for ever (logic2-r2 1).

## Findings

### logic2-r2 1. BLOCKER (Security, integrity). The raise of the event mark trusts an unsigned field, and says nothing about when it happens

- **Tied to:** D39 (decision 39), and the item 6 rule "Event marks".
- **Evidence:** `.plans/plans/go-s0-contract/plan.md:535` says that a server whose mark is lower "raises its mark to that number before it sends `Welcome`". `draft/link.proto:198-202` declares the field in `Hello`. The proof texts of item 6 and the table of public names hold a label, the machine id and the two nonces, so the claim is outside both signatures. Neither the plan nor the decision says that the raise waits for a verified `Proof`, that it belongs only to the stream that becomes current, or what bounds the claim. Point 2 for the owner (`plan.md:124-130`) says that nothing protects the messages on the hop behind the web server, and `plan.md:62` says a machine proves itself only by signing a challenge.
- **Failure scenario:** The machine with the id M has the server mark 40. A process on the hop behind the web server, or a bug that runs the raise before the proof, sends `Hello{machine_id: M, acked_event_number: 4611686018427387904}`. The proof of the real machine still verifies, because the claim is not in its signed text. The server commits the mark 4611686018427387904. Every later event of M, numbered 41 and above, is "at or below the mark", so it is a copy: the server sends its mark again, the machine deletes the events as acknowledged, and nothing is ever applied. The machine looks online with a healthy stream, and its `Facts` and `HarnessesFound` never reach the server again. The plan's sentence "A machine that claims a higher number can only skip its own reports" holds only for the real machine, and the plan does not make the claim the real machine's.
- **Prescribed fix:**
  1. Add the claim to the machine's signed text: the machine text becomes the label, a zero byte, the length byte, the machine id, the machine nonce, the server nonce and the claim as 8 bytes, big-endian. Change `testdata/link-proof.json` and the mutation of item 6 to match, and add a test mutation that moves the claim and must make `TestProofExamplesHoldTogether` fail.
  2. Write in the rules of item 6 that the raise happens only after `Proof` verified, in the same transaction that makes the stream current, and only when the claim is higher than the mark. A claim at or below the mark changes nothing.
  3. Write that the server logs each raise with the old and the new mark, so a skip is visible.

### logic2-r2 2. MAJOR (Design). The plan and the client-local plan contradict each other about a server mark above the machine's numbers, and the field they depend on is missing

- **Tied to:** D39, the item 6 rule "Event marks" and the first agreement of the table of agreements.
- **Evidence:** `plan.md:534` says that when the mark is higher than the machine's highest number the machine forgets its kept events and numbers the next one higher, and that "The client-local plan's `Outbox.Ack` beyond `Next()` already does this". The client-local plan changed on 2026-11-26 at 07:35, eleven minutes before this plan: `.plans/plans/go-s1-client-local/plan.md:686` (the public names) and the behaviour of `Ack` below it make `Ack` refuse a number at or above `Next()` with `ErrAckAhead`, and `plan.md:870` makes `ErrServerAhead` and `ErrServerBehind` close the connection and retry later. That plan keeps the server's mark for each epoch of the outbox (`go-s1-client-local/plan.md:631`, decision 41), and asks the Contract team for an epoch field. A search of `go-s0-contract/` for `epoch` finds nothing: `Hello` has no such field, and the agreements table has no such row.
- **Failure scenario A (livelock):** The server holds the mark 40 for M. The machine's state folder was restored from a copy, so its outbox is new, with a new epoch, `Next()` 1 and no event. `Welcome.last_event_number` is 40. The contract says "forget and number from 41"; the client-local plan says `Reconcile(40)` returns `ErrServerAhead`, closes the connection and retries in 15 seconds. The retry meets the same mark. The machine never sends an event, and stays "joining" for ever.
  **Failure scenario B (loss):** If the Client Link follows the contract and sends the new outbox's events 1 and 2 under the old mark 40, the server treats them as copies and confirms 40. The machine deletes its two new events, which were never applied.
- **Prescribed fix:** Adopt the epoch, because the client-local plan already builds on it and decision 41 there records it as an assumption. Add `string event_epoch = 5;` to `Hello` (32 lowercase hexadecimal characters, a value rule, and inside the signed machine text with the claim of logic2-r2 1). State that the server keeps one mark for each pair of machine id and epoch, that a new epoch starts at 0, that `Welcome.last_event_number` and `EventAck.through` are the mark of that epoch, and that `Hello.acked_event_number` raises only the mark of the same epoch. Delete the sentence at `plan.md:534` and the clause about `Outbox.Ack`. Add the row "The server keeps its mark for each epoch" to the agreements table: written by Server Link with the store of `go-s1-server-store`, read by Client Link and by `go-s1-client-local`. Put `event_epoch` into the table of public names, `describe` golden `open.txt` and `TestJoinMatchesItsDescription`'s sibling for `Hello`.

### logic2-r2 3. MAJOR (Bug). A machine that is approved on a stream it already has never sends its `Facts` and `HarnessesFound`

- **Tied to:** the item 4 rules of events and facts, and point 3 for the owner.
- **Evidence:** `plan.md:351` sends the two reports "After every `Welcome` in which it may send events". `plan.md:356` shows an approved machine as joining "until the server holds a `Facts` and a `HarnessesFound` sent on its current stream". The owner approves through `ApproveClient`, which the server delivers as `SetState` on the open stream, not as a new `Welcome` (`plan.md:536` and the standing rules at `plan.md:338-340`). The design says that a waiting machine "can do nothing else" (`docs/specs/2026-11-25-go-rewrite-foundation-design.md:251`), which is option A of point 3.
- **Failure scenario:** The owner chooses option A or B of point 3. The machine opens a stream, gets `Welcome` with the state waiting, and sends no event. The owner approves it. The server sends `SetState{approval: APPROVED, revision: 2}` on that same stream. The machine applies it, and no `Welcome` follows, so the rule of `plan.md:351` never fires again. The machine stays "joining" until the stream breaks. With option C the machine sent the reports while it waited, so the draft hides the hole; the first change of point 3 opens it.
- **Prescribed fix:** Replace the sentence at `plan.md:351` and its copy in `draft/events.proto` by: "The machine sends its current `Facts` and `HarnessesFound` as new events when it becomes approved on a stream: after a `Welcome` whose state is approved, and when it applies a `SetState` that makes it approved." Add one row to the post-build check 7: approve a machine on a stream that opened while it was waiting and require the state online within 30 seconds without a reconnection.

### logic2-r2 4. MAJOR (Bug). After a restore, a machine ignores the server's standing for ever, because `Welcome.state` has no way to go back

- **Tied to:** the item 4 rules of the standing, decision 38 (revisions), and D39.
- **Evidence:** `plan.md:338` says that a machine applies a `MachineState` only when its `revision` is higher than the last one it applied, and that "the same revision with other content is a fault of the server, and the machine keeps what it holds". `plan.md:339` says that the machine applies `Welcome.state` before any command. The plan repairs a restored server for the event mark through `acked_event_number`, and has no repair for the revision.
- **Failure scenario:** The machine holds `revision 7, approved, name "build"`. The owner restores the server's database to a copy in which this machine is at `revision 5`, approved, name "old". The next `Welcome.state` has revision 5: not higher, so it is ignored. The owner renames the machine twice: revision 6 and revision 7 with the name "ci". The second has the same revision with other content: a "fault of the server", so the machine keeps "build". It also drops a restored standing of `waiting` at revision 1, and keeps acting as approved. The machine and the Machines page disagree until the server passes 7, and nothing in the plan repairs it or reports it to the owner.
- **Prescribed fix:** Split the rule. A `SetState` message inside a stream keeps the rule "applied only when higher". The `state` of a `Welcome`, which follows a verified proof, is always applied, and the machine takes its revision as the new last applied revision, even when it is lower. Write this in the rules of the standing, in the comment of `Welcome.state`, and as a case of `TestCommandsMatchItsDescription`'s sibling for `Welcome`. Add to post-build check 3 a rename after the restore and require the machine to show the new name.

### logic2-r2 5. MAJOR (Bug). A server restored from an older copy makes a healthy machine stop for good

- **Tied to:** D42 (decision 42), D44, and post-build check 3.
- **Evidence:** `plan.md:511` and `plan.md:531` end a stream with `unauthenticated` for "unknown or removed", and `plan.md:518` and `draft/link.proto:42-43` make the client stop on it after a verified `Challenge`. The plan says it needs no record of removed ids, so the server cannot tell a removal from a row that the restore never had. Post-build check 3 restores the database to "an older copy" and expects only the event rules.
- **Failure scenario:** A machine joined and was approved on Tuesday. The owner restores a copy from Monday. The server has no row for the machine, so it sends a verified `Challenge`, then `unauthenticated`. The client prints "The server does not know this machine. Join it again.", and `lgtm-client run` stops. The service is unattended, so the machine is offline until a person notices. A copy that holds the machine, restored after a removal, does the opposite: it brings a removed machine back with its key.
- **Prescribed fix:** Keep the message and drop the permanent stop. After a verified `Challenge` and `unauthenticated`, the client keeps its key and files, shows the sentence on its status, and retries every 5 minutes instead of every 15 seconds. Change the row of the table of codes in `draft/link.proto` and decision 44 to "Retry every 5 minutes, and show: ...". The rejoin with a new token still works, and a restored server heals without a person. Add to post-build check 3 a copy that predates the join and require the machine online within 6 minutes of the restore.

### logic2-r2 6. MINOR (Bug, timing). Two streams of one machine that verify together have no ordering, and a retry of `aborted` can ping-pong

- **Tied to:** the item 6 rule "The current stream" and D44.
- **Evidence:** `plan.md:524` makes a stream current "only after its `Proof` verified and the server read the machine's record again". It names no lock, no order and no generation. `plan.md:526` and `draft/link.proto:93` end "the older stream" with `aborted`, and `draft/link.proto:45` makes the client retry in 15 seconds.
- **Failure scenario:** Streams A and B of one machine finish their proof in the same millisecond. Each reads the record, each decides it is the newer, and each ends the other with `aborted`. Both clients retry within 15 seconds, and a second process with the same key makes the loop continue for ever. A stale stream can also pass the check "am I current" and then write "offline" after B became current, so B shows offline until its next heartbeat.
- **Prescribed fix:** Write that the server keeps one counter of streams for each machine, taken under one in-memory lock for the machine id. The stream that takes the higher counter is the newer. Every write of presence, an event or a result is one conditional write that names the stream's counter (`... WHERE stream = $n`), so a stale stream's write changes no row. Write that a client that gets `aborted` twice within one minute waits 60 seconds before the next try.

### logic2-r2 7. MINOR (Design). The agreements do not say whose clock feeds the client-local receipts

- **Tied to:** the item 4 rule about the server's clock and the third agreement.
- **Evidence:** `plan.md:331` makes the machine count the server's time as `Welcome.server_time` plus the monotonic time since `Proof`. `go-s1-client-local/plan.md:153-155` and `:765` compare a command's expiry with the machine's own clock and keep the highest time in `receipts/clock`. Row 3 of the agreements table (`plan.md:710`) names the receipts but not this feed.
- **Failure scenario:** The Client Link builds the receipts with their default clock. A machine whose clock is five minutes behind runs a command that the server counted as expired two minutes ago, which post-build check 6 says must not happen. If the Client Link instead feeds the server count without saying so, the file `receipts/clock` records server times, and a server whose clock was wrong by a day for an hour leaves a high-water mark that makes every new command "expired" for a day.
- **Prescribed fix:** Add to the third agreement: "The Client Link gives the receipts a clock that returns the server count of `Welcome.server_time` plus the monotonic time, and does not use the machine's wall clock for expiry. A `Welcome` that arrives with a `server_time` more than 1 hour below the stored high-water mark makes the client log one sentence and reset `receipts/clock` to the new count." Name `go-s1-client-local` as a reader of this row.

### logic2-r2 8. MINOR (Design). `TestEveryLinkRuleIsWritten` passes on an empty comment

- **Tied to:** the patch for logic2-r1 12, item 6 test list.
- **Evidence:** `plan.md:559` requires that the nearest line above each declaration "starts with `//`". A line holding only `//` starts with `//`.
- **Failure scenario:** A builder adds `//` above `acked_event_number`, `COMMAND_OUTCOME_INTERRUPTED` and `Restart restart = 12;`. The test, and its mutation 3, pass or are satisfied by this edit, while the rules of the comments disappear from the file.
- **Prescribed fix:** Require each comment block above a declaration to hold at least 5 words of letters, and require the comments of the declarations in the table of public names (`acked_event_number`, `INTERRUPTED`, `optional` loads, `event_epoch`) to contain the words of their rule (for example `acked_event_number` must contain `raise` and `signed`). Add the mutation "replace the comment above `COMMAND_OUTCOME_INTERRUPTED` by `//`" to item 6.

## Answers to the attack questions

### The questions of the task

1. **Does each patch remove its failure, and does it break something else?** The patches for events (acknowledge after commit, mark plus one, a gap ends the stream), for commands (`INTERRUPTED`, one expiry, the clock count, `Restart` writes its receipt first), for the heartbeat load, the value rules, `Join` as one transaction and `CreateClientToken` never replayed do remove the failures they answer. I checked the clock count: the machine's count is ahead of the server's by the delay of the proof, never behind, so a machine never starts a command the server counts as expired (a late start is a miss, not a wrong run). The event patch breaks the client-local plan's refusal of a mark above its numbers (logic2-r2 2). The removal patch breaks the restore case (logic2-r2 5). The approval path breaks the facts rule (logic2-r2 3). The standing patch breaks after a restore (logic2-r2 4).
2. **The three `UNREVIEWED MECHANISM` places.** Decision 39 (`acked_event_number`): attacked as logic2-r2 1 and 2; the mechanism is needed (without it a restored server causes a gap that no one repairs) but is unsigned, unbounded in time, and incomplete without an epoch. Decision 42 (the signed `Challenge` for every well-formed `Hello`): the signed challenge does make the refusal trustworthy as to the sender; it does not make it correct as to cause (logic2-r2 5). A cheap wrong implementation that passes every listed test: answer `unauthenticated` for every error of the database lookup, which `unavailable` guards only by a sentence in the comment and by no named test. Decision 44 (the code table): the stop on `failed_precondition` is correct, the stop on `unauthenticated` is wrong for restores (logic2-r2 5), and `aborted` has no bound (logic2-r2 6). Retry of `Open invalid_argument` and `permission_denied` is unbounded, but costs one attempt in 15 seconds and a log line, so I did not file it.
3. **Rejected findings.** The register has 0 rejected findings, so there is no rejection to check. I probed the outcomes "fixed another way" and "for the owner" instead: point 3 (what a waiting machine sends) interacts with the facts rule (logic2-r2 3), and point 2 (the hop behind the web server) bears on the unsigned claim (logic2-r2 1). Point 1 and point 4 have no logic interaction with the patches.
4. **Names that others build against.** `Hello.acked_event_number`: the table at `plan.md:184` names a writer (Client Link) and a reader (Server Link) but not `go-s1-client-local`, whose outbox must persist its mark when it holds no event (it does: `outbox/acked`), and it lacks the epoch and the signed text (logic2-r2 1 and 2). `COMMAND_OUTCOME_INTERRUPTED`: writer and readers complete. The optional load fields: readers complete (server and website through Server Machines). The code table: the Stack Web team passes codes through unchanged, and it is not named as a reader; the agreements table row for the link's paths covers it only for `Join` without a cookie, a minor omission that I do not file. `CreateClientTokenResponse.token` and `ReconnectClient`: complete. The clock count has no named reader in the client-local plan (logic2-r2 7).
5. **Truth tables of rules that interact.** (a) Presence against readiness: `Welcome` marks online (`plan.md:526`), an approved machine "joins" until both reports arrive (`plan.md:356`), and a waiting machine may send events (draft). Cells: waiting and online and no report: shows "waiting"; approved and online and no report: "joining"; approved after a `SetState` with no `Welcome`: empty cell, which logic2-r2 3 fills. (b) Receipt state against expiry and attempt: no receipt and count before expiry runs; no receipt and count at or after expiry answers expired; a final receipt replays under the new attempt in both cases; a running receipt answers under the newest attempt; a receipt found "started" after a restart is `INTERRUPTED`. No empty cell, and it agrees with `TestReplayTruthTable` in the client-local plan. (c) Mark against claim against machine numbers: claim above the server's mark with epoch unknown is the empty cell of logic2-r2 2, and the claim from an unsigned `Hello` is the hole of logic2-r2 1. (d) Revision against `Welcome` after a restore: logic2-r2 4. (e) `Welcome`'s mark and a gap: a machine with kept events above mark plus one cannot arise after the raise, so `out_of_range` is only a fault signal; I found no livelock beyond logic2-r2 2.
6. **A blocker or major of round 1 that is still open although marked fixed.** The `Hello` claim of round 1's threat finding 3 is marked fixed and is open in the sense of logic2-r2 1. The logic2-r1 findings 1 to 12 were fixed as written; my round-1 finding 2 (counter restart) is fixed by the machine's rule "never reuses a number", which the client-local plan now contradicts for the case of a lost outbox (logic2-r2 2). Nothing else is open.
7. **Lens questions touched by the patches.** See the next list.

### The questions of the lens

1. **Sequences and ties.** Event numbers: mark plus one, copies, gaps, restart: answered, with the exception of the epoch (logic2-r2 2). Attempts: the server never wraps; `uint32` was the mutation target. Revisions: logic2-r2 4. Streams: logic2-r2 6.
2. **Failures.** Crash between commit and acknowledgement: the machine sends again, the server answers with its mark: holds. Database down: `unavailable`, never `unauthenticated`: holds by a sentence only. Restore: logic2-r2 1, 4 and 5. Expired token and clocks: holds, see question 1 above.
3. **Truth tables.** Built in answer 5 above. Cells named: the approval without `Welcome`, the claim above the mark, the revision below the last applied.
4. **Zero values.** `acked_event_number` 0 means "nothing acknowledged" and never lowers a mark: holds. `APPROVAL_UNSPECIFIED` reads as waiting: holds. `COMMAND_OUTCOME_UNSPECIFIED` reads as failed on the server: holds. A missing `Welcome.state` reads as waiting, which logic2-r2 4 uses for the restored case.
5. **Two actors on one row.** Two streams of one machine: logic2-r2 6. The removal against a live stream: the key's deletion commits before the stream ends, so a verified proof afterwards cannot succeed; a stream that passed the proof just before the commit stays current until the server ends it, which the removal does in the same step: holds.
6. **Risky mutations.** Item 6's mutations (swap the nonces; drop `last_event_number`; delete the comment above `Restart`) fail their tests. A wrong change that no listed test catches: moving the claim into a different place in `Hello`, or reading it before the proof, because the claim is outside the signed text and no test orders the raise (logic2-r2 1); and an empty `//` above a declaration (logic2-r2 8).
7. **Cheapest wrong implementation.** A server that raises on the claim before the proof passes every listed test. A client that follows the contract's "forget and number from the mark" instead of the client-local plan passes the contract's tests (logic2-r2 2). A server that answers `unauthenticated` for a database error passes every listed test.
8. **A different shape.** One counter for each pair of machine and epoch, written under one lock, and a claim that the machine signs, make logic2-r2 1, 2 and 6 impossible. A `Welcome` that always carries the truth of the server and is always applied makes logic2-r2 4 impossible.

## Post-build checks

These add to the nine checks of the plan, and the orchestrator's combined link test runs them.

1. **Forged claim.** Open a stream with the machine's id, a valid proof, and a claim of 2^62 in an altered `Hello`. Expect the proof to fail, the mark of the machine to stay, and the next event to be applied (logic2-r2 1).
2. **Lost outbox.** Delete the machine's outbox folder while the server holds the mark 40. Expect a new epoch, the first events applied from 1, and the state online within 30 seconds (logic2-r2 2).
3. **Approval on a stream that exists.** With a waiting machine connected, approve it, and expect online with facts within 30 seconds and no reconnection (logic2-r2 3).
4. **Restore, then rename.** Restore a copy at a lower revision, rename the machine, and expect the machine to show the new name (logic2-r2 4).
5. **Restore of a copy that predates the join.** Expect the machine to retry and to come online within 6 minutes after a new join token or a restore of the newer copy, and no permanent stop (logic2-r2 5).
6. **Two processes with one key.** Run two clients with one key for 2 minutes. Expect no more than one stream replacement per minute (logic2-r2 6).
