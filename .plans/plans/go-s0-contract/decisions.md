| 12 | How are the two Go generators pinned? | With `tool` lines in `go.mod`: `google.golang.org/protobuf/cmd/protoc-gen-go` at v1.36.12 and `connectrpc.com/connect/cmd/protoc-gen-connect-go` at v1.21.1. `buf.gen.yaml` runs them through `go tool`. | The brief asks for pins in `go.mod`. | 13 | Which Go line does `go.mod` carry? | `go 1.26.0`. | The installed Go 1.23.3 switched itself to the cached Go 1.26.0 on that line. A line without a patch number names a release that the download service does not have. | closed | 2026-11-26 |
| 14 | What does the join token carry, and how is it written? | A message `JoinToken` with the token id, a 32-byte secret, the address to dial, the hash SHA-256 (Secure Hash Algorithm, 256 bits) of the server's Ed25519 public key, and the hash SHA-256 of the key of the certificate at an address that uses the Hypertext Transfer Protocol Secure (HTTPS). Its text is `lgtm1_` and the message's binary encoding in unpadded base64url. | The design puts the server key's fingerprint and the certificate's fingerprint in the token. The orchestrator's reading of issue 1633 adds the address. One message that both programs generate leaves no hand-written parser to disagree. The assumption is that a token of about 200 characters is short enough to copy. | unanswered | 2026-11-26 |
| 15 | Which fingerprint of the certificate does the token carry? | The hash SHA-256 of the certificate's SubjectPublicKeyInfo, which is its public key. | A renewed certificate that keeps its key still matches, so a renewal does not cut off every machine. The design says "the fingerprint of the server's certificate" and does not name the bytes. The assumption is that pinning the key meets the design's intent that the client trusts that certificate and no other. | unanswered | 2026-11-26 |
| 16 | Does the link depend on a certificate that the machine presents? | No. The signed challenge on every stream proves the machine. Nothing in the contract reads a certificate of the machine. | Issue 1633 notes that encryption ends at the web server, so a certificate of the machine never reaches the server. This departs from the design's sentence that the machine presents a self-signed certificate. The result file reports it. | unanswered | 2026-11-26 |
| 17 | Is a heartbeat a numbered event? | No. A heartbeat travels as its own kind of message, is never kept on disk, and the server answers each one with `HeartbeatAck`. Facts and harnesses found are numbered events. | A heartbeat kept while the server is down would report an old load when it arrives. The answer makes the stream carry data in both directions, which issue 1633 asks of the web server in front. | unanswered | 2026-11-26 |
| 18 | Is the result of a command an event? | No. A result is its own kind of message. A machine that receives a command it already ran sends the recorded outcome with the attempt number of the copy it just received. | The receipt already makes a result survive a lost stream. Sending the recorded result with its old attempt number would be ignored by the server forever, because the design ignores a result for an older attempt. | unanswered | 2026-11-26 |
| 19 | How does a machine order two changes of its standing? | `MachineState` carries a `revision` that grows with each change. A machine ignores a state with a lower revision than one it applied. `Welcome` carries the current state too. | Commands are sent again after a reconnection. Without a revision, an old approval sent again after a rename would put the old name back. | unanswered | 2026-11-26 |
| 20 | How does the contract carry `ReconnectClient`, which restarts a connected client? | A third command, `Restart`. The comment on `ClientService.ReconnectClient` changes to say that it restarts a connected client, and that a client that is not connected is refused with `failed_precondition`. | The owner decided on 2026-11-25 that the call restarts a client that is connected. The design's table of what travels in wave 1 lists no such command. The brief of `go-s3-client-link` already plans a restart command. Only a comment changes in `clients.proto`, so the revision stays at 1. | unanswered | 2026-11-26 |
| 21 | What may a machine that waits for approval do on the stream? | It proves itself, sends heartbeats and events, and receives `Welcome` and `SetState`. The server sends it no other command. | The website already shows the operating system, cores and memory of a waiting machine, which arrive as facts. The design says a waiting machine can connect and can do nothing else; the assumption is that sending its own facts is not work. | unanswered | 2026-11-26 |
| 22 | May event numbers have gaps? | Yes. The server applies an event only when its number is higher than the last one it applied, and it drops any other. A gap means the machine dropped events it could not keep. | The design keeps events within a limit, so a full buffer can lose events. The brief of `go-s1-client-local` leaves open whether the oldest or the newest are lost. This rule holds for both answers. | unanswered | 2026-11-26 |
| 23 | Can `Join` be sent twice? | Yes. The same token with the same machine key returns the same reply until the token expires. The same token with another key is refused. | Rule 4 of the design's database layer says every request that changes something can be sent twice and happens once. A client whose reply was lost would otherwise be locked out by its own used token. | unanswered | 2026-11-26 |
| 24 | Which bytes does each end sign? | A label, one zero byte, one byte with the length of the machine id, the machine id, the machine's 32-byte nonce and the server's 32-byte nonce. The labels are `lgtm-link-v1 server` and `lgtm-link-v1 machine`. Examples with fixed seeds live in `src/contracts/testdata/link-proof.json`. | The design gives the steps and not the bytes. Two labels keep a signature of one role from serving as the other's. Both nonces in both texts tie each signature to this one stream. Shared examples let the server and the client test against the same bytes without sharing code. | unanswered | 2026-11-26 |
| 25 | Which error codes does the link use? | `permission_denied` for every refused join token; `unauthenticated` for an unknown machine or a bad signature; `failed_precondition` for a link revision the server does not speak; `invalid_argument` for a message out of order; `deadline_exceeded` when `Hello` or `Proof` is late by 10 seconds; `aborted` for a stream that a newer one replaced. | Rule 8 of the design says an error is a Connect code with one sentence. The client team needs to know which codes mean stop and which mean try again. | unanswered | 2026-11-26 |
| 26 | How do the two ends agree on a revision of the link? | `Hello` and `Welcome` carry `link_revision`. Each program names the revision it speaks, which is 1, as the website and the mock server name the contract revision today. | A later wave may break the link. A machine with an older client then gets a clear refusal. | unanswered | 2026-11-26 |
| 27 | How does the contract keep room for wave 2? | Wave 2 adds new cases to the oneofs `OpenRequest.kind`, `OpenResponse.kind`, `Command.action` and `Event.report`, with numbers not used yet, and new calls beside the stream that present the header `Lgtm-Link-Token`. A machine answers a command it does not know with `COMMAND_OUTCOME_UNSUPPORTED`. A receiver ignores a message of a kind it does not know. No number is reserved. | The task file asks for room for byte streams and for the calls an agent makes through its machine, without planning them. A reserved number could never be used, so reserving would take room away. The blueprint names `agent_calls.proto` as the wave-2 file. | unanswered | 2026-11-26 |
| 28 | How long is the connection token good for? | Only while the stream that issued it is open. | The design calls it short-lived and gives no time. A token tied to its stream needs no renewal. A time limit can be added later as a new field. | unanswered | 2026-11-26 |

| 38 | How do events stay in order, and what does an acknowledgement cover? | The server applies only the number one above its mark, commits the effect and the mark together, and acknowledges after the commit. This supersedes row 22. | Review round 1 showed that gaps and an acknowledgement of dropped events let the client delete an event the server never applied (architect-r1 01, logic-r1 01, threat-r1 3, critic-r1 5). | 39 | What happens when the server's mark is behind the machine's, after a restore of the database? | `Hello.acked_event_number`, field 4, carries the machine's mark, and the server raises its own mark to it before `Welcome`. | Without it, the machine's next event is a gap forever (threat-r1 3). A machine that claims too high a number can only skip its own reports. No reviewer proposed the field, so round 2 attacks it. | unanswered | 2026-11-26 |
| 40 | How do expiry, attempts and outcomes work together? | One expiry per command, decided by the server's clock, which the machine counts from `Welcome.server_time` plus its monotonic time since `Proof`. A recorded result is sent also after the expiry. The server accepts only its current attempt on the current stream, and records `COMMAND_OUTCOME_EXPIRED` itself 24 hours after the expiry. `COMMAND_OUTCOME_INTERRUPTED = 5` is added. Every outcome except `UNSPECIFIED` is final. This amends row 18. | Six reviewers found gaps in the life of a command (architect-r1 07, critic-r1 6, logic-r1 02 and 03, logic2-r1 5, threat-r1 9). The client-local receipts already keep each receipt 24 hours and recover a half-finished one as `interrupted`. | closed | 2026-11-26 |
| 41 | When does a `Restart` record its result? | The machine writes its receipt with `COMMAND_OUTCOME_DONE` to disk, sends the result, and then ends. The outcome means that the restart was accepted. This amends row 20. | Without the receipt on disk first, a restart can repeat forever (logic2-r1 3, threat-r1 8). | closed | 2026-11-26 |
| 42 | How does removal work when the machine cannot be told? | The commit of the removal deletes the key, and the server then ends the current stream. `SetState` with `APPROVAL_REMOVED` is a courtesy. The server answers every well-formed `Hello` with a signed `Challenge`, so a client that then gets `unauthenticated` knows the refusal came from its server, and stops. | Removal must not depend on delivering a message (architect-r1 02, threat-r1 1, logic-r1 04, critic-r1 7). The verified challenge makes the refusal trustworthy without a record of removed ids. Round 2 attacks this mechanism. | unanswered | 2026-11-26 |
| 43 | Which stream may change a machine's record? | Only the current stream, which a stream becomes after its proof and a fresh read of the record. A stream that is no longer current changes nothing, also when it ends. Only `Welcome` marks a machine online. | A late end of a replaced stream could mark a connected machine offline (logic2-r1 4, logic-r1 06, architect-r1 09). | closed | 2026-11-26 |
| 44 | What does a client do with each code, and when does it give up on a quiet peer? | The table in the `LinkService` comment. It stops on `permission_denied` from `Join`, on `failed_precondition` from `Open`, and on `unauthenticated` after a verified `Challenge`. It retries everything else within 15 seconds, `aborted` included. It gives `Challenge` and `Welcome` 10 seconds each, and closes a stream that is silent for 30 seconds. A server that cannot read its database answers `unavailable`. This amends row 25. | The design requires a retry at least every 15 seconds. A client must not stop on a temporary failure, and must stop on a removal (logic2-r1 6, logic-r1 09, critic-r1 7). Retrying `aborted` after the normal wait keeps two processes with one key from replacing each other without pause. | closed | 2026-11-26 |
| 45 | Which values must every message keep? | Canonical UUIDs, exact lengths of nonces, keys, signatures and hashes, link revision 1, counters from 1, present timestamps and state, and limits on strings. A breach is `invalid_argument`. An unspecified or unknown approval counts as waiting. An unspecified or unknown outcome is stored as failed. | Two builders would otherwise answer malformed input differently (logic-r1 09, critic-r1 10, logic2-r1 10, threat-r1 11). | closed | 2026-11-26 |
| 46 | When does `Join` replay its reply? | One transaction uses up the token, binds the key and creates the machine. A request with the same token, a verified secret and the same key gets the first reply while the token is unexpired and its machine exists. Every other request gets `permission_denied`, checked in a fixed order. Revoking a used token removes a machine that still waits. This amends row 23. | Five reviewers found that the draft both replayed and refused a used token (architect-r1 06, critic-r1 3, logic-r1 05, threat-r1 6, logic2-r1 8). | closed | 2026-11-26 |
| 47 | Which address does a client dial, and where does the certificate pin come from? | The token's address only. A different address on the command line is refused. One configured address and pin feed every token, and the server makes no `https` token without a pin. The client checks the pin before it sends the secret, and on every stream. | Two addresses and two token makers could disagree (architect-r1 04 and 05, critic-r1 1 and 4, logic-r1 08, logic2-r1 7, threat-r1 10). Whether a pin of the key meets the design's word "certificate" is part of point 2 for the owner. | closed | 2026-11-26 |
| 48 | Is the load of a heartbeat optional? | Yes. Both percentages are `optional`, from 0 to 100, and absent means not measured. This amends row 17. | An idle machine and a machine that could not measure its load looked the same (logic-r1 10). | closed | 2026-11-26 |
| 49 | How does the server fill the fields of a machine that the website reads? | `hosts_server` from a token of the server's own command, `address` from the connection for showing only, `memory_gigabytes` as bytes over 2^30 rounded, `harnesses_scanned` from the first `HarnessesFound`, and joining until a `Facts` and a `HarnessesFound` came on the current stream. The machine sends both after every `Welcome`. | The website already reads these fields, and nothing gave their source (architect-r1 11, critic-r1 9, logic2-r1 11). | closed | 2026-11-26 |
| 50 | What may be kept of a token's reply? | Nothing. `CreateClientToken` is never replayed from a stored reply. `CreateClientTokenResponse.token` holds the `JoinToken` text. | The design's safe retries store the reply, and this reply holds a secret (threat-r1 4, logic2-r1 7). | closed | 2026-11-26 |
| 51 | What does the first position of a `Watch` call mean on an empty feed? | 0, and a Go server sets the position on every message. An absent position comes from an older or a sample server. | Two servers could otherwise send different first messages (logic-r1 11). | closed | 2026-11-26 |
