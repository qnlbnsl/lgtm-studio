REVISE

The server can record a command as done when its latest attempt was claimed but never sent.

## Findings

### threat-r1 01 · MAJOR · R6

**A claim makes an unsent attempt eligible for completion.** The claim stores the stream and attempt before sending. The result writer accepts that pair without evidence of dispatch, and the send test explicitly allows a matching result to win during the pause before dispatch. The frozen contract limits results to the last attempt the server sent. This is confirmed by reading `.plans/plans/go-s3-server-commands/plan.md:101`, `.plans/plans/go-s3-server-commands/plan.md:153`, `.plans/plans/go-s3-server-commands/plan.md:170`, `.plans/plans/go-s3-server-commands/plan.md:172` and `src/contracts/proto/lgtm/link/v1/commands.proto:63`.

If a restart claim commits just before the send cutoff and the second check skips the frame just after it, a matching `done` from the approved current stream still closes the row. The first outcome is final, so the server retains a success that has no corresponding delivery of that attempt. The sole writer can reach the result on a later turn because skipping an ineligible claim leaves the stream running.

Store a dispatch marker separately from claim ownership, reset it on each new claim, and require it for a result. Publish it under the machine lock only after the bounded write and flush succeed. On an ambiguous flush or marker commit, end the stream and let the next stream recover from the durable command and client receipt. Keep the wire unchanged. Change the post-claim pause test to require an untouched pending row for a matching result before dispatch and after a skipped send. Prove that a result for a dispatched attempt still closes the row once.

Category is security integrity. The Server command storage and dispatch builders own it. Risk score is 72 (6 for a restart that silently fails until the owner retries, 3 for one owner's recoverable operation, and 4 for a narrow timing boundary with an invalid result).

### threat-r1 02 · MAJOR · R6

**The ordinary response sender can report success when its flush fails.** Item 4b counts a successful callback as a send and promises that a partial, blocked or canceled write ends the stream. The link response writer drops the error from `Flush` and the ordinary transport wrapper returns the callback's error. The pinned Connect library uses the errorless `Flush` interface for Connect and Google Remote Procedure Call (gRPC) stream sends. This is confirmed by reading `.plans/plans/go-s3-server-commands/plan.md:161`, `.plans/plans/go-s3-server-commands/plan.md:169`, `.plans/plans/go-s3-server-commands/plan.md:171`, `src/server/internal/transport/link_stream.go:120`, `src/server/internal/transport/deadline.go:49` and the module pinned at `go.mod:11`.

If a small command frame is accepted by the response buffer and then times out during the flush, the callback can return success. The writer can continue on a stream that failed to deliver the frame, with the claim treated as consumed for that stream. This also makes a successful callback insufficient evidence for the dispatch marker in threat-r1 01.

Make item 4a or 4b capture the actual flush error within the deadline of the fenced write. Return failure when the send context expires during the callback. Test a successful buffered write followed by a failing flush, in addition to the held network write. Require the stream to terminate, the machine lock to release, and the attempt to remain recoverable on the next stream.

Category is security integrity and a transport failure. The Server command transport builder owns it. Risk score is 72 (6 for a command that appears sent without reaching its peer, 3 for one owner's recoverable operation, and 4 for a rare stalled flush).

### threat-r1 03 · MAJOR · C8

**Slow command writes can occupy every shared database writer slot.** Each fenced command send holds a `Store.Write` slot while waiting for the network. The pool grants five writer slots at its minimum size, and heartbeat updates, admission and cleanup also use `Store.Write`. The plan sets a per-send deadline and has no cross-stream admission limit for these sends. This is confirmed by reading `.plans/plans/go-s3-server-commands/plan.md:170`, `.plans/plans/go-s3-server-commands/plan.md:183`, `src/server/internal/store/pool.go:19`, `src/server/internal/store/pool.go:181`, `src/server/internal/store/pool.go:301`, `src/server/internal/link/presence.go:107` and `.plans/plans/go-s3-server-stream/plan.md:235`.

With five approved machines receiving pending commands through slow readers at the same time, all five slots can be held by network writes. A healthy sixth machine queues behind those writes even though its registry row is free. A command turn already waiting near its own two-second budget can terminate that healthy stream. Limiting each individual hold still permits repeated contention during a shared network slowdown.

Set a shared limit for fenced sends that reserves writer capacity for admission, heartbeats and cleanup at the minimum pool size. Take the send permit before opening the fenced transaction. When no permit is available, schedule a bounded later turn without holding a database slot or terminating the stream. Exercise more stalled peers than the send limit and verify independent health and command progress after release.

Category is shared-service availability. The Server command dispatch builder owns it. Risk score is 48 (4 for recoverable stream delays and disconnections, 3 for the single owner's fleet, and 4 for a shared network stall).

### threat-r1 04 · MINOR · R6

**The stored outcome loses the distinction between a machine refusal and a missing result.** The result writer and sweeper use the same stored `expired` value and the same finish-time column. The contract gives machine-reported expiry and server-recorded expiry different meanings. This is confirmed by reading `.plans/plans/go-s3-server-commands/plan.md:92`, `.plans/plans/go-s3-server-commands/plan.md:101`, `.plans/plans/go-s3-server-commands/plan.md:110` and `src/contracts/proto/lgtm/link/v1/commands.proto:89`.

If one restart returns `expired` after the grace cutoff but before a sweep and another reaches the sweep without a result, both can have the same action, outcome and relative finish time. The stored record cannot show whether the client explicitly declined to start or the effect is unknown.

Keep the wire outcome unchanged. Store a constrained finish source alongside the outcome and finish time in the same guarded write. Distinguish a machine result, the server's expiry sweep and removal. Exercise a late machine expiry and a sweep at the same relative time and require different stored sources.

Category is security integrity. The Server command storage builder owns it. Risk score is 36 (2 for ambiguity in the stored diagnostic, 3 for one owner's records, and 6 for the ordinary command expiry paths).

### threat-r1 05 · MINOR · R9

**The command table adds a history of the owner's machine names without settling how that history is protected at rest.** `SetState` stores the full name, and the maintenance policy keeps finished and removed command payloads for seven days. The stack gives PostgreSQL a permission-restricted named volume. The foundation specifies encryption for vault secrets, and the stream plan records the at-rest policy for machine metadata as pending. This is confirmed by reading `.plans/plans/go-s3-server-commands/plan.md:92`, `.plans/plans/go-s3-server-commands/plan.md:93`, `.plans/plans/go-s3-server-commands/plan.md:110`, `.plans/plans/go-s3-server-stream/decisions.md:42`, `deploy/compose.yaml:18`, `deploy/stack-prepare.sh:62` and `docs/specs/2026-11-25-go-rewrite-foundation-design.md:215`.

If the owner names a machine after a person or a private project, previous names remain in the new table after rename or removal. A reader of a copied application database can recover them even though the current registry no longer carries them.

Include command payloads and retained results in the Server and Stack decision on machine metadata at rest. Specify the protection for names while notices are pending. Clear the payload in the same transaction that finalizes a command when no later operation needs it. Keep the identifier, outcome and finish time for retention.

Category is security confidentiality. The Server command storage builder and Stack lead own it. Risk score is 42 (6 for identifying names, 7 because disclosure cannot be undone, and 1 because it requires access to the database or its copy).

## Answers to the attack questions

1. **Trust boundaries.** Browser mutations pass the router's origin and owner-session checks. Machine traffic crosses `Open` only after signature proof. The command path trusts the locked registry and exact current stream, and decodes only the supported action or declared result fields. The store orders durable changes and sanitizes callback errors. Client files supply credentials and receipts through existing client code. Settings and credential files are inherited at application startup. The unresolved dispatch and shared-resource boundaries are in threat-r1 01 through 03. 2. **Credential inventory.** The configured web password travels in the sign-in body. Sign-in issues a random host-only, script-inaccessible cookie and PostgreSQL stores its digest, salt and password binding. The join secret is generated by the server, stored as a verifier and presented to Join. The existing manual enrollment interface permits a token argument, and the installer uses standard input. The client's private signing key stays in its owned, restricted file. The registry stores the public key. The server signing seed lives in OpenBao and the server keeps its public fingerprint. Stack bootstrap supplies the restricted OpenBao seal file, scoped credential file and database password files. The approved Welcome connection token belongs to the existing handshake and is sent in that frame. The plan's stored request key is a replay identifier and is still subject to owner authentication. Command payloads hold standing or an action, and receipts hold a result or a credential-free owner reply. The plan requires fixed diagnostics without payloads, credentials or request keys. ## Post-build checks

- **Owner authorization and credential lifetime.** Use the real listener and an approved target. Exercise all four routes without a session, with an approved connection token alone, with a valid cookie from a foreign origin and with the same cookie after sign-out. Include a previously successful request key. Expect the refusal specified for each boundary and no new or replayed owner reply, registry mutation, command or wake from a denied call. Confirm the allowed owner still gets a single authorized action.
- **Dispatch and result ordering.** Observe a committed claim whose send is skipped at the cutoff and confirm the pending row cannot be closed by that attempt. Exercise a successful dispatch, a flush error and a lost dispatch commit reply. Observe the command row and the received frames independently. Only a dispatched current attempt can finalize. On recovery the real client uses the original command identifier and expiry, and a saved result prevents a second effect within the accepted clock margin.
- **Fleet isolation during slow writes.** Use a minimum-size store pool with several stalled command streams. Observe that an unrelated machine keeps acknowledging heartbeats and can reconnect, and that owner removal and disconnect cleanup retain a writer slot. Release the stalls and observe the pending commands continue.
- **Data minimization and transport.** In the loopback stack, send a valid result carrying a marked reserved field. Expect the result to close and the marker, raw credentials and request keys to be absent from logs and public replies. Confirm the raw credentials and reserved marker are absent from the command table. Observe the isolated proxy hop and the lack of a published Go listener. Confirm the approved policy for stored names and terminal payloads using a disposable database.
