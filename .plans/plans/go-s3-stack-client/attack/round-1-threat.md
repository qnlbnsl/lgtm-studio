### threat-r1 1 — BLOCKER — D17

The join-token command requires two fields that its dependencies omit. Item 1 reads `Config.TLSCertFile` and sets `machines.Issuer.CertificateFile`. A builder following that item encounters unknown fields when compiling against the declared Sprint 2 configuration and Sprint 3 token issuer. Remove both fields and the claimed dependency on them. ### threat-r1 2 — MAJOR — D7

The installer forwards a live join secret in the client's process arguments. A separate user on a Linux host that exposes process arguments can see the secret during the join. Redeeming it first consumes the token for a different key and places that key in the waiting row marked `hosts_server`. A manual join with a pasted literal can also leave it in shell history. Single use and expiry limit the window, and approval still gates the machine's work. Agree on a bounded standard-input form with the Client team before freezing the tests. Use it in the installer, the test driver, and the recommended manual flow. Disable shell tracing before capture, keep credential diagnostics fixed, and change the exposure test to inspect child arguments and captured channels as well as files. Capture criterion 1d's output privately and report only the result of validating its format. The server command's invalid-argument response must also omit supplied argument text. `.plans/plans/go-s3-stack-client/plan.md:153`, `.plans/plans/go-s3-stack-client/plan.md:239`, `.plans/plans/go-s3-stack-client/plan.md:258`, `.plans/plans/go-s3-client-link/plan.md:24`, `deploy/test/checks.sh:219`.

### threat-r1 3 — MAJOR — D19

The installer validates characters in paths and then performs file changes before the client applies its ownership and permission checks. An operator can point `LGTM_CLIENT_STATE_DIR` at an unrelated directory they own, such as a repositories directory. `--rejoin` will move that directory before it opens the new state. A group-writable parent of the binary or service file can also leave the service executable or its configuration replaceable by another user. Resolve the actual destinations and verify their ownership, type, and writable ancestors before building, stopping, moving, or deleting anything. Allow a rejoin archive only for a verified, dedicated client state directory and reserve the archive name without replacing an existing directory. Apply the same private-file policy to the launch agent log and its parent. `.plans/plans/go-s3-stack-client/plan.md:231`, `.plans/plans/go-s3-stack-client/plan.md:236`, `.plans/plans/go-s3-stack-client/plan.md:237`, `.plans/plans/go-s3-stack-client/plan.md:284`, `src/client/internal/state/folder.go:64`, `src/client/internal/state/folder.go:166`.

### threat-r1 4 — MAJOR — C6

An interrupted or failed rejoin can strand an otherwise working installation. For example, when token creation fails after the old state was moved, the executable has already been replaced and the enabled unit remains pointed at the now-missing state. The plan promises a failed join leaves no installed service, while that older unit can start at boot and repeatedly fail. Serialize installer runs for the service, preserve the old binary and service configuration until activation, and specify recoverable phases for staged enrollment, state switch, and activation. Restore the prior working installation when enrollment or activation fails. Record enough local recovery state to resume an interrupted switch on the next run. When a server-side join may already have committed, preserve the pending state and give the operator a way to identify and remove the abandoned waiting row before retrying with a fresh token. `.plans/plans/go-s3-stack-client/plan.md:111`, `.plans/plans/go-s3-stack-client/plan.md:236`, `.plans/plans/go-s3-stack-client/plan.md:242`, `.plans/plans/go-s3-client-link/plan.md:262`.

### threat-r1 5 — MAJOR — C6

The repeat-install decision trusts the existence of `identity.json`. After a first install with a custom state path, a shell that omits `LGTM_CLIENT_STATE_DIR` will select the default path and may enroll a second machine under the same service name. A stale identity can also make a repeat install report success when the service starts briefly and the server then rejects it. Read the installed service's state path when updating. Require an explicit migration or rejoin before switching folders. Validate the saved identity and its server against the intended stack before restarting, then verify the same machine reaches the expected waiting or online state before reporting success. `.plans/plans/go-s3-stack-client/plan.md:232`, `.plans/plans/go-s3-stack-client/plan.md:238`, `.plans/plans/go-s3-stack-client/plan.md:242`, `.plans/plans/go-s3-stack-client/plan.md:267`, `.plans/plans/go-s3-client-link/plan.md:263`.

### threat-r1 6 — MAJOR — D7

The local stack check does not establish the boundary implied by `--hosts-server`. For example, an operator can select a remote Docker context that reports a loopback port on its own host. The installer then probes that number on the installer's host and asks the remote container for a marked token. A local LGTM Studio at the same port satisfies `GetServer`, which only identifies the product. Enrollment can then fail after the installer has changed files. Document that minting is a stack-operator action authorized by container execution and access to the configured database and vault credential. Verify that the selected Docker endpoint and published service are local before changing files or requesting a marked token. Use a direct, bounded probe with environment proxies and redirects disabled. Describe `hosts_server` as operator-assigned metadata on a waiting enrollment, and keep it out of authorization decisions. `.plans/plans/go-s3-stack-client/decisions.md:19`, `.plans/plans/go-s3-stack-client/plan.md:154`, `.plans/plans/go-s3-stack-client/plan.md:234`, `.plans/plans/go-s3-server-machines/plan.md:269`, `deploy/test/checks.sh:60`, `src/frontend/src/server/sync.ts:18`.

## Answers to the attack questions

1. **Trust boundaries.** The shell supplies executable search paths, state and service destinations, and Docker selectors. The installer checks the calling user, allowed path characters, the published address, and product identity. Container execution and access to the database and OpenBao credential authorize the token command. The web session gates the Machines calls. The Client and Server plans validate token origin, verifier, key sizes, and signed challenges. Findings 3 and 6 cover the installer's unchecked filesystem and stack identity assumptions. `.plans/plans/go-s3-stack-client/plan.md:154`, `.plans/plans/go-s3-stack-client/plan.md:227`, `.plans/plans/go-s3-client-link/plan.md:105`, `.plans/plans/go-s3-server-machines/plan.md:263`, `.plans/plans/go-s3-server-machines/plan.md:359`.
2. **Credential inventory.** The issuer makes the join secret, prints it once for the caller, and stores its verifier in PostgreSQL. The installer captures it, passes it as an argument, and clears its variable after join. The client sends it to `Join` with a public key and stores the private key in `machine.key` and public enrollment data in `identity.json`. The command reads the database password and the OpenBao AppRole identifiers from the existing protected files. OpenBao issues a leased credential in memory and returns the vault-held signing key to the command. The database holds the public pin. The live test takes the configured website password and creates a session cookie in a scratch jar through its sign-in helper. The server database holds the cookie verifier, salt, and password binding. The link's approved connection token travels in `Welcome` and has no persistent store or wave 1 consumer. Findings 2 and 7 cover argument, history, and diagnostic exposure. `.plans/plans/go-s3-stack-client/plan.md:154`, `.plans/plans/go-s3-stack-client/plan.md:239`, `.plans/plans/go-s2-server-signin/plan.md:446`, `.plans/plans/go-s3-server-machines/plan.md:252`, `.plans/plans/go-s3-server-machines/plan.md:336`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:202`, `deploy/test/checks.sh:82`.
3. **Credential endings.** A join token expires after 15 minutes, can be revoked, and permits a replay for the same key before expiry while its machine exists. The verifier is pruned after the retention period, with a waiting-machine exception. Machine removal invalidates the registered key on the server. Local removal and rejoin retain private files, and the plan needs a documented archive cleanup and enrollment revocation procedure. Website sign-out, expiry, and password replacement end the corresponding sessions. The OpenBao batch token expires after 15 minutes. Vault file and database password replacement belong to the stack, and server signing-key rotation is outside wave 1. The live link discards its connection token when its session ends. `.plans/plans/go-s3-stack-client/decisions.md:35`, `.plans/plans/go-s3-server-machines/plan.md:254`, `.plans/plans/go-s3-server-machines/plan.md:263`, `.plans/plans/go-s2-server-signin/plan.md:450`, `.plans/plans/go-s2-server-signin/plan.md:456`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:204`.
4. **Encryption.** The design permits cleartext Hypertext Transfer Protocol version 2 (HTTP/2) on loopback and requires pinned HTTPS elsewhere. Wave 1 chooses loopback only. Caddy forwards cleartext HTTP/2 to the server over the private application network. The signed exchange proves both link identities. Issue 1633's public certificate termination, certificate pin source, and client certificate handling remain deferred to public proxy work. The vault encrypts the server signing key at rest. PostgreSQL holds public keys and verifiers, and the private machine key has owner-only file protection. Local key-file confidentiality depends on those permissions and the host's disk protection. Findings 1, 3, and 6 concern that boundary. `docs/issues.md:7524`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:215`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:316`, `.plans/plans/go-s2-stack-web/plan.md:155`, `.plans/plans/go-s2-stack-web/decisions.md:52`, `src/client/internal/state/atomic.go:86`.

## Post-build checks

- **PB1, credential handling.** On a disposable stack, hold enrollment and sign-in open with synthetic secrets. Stack and Client verify from process metadata, command traces, the user journal, and captured files that only the private input and intended output channels contain the secrets. Exercise malformed arguments, failed vault and database loads, and failed join. Inspect the emitted diagnostics.
- **PB2, authorization and identity.** On the built stack, exercise a user without container access, an unsigned-in browser, a signed-in token issuer, and an authorized command operator. Server and Stack verify the refusals and permission boundaries, the mark on the operator's waiting machine, an unmarked website token, and the second-key refusal. Supply an absent or mismatching established server pin and verify no token is minted and the vault identity stays intact.
- **PB3, state recovery.** Run the installer twice with a nondefault state path and exercise an interrupted rejoin, an activation failure, a concurrent run, and a destination writable by another account. Stack verifies the expected refusal or recovery, original identity and file permissions, and one active service. Archive cleanup follows explicit retirement of the old enrollment.
- **PB4, service recovery.** Reboot the disposable Linux host and collect the boot identifier, completed and running invocation records, and times for client connection and first login. Stack verifies pre-login recovery and a single service restart after exit 75, and that authenticated removal leaves the service stopped. On macOS, verify restart and removal with the real launch agent and check that login starts the installed client.
- **PB5, required user flow.** Sprint verification runs C5 to C11 with the merged stack and both binaries. Check the expiry update against the intended database account, observe both C10 refusals, and capture C11 logs and database state. Verify at least three durable outage events are applied once in order. Confirm that an injected duplicate application or dropped append causes the corresponding check to fail.
