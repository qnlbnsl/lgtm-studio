# Round 1, seat logic2: review of the plan `go-s3-stack-client`

- Task identifier: review-go-s3-stack-client-r1-logic2.
- Nonce: 03f0d6.
- Lens: logic and failure policy.
- Reviewed text: `.plans/plans/go-s3-stack-client/plan.md`, as it stands, which equals `attack/plan-v1.md`.

## Verdict

REVISE

## Top finding

A failed `--rejoin` stops the working service, moves its state away, and leaves the unit enabled, so the next restart of the machine starts a client with no identity that fails and restarts every 5 seconds without end (logic2-r1 01).

## Findings

### logic2-r1 01. A failed `--rejoin` leaves an enabled unit with no identity

- Severity: MAJOR.
- Tied statement: plan, work item 2, steps 11, 13 and 14, and the service rule "The service starts the client again 5 seconds after every exit except 0".
- Evidence: `plan.md:237` stops the service and renames the state folder before anything else is asked of the server. `plan.md:239` fetches the token and joins after that, and on failure exits 1 "with no service installed". `plan.md:240` is the only step that touches the unit, and it is never reached. `plan.md:112` and `plan.md:246` give `Restart=on-failure`, `RestartSec=5` and `StartLimitIntervalSec=0`. `.plans/plans/go-s3-client-link/plan.md:516` says `run` refuses to start without a valid `identity.json`, and the plan makes that an exit with status 1. The test `rejoin_moves_old_state` (`plan.md:268`) covers only the success path.
- Failure scenario: A machine is installed and running. The person runs `deploy/install-client.sh --rejoin` while the stack is stopped for a minute, or the token command fails, or the join is refused. Step 11 has already stopped `lgtm-client.service` and renamed the state folder to `lgtm-client.replaced-<time>`. Step 13 exits 1. The unit file is still enabled and lingering is on. At the next restart of the computer, or the next `systemctl --user restart`, the service runs `lgtm-client run` in a folder with no `identity.json`, which exits 1 every 5 seconds forever. The machine that worked before the command is now stopped, and its identity sits in a renamed folder that no document tells the person to move back.
- Prescribed fix: Order the steps so that nothing is destroyed before the new join has succeeded. Fetch and check the token first, then stop the service and rename the folder, then join. On a failed join, rename the old folder back and restart the service, or run `systemctl --user disable --now lgtm-client.service` and print one sentence that names the renamed folder. Add the test `rejoin_failure_restores_old_state`, with `SHIM_JOIN_EXIT=1` and a first run before it, which requires that the old `machine.key` is back in the state folder, or that the unit is disabled, and that `calls.log` holds no `restart` after the failure.

### logic2-r1 02. Success is reported for a client that has already stopped, and a removed machine is never told how to recover

- Severity: MAJOR.
- Tied statement: plan, work item 2, steps 12, 14, 16 and 17, the service rules for exit 0 (`plan.md:114`), and decision 36.
- Evidence: `plan.md:242` waits for `is-active`, and the unit is `Type=simple` (`plan.md:246`), so systemd reports `active` as soon as the process is forked. `plan.md:238` skips the join when `identity.json` exists. `plan.md:243` then prints the success sentence. `.plans/plans/go-s3-client-link/plan.md:204` makes a verified `unknown_machine` stop the process, and `.plans/plans/go-s3-client-link/plan.md:205` makes a missing, unsafe or damaged store exit 0 "to stop the service loop until repair". The test `rerun_keeps_joined_identity` (`plan.md:267`) uses a shim `systemctl` that is always active.
- Failure scenario: The owner removes a machine on the Machines page. The client exits 0 and the service stays stopped, which is intended. A week later the owner runs `deploy/install-client.sh` to update the program. `identity.json` exists, so step 12 skips the join. Step 14 restarts the unit, step 16 sees `active` for one second, and step 17 prints `lgtm-client runs as the user service lgtm-client.service.` and exits 0. The client then logs `link_refused` with `unknown_machine`, exits 0, and stays stopped. The installer's output says the opposite. The same happens after a damaged store. The only pointer to `--rejoin` is a sentence in the guide (`plan.md:323`), which the person is not reading at that moment.
- Prescribed fix: After step 16, keep watching for a short stable window, for example 3 seconds, and require that the unit is still `active` and that `ExecMainStatus` did not change. When the unit is `inactive` after the window, print one sentence that says the client stopped and that `--rejoin` makes a removed machine join again, and exit 1. Add a shim switch `SHIM_UNIT_EXITS_0` for the `systemctl` shim and the test `rerun_reports_stopped_client`, which requires exit 1 and the sentence. Add a second test for the timeout of step 16 (see logic2-r1 08).

### logic2-r1 03. The plan does not give `deploy/test/checks.sh` what the checks C5 to C11 need, and its acceptance depends on work it does not list

- Severity: MAJOR.
- Tied statement: plan, work item 2, "The change of the user-flow script" (`plan.md:248`), criteria 2e and 2j, and the line "Needs first: nothing" (`plan.md:221`).
- Evidence: `plan.md:248` says "No other line of the script changes." Yet criterion 2e (`plan.md:199`) requires `deploy/test/checks.sh --only C5,C6,C10` to print three `ok` lines, and criterion 2j requires 13 `ok` lines. The script, as it is now, assumes names that no item of this plan writes or checks. The full list is in the answer to question c below. The ones that matter most: `psql_in_stack` at `deploy/test/checks.sh:324` still runs `psql` as the user `lgtm` in the database `lgtm` with no password, while `.plans/plans/go-s1-stack-vault/plan.md:123` and `:223` make plan `go-s1-stack-vault` item 2 rewrite it for `lgtm_app` with a password file; `check_c5` at line 425 updates the table `client_join_tokens` by the columns `id` and `expires_at`; `check_c10` at line 505 edits the keys `clientPublicKey` and `serverPublicKey` of `identity.json`; and C5, C10 and C11 read the log messages `join_refused`, `link_refused`, `link_event_buffered` and `link_event_applied`.
- Failure scenario: The builder of item 2 changes lines 219 and 233 exactly as the plan says and runs `deploy/test/checks.sh --only C5,C6,C10`. C5 fails on `psql_in_stack` because the stack's database account does not match, or C10 fails because the client's log message has another name. The builder cannot tell whether the failure belongs to this plan, and criterion 2e is red for a reason outside the plan. Item 2 says it needs nothing first, which is false for criteria 2e and 2j.
- Prescribed fix: Replace "No other line of the script changes" with a table in the plan, one row per name the checks C5 to C11 assume, with the plan and item that writes it and the test that proves it. State in item 2 that criteria 2e and 2j need those items first. Split criterion 2e into the grep (`XDG_STATE_HOME` gone) and the three checks, and say that the grep prints 0 and exits 1, so it needs `|| true` or a comparison in the command.

### logic2-r1 04. The join token is visible in the process list, and a local user can redeem it first

- Severity: MINOR.
- Tied statement: plan, work item 2, step 13, decision 19, and the risk row "The token is visible to another user of the computer" (`plan.md:334`).
- Evidence: `plan.md:239` runs `lgtm-client join <address> <token>`, so the token is an argument of a child process for the whole length of the join. On Linux, `/proc/<pid>/cmdline` is readable by every user of the machine unless `/proc` is mounted with `hidepid`. `.plans/plans/go-s3-client-link/plan.md:276` fixes the program's interface as `join <address> <token>` and nothing else. The risk row calls it Low because "the token works once".
- Failure scenario: Another user of the same computer polls the process list. When `lgtm-client join` appears, the user copies the token and sends `Join` with their own key before the installer's client does. The token is spent, the installer's join fails with `token_used`, and a machine with the other user's key now waits for approval with `hosts_server` true, next to a machine that the owner believes is their own. The owner's approval on the page is the second gate, and the owner has no way to tell the two keys apart from the page. The consequence is bounded by that approval, and decision "security is deferred" applies, so this is MINOR. A fix is still cheap.
- Prescribed fix: Ask plan `go-s3-client-link` item 9 for one more way to give the token, standard input or a file descriptor, and make the installer use it. The test `token_never_printed` then also asserts that the shim client received the token on standard input and that no argument of the `client join` line holds it. If the interface stays as it is, change the risk row to say that the token is readable by every local user for the length of the join, and drop the word "Low".

### logic2-r1 05. A second machine with `hosts_server` true appears for every rejoin, changed state folder or second user

- Severity: MINOR.
- Tied statement: plan, work item 2, steps 6, 12 and 13, and decision 27 (D19, one user on a machine).
- Evidence: `plan.md:239` always asks for the token with `--hosts-server`. `plan.md:238` decides "already joined" only from `identity.json` inside the folder of step 6. `plan.md:228` refuses only root. `plan.md:225` lists `refuses_root` as the whole test of D19 (`plan.md:375`). Nothing in the plan says what the server does with two machines that both carry the mark.
- Failure scenario: Three runs give three rows. (a) The person runs `--rejoin` on a machine that still exists on the server: the old row stays, offline, with `hosts_server` true, and the new row also has it. (b) The person first ran with `LGTM_CLIENT_STATE_DIR` set, then runs the installer in a shell where it is unset: step 12 looks in the default folder, finds nothing, and joins a second machine, while the unit now points to the new folder. (c) A second user of the same computer runs the installer: it gets its own unit, state and token, and the server lists two machines that "run the server". The Machines page can no longer show which one is the server's own.
- Prescribed fix: Decide which of these the plan allows. For (b), read the state folder back from the installed unit when `LGTM_CLIENT_STATE_DIR` is unset, and add the test `rerun_uses_state_folder_of_installed_unit`. For (a), print one sentence after a successful `--rejoin` that tells the person to remove the old machine on the page. For (c), the installer cannot see another user's unit, so state in the guide that one user per computer is a rule that the installer does not enforce, and say what the server does with two machines that carry the mark.

### logic2-r1 06. Nothing prevents two runs at once, and a failed run leaves a temporary file

- Severity: MINOR.
- Tied statement: plan, work item 2, steps 10, 11 and 14.
- Evidence: `deploy/up.sh:16` and `:17` take a lock on the state directory with `flock`, but `plan.md:226` to `:243` takes no lock. `plan.md:236` writes the temporary program file into `$HOME/.local/bin/`, and no step removes it when the build, the `version` run or the rename fails.
- Failure scenario: The person runs the installer in two terminals, or a script runs it again while the first is waiting in step 16. Both run step 11, and the second renames a folder that the first has just created. Both write the unit by rename, and both call `join-token`, so two tokens exist and the second join starts with a state folder that the first is half way through. After a failed `version` check, a file with a temporary name stays in `$HOME/.local/bin/`.
- Prescribed fix: Take `flock` on a lock file in the parent of the state folder at step 1, as `deploy/up.sh` does, and register a `trap` that removes the temporary program file and the temporary unit file. Add a test `second_run_waits_for_lock` with the shim holding the lock, and a test `failed_build_leaves_no_temporary_file`.

### logic2-r1 07. Missing tools and a missing Docker permission give the wrong message

- Severity: MINOR.
- Tied statement: plan, work item 2, steps 8, 9 and 10, and the stated exit statuses (`plan.md:82`, "Exit 0 on success, 1 on a failure, 2 for a wrong argument").
- Evidence: Step 8 treats any output other than one loopback line as "The stack's web service publishes no loopback port. Start it with deploy/up.sh." Steps 9 and 10 call `curl`, `git` and `go` with no check that they exist. The shims in `plan.md:250` always exist, so no test reaches the case.
- Failure scenario: A user who is not in the `docker` group runs the installer. `docker compose port` fails with a permission error and prints nothing on standard output, so the person is told to start a stack that is running, and `deploy/up.sh` does not help. On a machine without Go, the shell reports `command not found` with status 127, which the table of exit statuses does not allow, and no sentence says what to install.
- Prescribed fix: Separate the failure of `docker compose` (its exit status and standard error) from empty output, and print one sentence for each. Check `command -v go docker curl` at step 3 and give one sentence for each missing tool with exit 1. Add the tests `refuses_missing_go` and `refuses_docker_without_permission`.

### logic2-r1 08. Four steps with a failure message have no test that reaches the failure

- Severity: MINOR.
- Tied statement: plan, work item 2, steps 9, 10 and 16, and the acceptance line (`plan.md:272`).
- Evidence: The `curl` shim prints one fixed good body unless `SHIM_CURL_FAIL` is set (`plan.md:250`), and the `go` shim always writes a working stand-in. The table of 16 tests has no case for a good status with a wrong body (step 9), a failed or wrong build (step 10), a program whose `version` run fails (step 10), or a unit that never becomes active (step 16, timeout of 10 seconds).
- Failure scenario: The cheapest wrong implementation of the installer passes every listed test: it checks only the exit status of `curl`, it skips the `version` run, it passes a wrong `-ldflags` or package path to a shim that ignores them, and it never waits in step 16. Another program that answers on the stack's port, for example a development server with status 200, is then taken for the stack. The wrong installer ships.
- Prescribed fix: Add `SHIM_CURL_BODY`, `SHIM_GO_FAIL`, `SHIM_VERSION_FAIL` and `SHIM_UNIT_STATE` to the shims, and the tests `refuses_wrong_answer_from_port`, `build_failure_stops_installer`, `build_flags_set_version` (which reads the arguments of the `go` shim for `-X main.version=` and the package path `./src/client/cmd/lgtm-client`) and `unit_never_active_fails`.

### logic2-r1 09. The test `token_never_printed` cannot catch the leaks that are likely

- Severity: MINOR.
- Tied statement: plan, work item 2, the risky mutation list (`plan.md:225`) and the test `token_never_printed` (`plan.md:258`).
- Evidence: The shim client never prints the token (`plan.md:250`), yet step 13 "passes on the client's output" on failure. The test looks only at files under the test's `HOME`. The temporary folder of the test is not `/tmp`, and the plan does not say that a shell trace (`set -x`) or a file under `/tmp` is checked.
- Failure scenario: Mutation: the installer writes the token to `${TMPDIR:-/tmp}/lgtm-join` for convenience, or runs under `set -x` in a debug branch, or the real client prints its argument in a usage error. The shim never does, and the file is outside `HOME`, so every test still prints `ok`.
- Prescribed fix: Run each test with `TMPDIR` inside the test's folder and scan that folder entirely. Add `SHIM_JOIN_ECHO_TOKEN=1`, with which the shim client prints its arguments, and state in the plan who guarantees the redaction: either the installer filters its output, or it relies on `TestAppLogRedactsSecrets` of plan `go-s3-client-link` (`.plans/plans/go-s3-client-link/plan.md:267`), and then names that test as its proof.

## Answers to the attack questions

Lens questions:

1. Sequences, counters, expiry and ties: The token's 15-minute expiry and its single use belong to plan `go-s3-server-machines`. This plan adds the order of installer steps: build (10), stop and rename (11), join (13), unit (14), wait (16). Step 11 before 13 is wrong, as logic2-r1 01 shows. The restart interval of 5 seconds has no ties. Two runs at once are not ordered at all (logic2-r1 06).
2. Failures permit or deny, and repair: A failed join installs no service, which is stated and tested for a first run. A failed join after `--rejoin` has no stated outcome (logic2-r1 01). A service that stops by itself with exit 0 has no stated repair beyond a sentence in the guide (logic2-r1 02). A failed build, a missing tool and a missing Docker permission have no stated outcome (logic2-r1 07 and 08).
3. Truth table of rules that speak about the same state: The state is "unit, `identity.json`, server row". The cells are: unit enabled and identity present and server row present (plain rerun, correct); unit enabled and identity present and server row removed (the installer says success, logic2-r1 02); unit enabled and identity moved away (failed rejoin, logic2-r1 01); unit absent and identity present (after `--remove`, the rerun skips the join and recreates the unit, correct); state folder changed between runs (logic2-r1 05). The rule "exit 0 means stop for good" and the rule "a damaged store exits 0" (`.plans/plans/go-s3-client-link/plan.md:205`) put two causes in one cell.
4. Zero values: An empty `LGTM_CLIENT_STATE_DIR` is treated as unset (step 6, tested by `joins_before_service_starts` for a relative value only). An empty port from `docker compose port` is refused and tested. An empty `HOME` is not mentioned: step 5 checks characters, and an empty value passes that check, so the unit would name `/.local/bin`. Add the case `refuses_empty_home` to the table of tests.
5. Two actors on the same state: Two installer runs, an installer run and the service restarting, and two users on one stack. Only the second has a sentence, in decision 27. The first is logic2-r1 06. The second is covered by `systemctl restart` in step 14, which stops the running client before it starts the new one, so the state folder lock of the client (`state.Open`) is not contended.
6. Risky mutations: Item 1: the flag fixed to false makes `TestJoinTokenHostsServerFlag` fail, and the token on standard error makes `TestJoinTokenPrintsOneTokenLine` fail. Both are real. A wrong change that the six tests do not catch: a command that uses `PublicURL` from a stale setting instead of the running server's, because the tests start the server and the command from one environment. Item 2: printing the token fails `token_never_printed` only when the printed text reaches the output of the installer, and writing it to a file outside `HOME` passes (logic2-r1 09). Moving the service step before the join fails `joins_before_service_starts`, which is real.
7. Cheapest wrong implementation that passes the tests: Item 2: an installer that checks only the exit status of `curl`, that never waits for the unit, that skips the `version` run and that passes the wrong package path (logic2-r1 08), and that reports success when the client has already stopped (logic2-r1 02). Item 1: a command that prints a hard-coded valid-looking text fails `TestJoinTokenJoinsOnce`, so nothing found. Item 4: a live test cannot be mocked, so nothing found.
8. Shapes that would make wrong states impossible: Rename the old folder only after the new join has succeeded (a new folder, then an atomic swap), which makes the failed rejoin state impossible (logic2-r1 01). Let the unit file hold the state folder and read it back, so that the installer and the service cannot disagree (logic2-r1 05). Give exit 0 and the damaged store different exit statuses in plan `go-s3-client-link`, which makes the cell in lens question 3 single-cause.

Questions about this plan:

a. The installer, a second run, another user, a failed run, and a restart of the machine.
   - Second run: the program is built again, the join is skipped when `identity.json` exists (step 12), the unit is written again, the service is restarted, and the installer reports success even when the client stopped by itself (logic2-r1 02). With `--rejoin`, the old folder is renamed first (logic2-r1 01).
   - Another user: the installer gives that user their own unit, state folder and token, and every token carries `hosts_server`, so the server lists a second machine that claims to run the server (logic2-r1 05). A user without Docker permission gets the wrong message (logic2-r1 07). Root is refused.
   - A failed run: a failed first join installs nothing, which is right. A failed `--rejoin` leaves a broken enabled unit (logic2-r1 01). A failed build leaves a temporary file (logic2-r1 06).
   - A restart of the machine: the unit is enabled and lingering is turned on, so the service starts before the first login, and the `live_service_started_before_login` test proves it from the clocks. The service retries every 5 seconds until the stack answers. The stack's own return after a restart belongs to plan `go-s2-stack-web` (its criterion 2c, `.plans/plans/go-s2-stack-web/plan.md:181`, and the `restart: unless-stopped` of the services), and this plan's test `live_machine_online_after_reboot` depends on it. On a Mac the client starts at login only, which decision 13 records. The one case that does not come back is a machine removed on the page, and that is by design.
b. The command that makes a join token on the server.
   - Who may run it: anyone who can run `docker compose exec` on the server's container. That is the Docker group or root of the host. The command takes no instance lock and checks no caller, and its mark `hosts_server` is available to that same person. This is acceptable only because Docker access already equals root of the host, and the plan's sentence "a remote machine cannot pose as the server's machine" (`plan.md:29`) holds against the machine's own claim, not against that person, who can pass the token to a remote machine.
   - Where the token appears: on standard output of the `docker compose exec` call, which the installer keeps in a shell variable. It does not appear in a log of the command (the command logs nothing and `TestJoinTokenPrintsOneTokenLine` requires an empty standard error), not in the log of the container, because `exec` output does not reach it, and not in the history of a shell, because the installer runs the command and the person never types the token. A person who runs the command by hand sees the token in the terminal only. It does appear in the process list of the machine, as the last argument of `lgtm-client join`, for the length of the join (logic2-r1 04). It does not appear in the process list of the server container, because it is output, not input.
c. What the plan gives the user-flow script for C5 to C11.
   - The plan gives two changed lines: line 219, where `join` gets `LGTM_CLIENT_STATE_DIR=$1/lgtm-client`, and line 233, where `run` gets `LGTM_CLIENT_STATE_DIR=$state_home/lgtm-client`, and one README row (`plan.md:248`, decision 35). I checked both line anchors in `deploy/test/checks.sh`, and they are right (`client_join` at line 217 and `start_client` at line 232).
   - The names that the script assumes and that the plan neither assigns nor checks, which logic2-r1 03 asks to list in the plan: `psql_in_stack` (line 324) with the account `lgtm_app` and a password file, owned by `go-s1-stack-vault` item 2; the table `client_join_tokens` with the columns `id` and `expires_at` (`check_c5`, line 425), owned by `go-s3-server-machines` item 3; the keys `clientPublicKey` and `serverPublicKey` of `identity.json` (`check_c10`, line 505), named in `.plans/plans/go-s1-client-local/plan.md:131` and written by `go-s3-client-link`; the client log messages `join_refused` with `token_used` and `token_expired` (C5), `link_refused` with `unknown_machine` and `server_key_mismatch` (C10), and `link_event_buffered` with `sequence` (C11); the server log message `link_event_applied` with `machine_id` and `sequence` (C11); the fields of `WatchClients` that C7 reads (`os`, `version`, `workspace`, `cores`, `memoryGigabytes`, `agentLimit`, `cpuPercent`, `memoryPercent`, `harnessesScanned` and `harnesses[].harness` and `.version`); the message `link_signing_key_loaded` with `source` and `fingerprint` (C13); and the README row for the working name `lgtm-server join-token` (`deploy/test/README.md`, row 80), which this plan makes final but does not change.
   - Not covered by this plan: a run of the checks while the installed service exists adds a second machine to the page. The live test asserts only a difference of counts, and `checks.sh` cleans up only its own fixtures, so the two do not break each other, but the plan does not say so.

## Post-build checks

1. Install, make the stack unavailable (`docker compose stop server`), run `deploy/install-client.sh --rejoin`. Expected: exit 1, the old state folder is back in place or the unit is disabled, and `systemctl --user show lgtm-client.service --property=NRestarts` does not grow after 60 seconds.
2. Remove the machine on the page, then run `deploy/install-client.sh`. Expected: exit 1 and a sentence that names `--rejoin`, and the unit is inactive.
3. Run `ps -eo args` as another user while the installer joins. Expected: no argument holds the token, or the plan's risk row says it does.
4. Run `deploy/install-client.sh` in two terminals at once. Expected: the second waits or refuses, and only one `client join` reaches the server.
5. Run the installer as a user outside the `docker` group. Expected: a sentence about Docker permission, not about `deploy/up.sh`.
6. Run `deploy/test/checks.sh --only C5,C6,C10` on a clean checkout with items 1 and 2 only. Expected: either three `ok` lines, or the plan names the item that must come first.
7. Run the installer with `LGTM_CLIENT_STATE_DIR` set once and unset the next time. Expected: the second run uses the folder named in the installed unit and joins nothing new.
8. Restart the computer. Expected: `live_service_started_before_login` and `live_machine_online_after_reboot` print `ok`, and the second reports an `ok` within 60 seconds only when the stack is back, so the failure message names the stack, not the client, when the stack is not.
