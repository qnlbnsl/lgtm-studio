| 8 | How are the brief's nine work items cut? | Into 14 items, each rated low or medium. The four high items of the brief are split: tokens into making a token and redeeming it, the proof into the handshake, the hub and the stream loop, and commands and events into database functions that the stream loop calls later. The calls of the Machines page are cut into those that touch only records and those that send a command. Two items are new: a write deadline for long streams, and the wiring into the server program. | The task file of 2026-11-26 asks that every high item be split where a clean cut exists. | 9 | How do the packages `machines` and `link` depend on each other, when the blueprint has each use the other? | `link` imports `machines`. `machines` declares the interface `machines.Link`, which `*link.State` satisfies, and the server program passes it in. Both import the generated contract. | Go refuses an import cycle. The records of machines and their tokens are the base that the link reads. The Machines page needs only three things from the link: presence, a stored command and forgetting a machine. | closed | 2026-11-26 |
| 10 | Issue 1633: where does encryption end, and what does the join token pin? | Encryption ends at the web server of the stack. The server reads the certificate named by `LGTM_TLS_CERT_FILE` when it makes a token for an `https` address, and puts the SHA-256 of the certificate's Subject Public Key Info into `certificate_key_sha256`. An `http` loopback address gets an empty pin. The server asks a machine for no certificate. The signed challenge proves the machine. | `go-s2-stack-web` decided the same on 2026-11-26 in its row 9, and the contract plan pins the certificate's key. Assumption: the owner keeps option A of point 2 of the contract plan, which `.foundry/go-rewrite/owner-choices.md` item 7 recommends. | unanswered | 2026-11-26 |
| 11 | What may a machine do on the link while it waits for approval? | It may complete the handshake and send heartbeats. Its `Welcome` carries an empty connection token. The server sends it no command except `SetState`. An event from it is consumed: its number becomes the mark and nothing else changes. A single policy function decides this, so another choice of the owner changes one table and its test. | The design says that a waiting machine can connect and do nothing else. The client plan of 2026-11-26 sends no event while waiting and sends its facts after approval, so no report is lost. Consuming an event, instead of refusing it, keeps a client that sends one anyway from looping. Assumption: the owner's answer to point 3 of the contract plan does not require the server to show the facts of a waiting machine. If it does, option B applies `Facts` and nothing else. | unanswered | 2026-11-26 |
| 12 | How does a client learn why `Join` refused a token? | The server sets the response header `Lgtm-Join-Refusal` on every `permission_denied` from `Join`. Its values are `token_unknown`, `token_expired`, `token_revoked`, `token_used` and `machine_removed`. A secret that does not verify gives `token_unknown`, so the header says nothing about a token whose secret the caller lacks. | Check C5 expects the client to log `token_used` and `token_expired`, and the client plan of 2026-11-26 reads this header. The contract has only one code for every refusal. Assumption: the Contract team writes the header and its values in the comment of `Join`. | unanswered | 2026-11-26 |
| 13 | How is a token's secret stored and checked? | As the SHA-256 of the label `lgtm-join-token-v1`, one zero byte and the 32 secret bytes. The check compares the two digests with `crypto/subtle.ConstantTimeCompare`. | The design says the server stores a verifier of each token. The secret has 256 random bits, so a slow hash adds nothing. The label keeps the digest from matching any other use of the same bytes. | closed | 2026-11-26 |
| 14 | Which address does a token carry? | The server's configured public address, `config.Config.PublicURL`, in lowercase, without a default port and without a trailing slash. `Tokens.Create` takes an optional address and refuses one that differs from the configured address after the same normalization. | The contract plan says that every token comes from one configured address and pin. The installer of `go-s3-stack-client` passes an address. A refusal of a different address shows a wrong setting at once, instead of a join that fails later. | unanswered | 2026-11-26 |
| 15 | Issue 1638: where does `Client.hosts_server` come from? | From the token. `Tokens.Create` takes `HostsServer`, the token row keeps it, and `Redeem` copies it to the machine. `CreateClientToken` never sets it. | `go-s3-stack-client` decided the same on 2026-11-26 in its row 10, and only its command `lgtm-server join-token --hosts-server` sets it. Assumption: no message of the link carries the fact. | unanswered | 2026-11-26 |
| 16 | Issue 1637: what does `Client.address` show? | The address the current connection came from, for showing only. Behind the stack's web server, the server takes the last entry of `X-Forwarded-For`. Otherwise it takes the peer's address. A value that is not an address of the internet protocol gives an empty string. While the machine is offline, the field shows the last address seen. | The contract plan rewrote the comment of `Client.address` that way. The web server of the stack sets the header to the address of its own peer. Assumption: the web server keeps that default. | unanswered | 2026-11-26 |
| 17 | Issue 1639: what happens when the server's signing key or the certificate's key is replaced? | Wave 1 replaces neither. The signing key is created once in OpenBao and never overwritten, and the certificate's key is kept for good. If either is replaced by hand, every machine that joined before refuses the server, and the Machines page shows it offline. The owner then removes each such machine and joins it again with a new token. A hand-over in which the old key signs the new key waits for a later wave. | `go-s2-server-signin` writes the key with compare-and-set and never overwrites it. `go-s2-stack-web` keeps the certificate's key for good. A hand-over needs a new message of the contract, which is frozen after sprint 0. | unanswered | 2026-11-26 |
| 18 | How does the server know that a machine is there, without trusting memory? | Each current stream has a row in `link_connections` with a lease that ends 35 seconds after the last heartbeat, by the database's clock. The stream's own timer ends the stream after 30 seconds without a heartbeat, by the process's monotonic clock, and deletes the row. A sweep every 5 seconds deletes a row whose lease has passed, which covers a process that died. A machine shows online only while its row's lease has not passed. | The design says the server marks a machine offline when its stream closes or after 30 seconds without a heartbeat. Rule 7 says nothing kept in memory may be unreadable from the database. The lease is 5 seconds longer than the timer, so a live stream is never swept. | unanswered | 2026-11-26 |
| 19 | How do two streams of one machine agree which one is current? | The table `link_machines` holds a generation for each machine. Becoming current raises it by one under the row's lock, and the stream keeps its generation. The hub of a process keeps only the stream of the highest generation, and ends a lower one with `aborted`. Every write of a stream names its stream identifier, so a stream that is no longer current changes no row. | The contract says that only the newest proven stream counts, and that a late end of an older stream cannot mark the machine offline. The row lock orders the generations in commit order, also across several server processes. | unanswered | 2026-11-26 |
| 20 | How are events numbered after round 2 of the contract? | The server's mark is the only record of what was applied. `Welcome.last_event_number` is the mark. The server applies an event only when its number is the mark plus one, drops a lower number and answers it with the mark, and ends the stream with `out_of_range` on a higher number. The server reads no number from `Hello`. | The orchestrator relayed on 2026-11-26 that round 2 of the contract removes `Hello.acked_event_number` and keeps the server as the only judge. Restoring the database to an earlier state is outside wave 1. | closed | 2026-11-26 |
| 21 | May the owner remove the machine that runs the server? | Yes. `RemoveClient` treats every machine alike. | The contract says nothing about refusing it. The answer to issue 1639 needs the owner to remove and join again the server's own machine too. The sample server refuses it, but the sample is not the contract. Assumption: the owner accepts that the page offers removal for that machine. | unanswered | 2026-11-26 |
| 22 | May a machine that waits for approval be renamed? | No. `RenameClient` refuses it with `failed_precondition`, and the name is given at approval. | The page offers renaming only for an approved machine. A waiting machine shows its host name, which the machine reported. | unanswered | 2026-11-26 |
| 23 | What does `CreateClientToken` do with a request key? | It refuses a present `Lgtm-Request-Key` with `invalid_argument` and the sentence "This call does not accept a request key." | `.foundry/go-rewrite/owner-choices.md` item 1 gives this as the default for a call whose reply holds a credential, and `go-s2-server-signin` does the same for `SignIn`. The website sends no request key. Assumption: the owner keeps that default. | unanswered | 2026-11-26 |
| 24 | How long may each command wait before it expires? | `SetState` 1 hour, `ScanHarnesses` 2 minutes and `Restart` 2 minutes, counted from the database's clock when the command is stored. | The design gives commands an expiry and no length. A scan or a restart that runs long after the click surprises the owner. `Welcome` carries the standing, so a `SetState` that expires loses nothing. | unanswered | 2026-11-26 |
| 25 | How does a removal reach a machine that is connected? | The removal commits, and the hub ends the machine's current stream with `unauthenticated` and the sentence "The server does not know this machine. Join it again." The server sends no `SetState` with `APPROVAL_REMOVED`. | Rule 6 says every command goes through stored commands, and a removed machine keeps no stored command. The contract lets the server skip the notice. The stream's `Challenge` verified, so the client stops, as the contract's table of codes says. | unanswered | 2026-11-26 |
| 26 | What does `ReconnectClient` do? | It stores a `Restart` command for an approved machine that is connected, and refuses every other machine with `failed_precondition`. | The owner decided on 2026-11-25 that the call restarts a client that is connected. How the Machines page follows is point 1 of the contract plan for the owner, and no file of this plan changes the page. | unanswered | 2026-11-26 |
| 27 | How does a long stream end when the other side stops reading? | A small package `src/server/internal/transport` puts a write deadline into each request's context, through `http.ResponseController`. Every send on `Open` and on `WatchClients` sets a deadline of 10 seconds first. The router of `go-s2-server-signin` wraps the two route families in it. | The store plan leaves the blocked-transport case to the Machines adapter. A send that blocks would otherwise hold its handler forever. | unanswered | 2026-11-26 |
| 28 | May this plan change files that `go-s2-server-signin` writes in sprint 2? | Yes, files of the Server team only: `src/server/internal/api/server.go`, `src/server/internal/config/config.go`, `src/server/internal/app/start.go` and `src/server/servertest/server.go`. Each change is named in an item, and the result file asks the sign-in plan to agree. | The epic lets the Server team edit `src/server/`. The sign-in plan says the later machine work plugs its handlers and migrations into the same application. The shared rules forbid only another team's folder. | closed | 2026-11-26 |
| 29 | Which setting names the certificate? | `LGTM_TLS_CERT_FILE`, read into `config.Config.TLSCertFile`. It is required when `LGTM_PUBLIC_URL` starts with `https://`. | `go-s2-stack-web` sets that name in its row 25. The sign-in plan's configuration has no such field yet. | unanswered | 2026-11-26 |
| 30 | Which topics of the change feed does this plan write? | `machines`, keyed by machine identifier, for the record the Machines page shows. `machine_outbox`, keyed by machine identifier, when a machine's stored commands change. `client_join_tokens`, keyed by token identifier, when a token changes. Every scope is empty. | The design says a feed row names a record and does not carry it. One topic for the page keeps `WatchClients` to one source. Keying the outbox by machine lets the hub wake one stream without a read. | closed | 2026-11-26 |
| 31 | Which tables does this plan create? | The part `machines` creates `machines` and `client_join_tokens`. The part `link` creates `link_machines`, `link_connections` and `link_commands`. | Rule 1 gives each part its own tables. `deploy/test/README.md` fixes the name `client_join_tokens` with its columns `id` and `expires_at`. | closed | 2026-11-26 |
| 32 | Does every heartbeat write to the database? | Yes. It renews the lease, writes the load and the time, and records a change of the topic `machines`. | The page shows the load and the last time heard. With 10 seconds between heartbeats, 100 machines write 10 rows a second, far below the feed's limit of 2,048 rows that a watch may fall behind. Assumption: wave 1 has fewer than 100 machines. | unanswered | 2026-11-26 |
| 33 | How long are old tokens and finished commands kept? | A token is deleted 24 hours after it expired, unless its machine still waits for approval. A command is deleted 7 days after it finished. A command with no final result 24 hours after its expiry is finished as `COMMAND_OUTCOME_EXPIRED`. | The contract fixes the 24 hours for commands. The other periods are long enough for a person to read what happened, and keep the tables small. | unanswered | 2026-11-26 |
| 34 | What is a valid name for a machine? | Text of 1 to 64 bytes of UTF-8 after trimming spaces at both ends, with no control character. Two approved machines cannot have the same name, compared in lowercase. | The sample server trims, refuses an empty name and compares without regard to case. A limit keeps the record small. | unanswered | 2026-11-26 |
| 35 | Which log lines does the server write for the link? | One JSON object per line: `link_event_applied` with `machine_id` and `sequence` after each commit that moved a mark, `link_stream_opened` with `machine_id` and `generation`, `link_stream_closed` with `machine_id` and `code`, and `link_refused` with `reason`. No line holds a token, a secret, a nonce or a signature. | `deploy/test/README.md` fixes the first line, which check C11 reads. | closed | 2026-11-26 |
| 36 | How do the server's own tests drive the link without the real client? | A scripted machine in `src/server/internal/link/machinetest/` speaks the link through the generated client, signs with a key it makes, and lets a test send any message in any order. Tests with the real client live in `src/linktest/`, which the orchestrator owns. | Issue 1634 keeps each program's code from the other's tests. A scripted machine can send the wrong message on purpose, which the real client never does. | closed | 2026-11-26 |
| 37 | How large may one message of the link be? | 64 kibibytes, for `Join` and for each message of `Open`. | The largest message of wave 1 is a list of at most 16 harnesses. A limit keeps a machine that has not proved itself from filling memory. | unanswered | 2026-11-26 |
| 38 | Which calls of the Machines page replay a stored reply for a request key? | `RevokeClientToken`, `ApproveClient`, `RenameClient`, `RemoveClient`, `ScanClientHarnesses` and `ReconnectClient`, each with `ReceiptSafe` true and a version 1 fingerprint of its request fields. | Their replies hold no secret. The design says every request that changes something can be sent twice and happens once. | unanswered | 2026-11-26 |
