REVISE

The command result path verifies the sending stream but leaves the command's owning machine implicit, so an implementation can let one machine finalize another machine's command.

## Findings

### logic-r1 1 — BLOCKER — R6

**Category and owner.** Command integrity. The Server team owns item 6. Evidence is by reading.

**Evidence and failure.** Item 6 checks that the sender's stream is current, then checks the command identifier and attempt. The table keys commands by identifier alone. A lookup with those two fields satisfies the listed tests, yet it can commit a final result from a different machine and permanently suppress delivery to the intended machine. The wire contract requires the current stream of the command's own machine. `.plans/plans/go-s3-server-machines/plan.md:449`, `.plans/plans/go-s3-server-machines/plan.md:459`, `.plans/plans/go-s3-server-machines/plan.md:470`, `src/contracts/proto/lgtm/link/v1/commands.proto:51`.

**Fix.** Under the sender's machine lock, update a pending command only when its identifier, owning machine, sent stream and attempt all match. Test two approved machines with real current streams. A result from the wrong machine leaves the command and feed unchanged, and the assigned machine can finish it.

### logic-r1 2 — MAJOR — R6

**Category and owner.** Command delivery. The Server team owns items 6 and 10. Evidence is by reading.

**Evidence and failure.** `Claim` takes every eligible command in one write and records an outbox reference for each. Independent calls can queue 257 commands before the next claim, and the outbox references all use the same machine key. The store rejects the 257th reference even when the references have identical keys. The entire claim rolls back. The same backlog can defeat each reconnect, including an approval command that stays pending indefinitely. `.plans/plans/go-s3-server-machines/plan.md:165`, `.plans/plans/go-s3-server-machines/plan.md:384`, `.plans/plans/go-s3-server-machines/plan.md:457`, `.plans/plans/go-s1-server-store/plan.md:318`, `src/server/internal/store/feed.go:25`.

**Fix.** Claim a bounded batch in deterministic order. Record one outbox reference for the machine per batch and continue draining while eligible rows remain, with a turn for heartbeat and input between batches. Specify a null-safe eligibility predicate so a never-sent command is included. Test 257 pending rows, including a non-expiring state command, and prove bounded progress across a reconnect.

### logic-r1 3 — MAJOR — C8

**Category and owner.** Presence during failures. The Server team owns items 5 and 10. Evidence is by reading.

**Evidence and failure.** The same goroutine services the heartbeat timer, database writes and every send. A heartbeat just before a series of slow sends or a blocked write can leave timer expiry waiting behind that work. If the handler returns while PostgreSQL is unavailable, its single five-second cleanup can fail. The presence read still treats the row as current, with no repair until a server restart or a new admission. Even a timer handled at exactly 30 seconds still has a cleanup commit and a Watch delivery ahead of it. The current C8 script exercises a stopped client and can pass on prompt transport closure without testing silence. `.plans/plans/go-s3-server-machines/plan.md:337`, `.plans/plans/go-s3-server-machines/plan.md:339`, `.plans/plans/go-s3-server-machines/plan.md:384`, `.plans/plans/go-s3-server-machines/decisions.md:48`, `src/server/internal/store/pool.go:313`, `src/contracts/proto/lgtm/link/v1/events.proto:98`, `deploy/test/checks.sh:470`.

**Fix.** Give each admitted stream an independently enforced monotonic deadline that cancels blocked work and prevents a heartbeat arriving after expiry from renewing it. Make an expired row ineligible for presence and commands, and retry fenced cleanup and publication after a database failure. Define the deadline budget for the healthy Watch path and what the Watch reports during an outage. Test an open but silent transport, a blocked writer at expiry, and database recovery without a process restart.

### logic-r1 4 — MAJOR — C10

**Category and owner.** Stream admission and removal. The Server team owns items 8 to 10. Evidence is by reading.

**Evidence and failure.** Stream B can commit admission, pause before registration, and miss a removal that commits and is handled by the hub during the pause. Item 8 then allows B to send `Welcome` even though it was never sent before removal. Its own test permits this. Contract check 10 requires no `Welcome` at that seam. Check 16 permits a `Welcome` already sent and held in transit. The same registration gap can leave an older admission with no higher-generation handle to compare against. Resubscribing at the head only wakes handles, so it also skips a removal row that the old subscription missed. `.plans/plans/go-s3-server-machines/plan.md:364`, `.plans/plans/go-s3-server-machines/plan.md:369`, `.plans/plans/go-s3-server-machines/plan.md:377`, `.plans/plans/go-s0-contract/plan.md:766`, `.plans/plans/go-s0-contract/plan.md:772`, `src/contracts/proto/lgtm/link/v1/link.proto:129`.

**Fix.** Specify how the final send of `Welcome` is ordered against removal and a later admission, including the boundary between an unsent message and bytes in transit. Fence registration and the send against current database state. On follower recovery, reconcile each live handle against that state and end removed or replaced handles with the specified status. Preserve the two separate removal tests for the unsent and in-transit cases.

### logic-r1 5 — MAJOR — D16

**Category and owner.** Ordering when approval changes during a connection. The Server team owns items 6 and 13. Evidence is by reading.

**Evidence and failure.** A stream can receive a waiting `Welcome`, then the owner can approve it and enqueue a restart before its next claim. The claim sees approval and orders both commands by database wall time alone. With tied timestamps or a backward clock step, it can send the restart before `SetState`. The client accepts only `SetState` while waiting, and the server will not claim the discarded restart again on the same stream. Separately, item 13 accepts a scan while the machine is still joining, although the website contract says the scan is for an online machine. `.plans/plans/go-s3-server-machines/plan.md:365`, `.plans/plans/go-s3-server-machines/plan.md:458`, `.plans/plans/go-s3-server-machines/plan.md:541`, `.plans/plans/go-s3-server-machines/plan.md:572`, `.plans/plans/go-s3-client-link/plan.md:243`, `src/contracts/proto/lgtm/v1/clients.proto:31`.

**Fix.** Keep a per-machine enqueue order allocated under the machine lock. Deliver the approval state before any work that depends on it when the stream's `Welcome` was waiting. ### logic-r1 6 — MAJOR — R6

**Category and owner.** Command receipt retention across reconnect. The Server and Client teams share the repair. Evidence is by reading.

**Evidence and failure.** The server decides expiry with its own time, while the client can prune a finished receipt using its wall clock. A client with a clock more than a day fast can complete a command, lose its reply, and prune its receipt when finishing other work. If it reconnects before the original command expires by the server's clock, that command can run again. The client's conservative estimate for starting a command does not protect a receipt already discarded by a different clock. `.plans/plans/go-s3-server-machines/plan.md:458`, `.plans/plans/go-s3-client-link/plan.md:242`, `.plans/plans/go-s3-client-link/plan.md:244`, `.plans/plans/go-s3-client-link/plan.md:246`, `src/contracts/proto/lgtm/link/v1/commands.proto:12`.

**Fix.** Align retention with the authenticated server-time window. Keep a receipt or a durable no-rerun record until the client can establish that the server's retry window has ended. Preserve the recorded result throughout that window. Add a real-client test with a fast local wall clock, a lost reply, intervening work and replay before server expiry. Describe a crash after reservation as an interrupted outcome with an unknown effect, as the contract does.

### logic-r1 7 — MAJOR — C11

**Category and owner.** Contract values and durable event ordering. The Server and Contract teams own the repair, with the Client team for counter exhaustion. Evidence is by reading.

**Evidence and failure.** Wire event numbers and state revisions are unsigned 64-bit integers. The server's counters are signed 64-bit database integers. The client plan only stops before the unsigned limit, so it can durably append a next event the server cannot store. **Fix.** Agree on representable ranges and encodings at the contract boundary. Store the agreed range losslessly, and check exhaustion before changing counters on either end. Specify bounds for the website's rounded memory value and for PostgreSQL text, including join host names. If an agreed report value is invalid, consume it without a readiness update after checking its number. Define how the capture timestamp is retained and shown, or ask the Contract team to resolve that promise. Test the signed boundary, the first value beyond it and the successor or explicit exhaustion behavior.

### logic-r1 8 — MAJOR — R4

### logic-r1 10 — MAJOR — C11

**Category and owner.** Commit and rollback evidence. The Server team owns items 6, 7 and 10. Evidence is by reading.

**Evidence and failure.** The claim seam fails before commit, and the event fixtures fail an update of either the effect or the mark. An implementation can commit the effect in one transaction, then write the mark in another. ### logic-r1 12 — MINOR — R4

**Category and owner.** Command sweep concurrency. The Server team owns item 6. Evidence is by reading.

**Evidence and failure.** The plan declares one machine lock order for every writer, then describes an unrestricted sweep across command rows. ## Answers to the attack questions

1. **Order and limits.** Feed positions order commits and can have rollback gaps. The client starts events at 1, and the server starts its mark at 0, tolerates repeats and refuses gaps without remembering them. Admission uses a persisted generation and standing starts at revision 1. Claims start at attempt 1 on the wire and retain their committed attempts through restart. Wall-clock ties can reorder commands, the two creation timestamps can diverge, and counter limits need explicit rules. Post-commit logs can be written out of order across two handlers or lost at process death, even when application order is correct. The C11 script observes those logs. `.plans/plans/go-s1-server-store/plan.md:337`, `.plans/plans/go-s3-server-machines/plan.md:233`, `.plans/plans/go-s3-server-machines/plan.md:336`, `.plans/plans/go-s3-server-machines/plan.md:458`, `.plans/plans/go-s3-server-machines/plan.md:479`, `deploy/test/checks.sh:540`.
2. **Failure and repair.** Join rollback allows retry, and a lost reply replays for the same key only while eligible by the database clock. The event transaction and the persisted mark handle lost acknowledgements and ordinary restarts. The open-stream error mapping needs an explicit unavailable case for failed writes, and cleanup needs recovery after the database returns. Command outcomes use the client receipt, whose retention can disagree with server expiry. `.plans/plans/go-s3-server-machines/plan.md:263`, `.plans/plans/go-s3-server-machines/plan.md:337`, `.plans/plans/go-s3-server-machines/plan.md:390`, `.plans/plans/go-s3-server-machines/plan.md:479`, `.plans/plans/go-s3-client-link/plan.md:246`.
3. **Interacting rules.** Join chooses unknown, expired, revoked, different key, removed, replay or first use in that order. Approval first preserves the machine during revocation, while revocation first removes the waiting machine. A waiting record stays waiting with either presence value. An approved record is offline without presence, joining with an incomplete current report pair, and online with both. A stale presence row occupies the wrong cell after failed cleanup. The removal-before-unsent-welcome cell contradicts contract check 10. The waiting-welcome/approved-claim cell lacks a guaranteed state-before-work order, the current-sender/other-owner command cell lacks an ownership check, and decision 46 forbids recording an expired state command while the result handler would accept that outcome. `.plans/plans/go-s3-server-machines/plan.md:263`, `.plans/plans/go-s3-server-machines/plan.md:369`, `.plans/plans/go-s3-server-machines/plan.md:458`, `.plans/plans/go-s3-server-machines/plan.md:541`, `.plans/plans/go-s3-server-machines/plan.md:561`.
4. **Zero and absence.** An empty or malformed first frame is invalid, while an unknown kind after welcome is ignored. Zero event number and zero result attempt are invalid, zero outcome becomes failed, and approval projects from its two stored states. A waiting welcome has an empty name and token, and its event mark may be zero. An empty normalized owner name is refused, an empty host name passes the given limits, an empty token address selects the configured address, and an empty feed still carries a present zero position. Absent heartbeat load maps to null, whereas measured zero must remain present. The never-sent command's null stream needs explicit claim semantics. `.plans/plans/go-s3-server-machines/plan.md:233`, `.plans/plans/go-s3-server-machines/plan.md:251`, `.plans/plans/go-s3-server-machines/plan.md:272`, `.plans/plans/go-s3-server-machines/plan.md:346`, `.plans/plans/go-s3-server-machines/plan.md:385`, `.plans/plans/go-s3-server-machines/plan.md:452`, `.plans/plans/go-s3-server-machines/plan.md:481`, `.plans/plans/go-s3-server-machines/plan.md:549`.
5. **Concurrent owners.** Two joins and revocation serialize on the token, approval and revocation meet at the conditional machine delete, and admission serializes with older stream writes on the machine row. A late disconnect cannot delete a replacement row. The sweep has no matching lock rule. The hub, shutdown and delayed registrations need a live-handle convergence test because their memory ordering is separate from the row ordering. `.plans/plans/go-s3-server-machines/plan.md:120`, `.plans/plans/go-s3-server-machines/plan.md:263`, `.plans/plans/go-s3-server-machines/plan.md:336`, `.plans/plans/go-s3-server-machines/plan.md:377`, `.plans/plans/go-s3-server-machines/plan.md:460`, `.plans/plans/go-s3-server-machines/plan.md:561`.

## Post-build checks

- **Fresh challenges and transport errors.** Have a real client receive a challenge signed by the wrong server key. Verify that it stops that handshake before sending proof. Replay an earlier proof under a new valid challenge and require refusal with no admission. Run the refusal cases over Connect and the gRPC remote procedure call protocol through the stack proxy, and verify the reason comes from the terminal status metadata.
- **Recovery after an ambiguous commit.** Cut server or client transport after a particular event commits and before its acknowledgement arrives. Restart each program separately using its existing durable state. Verify from the committed effect and mark that the event applied once and the next event applied in order. Check the observation path separately from the state so a lost diagnostic cannot be mistaken for lost data.
- **Blocked response.** Observe actual socket or protocol backpressure with a client that stops reading. Require the write deadline to end both link and Watch handlers. Measure the healthy client stopping and returning online through one Watch, and run the independent silent-current-stream case.
- **Restart on a new process.** Lose the first restart result after the client has saved it. Observe the system service start a new process, that process return online, and the server finish the same command under the later attempt without another exit.
- **Shutdown with admission in flight.** Pause immediately before or after admission and start server shutdown. Release the pause and require a transient shutdown status and no surviving handle.
