REVISE

The plan treats the signed handshake as sufficient on a cleartext path that carries the enrollment secret, commands and durable event acknowledgements.

## Findings

The review used commit `6e5abd4b`. Confirmed live by comparison, the reviewed plan matched the frozen copy byte for byte. Findings are by reading the plan, the current contract and the named source files.

### threat-r1 01 — BLOCKER — C10

**The cleartext path has an unresolved integrity boundary.** The plan calls issue 1633 settled and configures tokens with an empty certificate pin. The server signs both nonces and the machine identifier at the start of the stream. Later frames, including acknowledgements, have no cryptographic integrity check of their own. Contract point 2 still asks which transport boundary Wave 1 can trust. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:50`, `.plans/plans/go-s3-server-machines/plan.md:359`, `.plans/plans/go-s3-server-machines/plan.md:385`, `.plans/plans/go-s0-contract/plan.md:129` and `docs/specs/2026-11-25-go-rewrite-foundation-design.md:316`.

**Failure.** An unintended local listener can receive the raw join secret before the client checks the returned public key. A party that can alter traffic on either cleartext hop can also invalidate the integrity guarantee after a valid handshake. An altered acknowledgement within the client's sent range can leave the client believing an uncommitted report is safe to discard. Evidence for the client's deletion rule is in `.plans/plans/go-s3-client-link/plan.md:107` and `.plans/plans/go-s3-client-link/plan.md:169`.

**Change.** Make the recorded transport decision a prerequisite for freezing this plan. Require the intended listener to be authenticated before releasing a join secret and require integrity for subsequent frames wherever other local principals can reach the path. Coordinate the mechanism with the Contract, Client and Stack teams. For any expressly accepted cleartext path, record the trusted principals and enforce the network or operating-system boundary that keeps other principals outside it. Keep the loopback-only public exposure for Wave 1.

### threat-r1 02 — BLOCKER — R6

**A result is checked against the stream but can close another machine's command.** The command row has a machine identifier and a sent-stream identifier. The acceptance procedure only tests whether the sender is current for its own machine and whether the command and attempt match. The contract requires the current stream of the command's machine. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:449`, `.plans/plans/go-s3-server-machines/plan.md:458`, `.plans/plans/go-s3-server-machines/plan.md:459` and `src/contracts/proto/lgtm/link/v1/commands.proto:55`.

**Failure.** Machine A's current stream supplies a result for a pending command addressed to machine B. If the identifier and attempt match, the planned checks can permanently finish B's command under A's lock. If the real delivery was lost, B never receives another attempt.

**Change.** Require the command identifier, authenticated machine identifier, current stream identifier, exact attempt and pending status in the same guarded update. Keep the machine lock. Add assertions that a result from a different machine and a result on a new stream before it claims the command both leave the command pending.

### threat-r1 03 — MAJOR — C8

**Offline depends on a handler getting through its own send loop and deleting the row.** The timer is selected after the initial batch of sends and competes with later writes and sends. Each send can use 10 seconds, and cleanup has a separate five-second context. Presence reads every connection row. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:318`, `.plans/plans/go-s3-server-machines/plan.md:337`, `.plans/plans/go-s3-server-machines/plan.md:339`, `.plans/plans/go-s3-server-machines/plan.md:384`, `.plans/plans/go-s3-server-machines/decisions.md:48` and `src/contracts/proto/lgtm/link/v1/events.proto:98`.

**Failure.** A client goes silent just after a heartbeat, and the handler is in a send when the 30 seconds pass. The page remains online until the handler returns and cleanup commits. If cleanup fails while the server remains running, later snapshots can keep returning presence until another connection or a server restart.

**Change.** Give the heartbeat deadline independent cancellation, cap all stream work by the remaining heartbeat budget and have the presence read exclude expired rows. Add a retryable expiry path that publishes the offline change to an already open watch and only expires the matching stream. Exercise both a blocked writer and a failed first cleanup. Keep the normal 10-second heartbeat and the startup cleanup.

### threat-r1 04 — MAJOR — C10

**The hub can forget the ordering information needed by delayed registration and removal.** Admission precedes hub registration. The hub compares generations only against a currently registered handle, and its feed recovery wakes handles without reconciling them against the database. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:364`, `.plans/plans/go-s3-server-machines/plan.md:365`, `.plans/plans/go-s3-server-machines/plan.md:377` and `src/contracts/proto/lgtm/link/v1/link.proto:100`.

**Failure.** Stream A pauses after admission. Stream B is admitted, registers, then closes and unregisters. When A resumes, the hub is empty and permits A to send a stale `Welcome`. Its first guarded write still fails. If a removal lands during a feed resubscription, the hub merely wakes the handle. `Claim` has no explicit mapping from a deleted machine to the required terminal refusal.

**Change.** Fence registration and the decision to send `Welcome` against the durable admission and removal state even when there is no hub handle. Let an already in-flight welcome finish with the contract's terminal reason. Reconcile handles on feed recovery so a missed removal ends the stream with `unknown_machine`. Freeze tests with a replacement that registers and exits while the older handler is paused, and with removal during resubscription.

### threat-r1 05 — MAJOR — R6

**Server retry eligibility outlives the client's promise to retain a result.** The contract gives the client a result replay window of 24 hours after expiry. The server claims any pending command, including after this window until the hourly sweep runs. The client plan prunes receipts using its own wall clock. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:391`, `.plans/plans/go-s3-server-machines/plan.md:458`, `.plans/plans/go-s3-server-machines/plan.md:460`, `.plans/plans/go-s3-client-link/plan.md:246` and `src/contracts/proto/lgtm/link/v1/commands.proto:6`.

**Failure.** A scan or restart completes, but its result is lost. On reconnect after the 24-hour window and before the next sweep, the server retries after the client legitimately discarded its receipt. A client clock ahead of the server can produce the same failure inside the required replay window. The completed command can be recorded as expired, even when the execution itself was correctly deduplicated.

**Change.** Enforce the retry cutoff in the claim transaction using the server's clock. Preserve the exception for `SetState`. Have the Client team keep receipts until safe against the same server-based cutoff, including after a process restart, and retain them when the cutoff cannot be established. Cover late claims before a sweep and a fast client clock near the end of the replay window.

### threat-r1 06 — MAJOR — C11

**Reports that pass the plan's checks can fail the database write and jam the durable queue.** The contract uses unsigned Protocol Buffers fields for core count, agent limit, memory bytes and event numbers. The plan uses signed PostgreSQL columns with smaller positive ranges. Its string policy also allows a zero character in fields stored as PostgreSQL text. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:227`, `.plans/plans/go-s3-server-machines/plan.md:328`, `.plans/plans/go-s3-server-machines/plan.md:483` and `src/contracts/proto/lgtm/link/v1/events.proto:41`, `src/contracts/proto/lgtm/link/v1/events.proto:66`.

**Failure.** A decoded next report has the value 2,147,483,648 in its core count, which fits the wire type. The plan treats the report as valid and attempts to write it into a signed 32-bit column. The write cannot commit, the server leaves the mark unchanged, and the client keeps replaying the same report before all later reports. A zero character in the workspace has the same persistence failure.

**Change.** Use representations that round-trip supported wire values. Agree with the Contract team on bounds for values that cannot be represented downstream, including memory projected to the website's unsigned 32-bit field. For report content outside those bounds, consume the next event and advance its mark without applying the report. Specify handling for exhausted counters and invalid text separately from transient database errors. Test the boundaries with real PostgreSQL and follow each rejected report with a normal report.

### threat-r1 07 — MAJOR — C11

**The acceptance check reads log order as if it were database commit order.** The server logs after the event transaction returns and after its locks are released. The stack check asserts the exact ordered sequence of the relevant log lines. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:479`, `.plans/plans/go-s3-server-machines/plan.md:486`, `src/server/internal/store/pool.go:338` and `deploy/test/checks.sh:540`, `deploy/test/checks.sh:583`.

**Failure.** Stream A commits event 41 and pauses before logging it. Its replacement commits and logs event 42 before A resumes. The durable state is correct, but the gate can fail because it reads 42 before 41. A crash after commit and before logging can permanently omit the line for a committed report.

**Change.** Drive the gate from durable transaction evidence that records each tested sequence and effect in commit order, with the receipt and replay path exercised across a restart. Retain the logs to corroborate the transaction evidence.

### threat-r1 08 — MAJOR — R9

**The enrollment handoff exposes the live token outside the server's storage controls.** The server stores only a verifier. The installer places the raw token in process arguments, and the existing Machines dialog puts it in a command that can enter shell history. The contract's token-input decision remains open. The inherited web guard only specifies `Cache-Control: no-store` for the Session procedures. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:252`, `.plans/plans/go-s3-server-machines/plan.md:560`, `.plans/plans/go-s3-stack-client/plan.md:239`, `src/frontend/src/screens/service.tsx:410`, `.plans/plans/go-s0-contract/plan.md:148` and `.plans/plans/go-s2-server-signin/plan.md:294`.

**Failure.** On a host that exposes process arguments to another user, an unfinished join reveals an unused bearer token during the handoff. A copy in shell history can outlive the command. A recipient who obtains it before the legitimate redemption can register a different waiting key. Owner approval still applies.

**Change.** Have the owner resolve the token-input choice before freezing the joint enrollment flow. Specify a private standard-input or non-echoing prompt path for the installer and page, and prevent caching of the token reply at the server. Check that process arguments, shell traces, logs, errors and persisted responses contain no raw secret on the selected path.

### threat-r1 09 — MINOR — C7

**A scan is allowed during the joining state.** The web contract describes scanning an online client. The plan projects an approved stream with fewer than both accepted reports as joining, but accepts a scan with any approved presence. Evidence is in `src/contracts/proto/lgtm/v1/clients.proto:31` and `.plans/plans/go-s3-server-machines/plan.md:541`, `.plans/plans/go-s3-server-machines/plan.md:574`.

**Failure.** An authenticated request to scan reaches an approved machine immediately after `Welcome`, while the machine is still joining. The server enqueues work before the contract's readiness condition. Restart has the distinct contract condition of being connected.

**Change.** Require both readiness flags and an unexpired current connection for `ScanClientHarnesses`. Keep the connected condition for restart and test the joining case for both calls.

### threat-r1 10 — MINOR — C5

**The server reads a replay field the contract says to ignore.** The plan validates every host name before entering redemption. The contract allows a same-key replay to return the first answer without reading that host name. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:268`, `.plans/plans/go-s3-server-machines/plan.md:272` and `src/contracts/proto/lgtm/link/v1/link.proto:75`.

**Failure.** A join commits, its reply is lost, and a retry with the same token and key supplies a host name over the length limit. The handler returns `invalid_argument` before it can return the original identifier, even though the existing record would remain untouched.

**Change.** Agree with the Contract team on the precedence between general value validation and replay. Preserve decoding and validation of the token identifier, secret and key before redemption. If the replay rule takes precedence as written, validate the host name only before creating a new machine, and test the overlong-host replay.

## Answers to the attack questions

1. The website crosses the origin and session guards and its watch is reauthorized. A machine crosses the token verifier and then fresh key proof. Settings and the stack supply the listener and signing identity. PostgreSQL holds durable claims, with machine locks and input rules at each write. The remaining boundaries are the cleartext route, the result's machine ownership and the translation of wire data into database values. Evidence is in `.plans/plans/go-s2-server-signin/plan.md:288` and `.plans/plans/go-s3-server-machines/plan.md:120`, `.plans/plans/go-s3-server-machines/plan.md:340`, `.plans/plans/go-s3-server-machines/plan.md:542`.
2. The server creates the 32-byte join secret and returns it only from token creation or the token command. PostgreSQL and the feed hold a verifier or identifiers. The client presents the secret in `Join`, with the argument and transport exposures above. The enrollment key is created on the client in a user-only file, and only its public key goes to the server. The server signing seed is created and kept in OpenBao, loaded into process memory, and exposed only as a public key or signature. The server creates the connection token in memory, sends it once to the approved stream, and stores no copy. Sign-in owns the password, derived binding and session cookie. It stores only verifiers and passes the verified session digest to these handlers. Database and vault credentials are inherited from the protected stack files. The plan excludes tokens, nonces and signatures from logs, and public pins and identifiers are safe to store. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:167`, `.plans/plans/go-s3-server-machines/plan.md:252`, `.plans/plans/go-s3-server-machines/plan.md:336`, `src/client/internal/enroll/credential.go:77` and `.plans/plans/go-s2-server-signin/plan.md:294`, `.plans/plans/go-s2-server-signin/plan.md:417`, `.plans/plans/go-s2-server-signin/plan.md:446`.
3. A join token expires in 15 minutes, binds on first use, can be revoked, and is pruned 24 hours after expiry unless a waiting record still needs it. Revoking a waiting machine's token removes that machine. An approved machine's authority ends on removal. The client keeps its local key until the user removes or replaces the local state. A connection token ends with its stream and has no accepting call this wave. Sign-out, session expiry and password changes are inherited from sign-in. Key rotation is deferred. The sign-in plan fails startup if the stored server pin and vault key diverge, so any later recovery procedure must restore that invariant before reenrollment. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:252`, `.plans/plans/go-s3-server-machines/plan.md:254`, `.plans/plans/go-s3-server-machines/plan.md:562`, `.plans/plans/go-s3-stack-client/plan.md:237` and `.plans/plans/go-s2-server-signin/plan.md:456`.
4. The design allows plaintext loopback and requires pinned Hypertext Transfer Protocol Secure for other addresses. It also specifies a machine certificate. Wave 1 proposes loopback and a private cleartext proxy hop with signed proofs, and has no certificate. OpenBao encrypts the server seed at rest, the join secret is represented by its verifier, and the local machine key is protected by file ownership and permissions. PostgreSQL machine metadata is ordinary database data. Issue 1633 and the contract's transport choice still need the explicit custody of both hops in finding 01. Evidence is in `docs/issues.md:7520`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:215`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:316` and `.plans/plans/go-s2-stack-web/plan.md:155`.
5. Nothing found for a new dependency or image. This plan reuses the standard library, Connect, Protocol Buffers and the PostgreSQL stack. The module versions and existing PostgreSQL and OpenBao image digests are pinned. The Stack plan requires digest-pinned bases for the server and web images. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:658`, `go.mod:10`, `deploy/compose.yaml:3` and `.plans/plans/go-s2-stack-web/plan.md:137`, `.plans/plans/go-s2-stack-web/plan.md:190`.
6. A waiting machine can supply its displayed host name and presence, and under the provisional policy it can advance its own event cursor without applying facts or harnesses. It gets no work or side-call token. The website's origin and cookie guards protect owner actions. Treat all self-reported strings as text and only use forwarding headers from the actual proxy. A local process outside that trust boundary raises findings 01 and 08, and another approved machine's command result is covered by finding 02. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:340`, `.plans/plans/go-s3-server-machines/plan.md:458`, `.plans/plans/go-s3-server-machines/plan.md:483` and `.plans/plans/go-s2-server-signin/plan.md:290`.
7. The post-build checks below exercise the deployed transport, credential custody, supersession, command receipts, durable acknowledgement, session revocation and the website's actual presence timing.
a. A different key cannot redeem a used token. An expired or revoked token is refused before same-key replay, and an eligible replay returns the original machine without another write. A fresh challenge defeats a recorded proof, and an unknown machine or bad signature gets no admission. A second valid stream wins the database lock and blocks older writes, with the stale registration and removal gap in finding 04 and the transport boundary in finding 01. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:263`, `.plans/plans/go-s3-server-machines/plan.md:336`, `.plans/plans/go-s3-server-machines/plan.md:361`.
b. Claim commits before send. A resend may use a new attempt and the client's durable receipt is what prevents repeated effects. An expired command can intentionally go unrun, and an interrupted action has an unknown effect. Findings 02 and 05 cover unintended loss of delivery or outcome. For events, effect and mark commit together before acknowledgement. Repeated numbers have no effect, a gap advances nothing and the next welcome recovers the durable prefix across restart. Findings 06 and 07 cover input and acceptance evidence gaps. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:385`, `.plans/plans/go-s3-server-machines/plan.md:458`, `.plans/plans/go-s3-server-machines/plan.md:479` and `.plans/plans/go-s3-client-link/plan.md:168`, `.plans/plans/go-s3-client-link/plan.md:244`.
c. A prompt disconnect removes presence, and a new stream becomes online after both fresh approved reports. The 10-second heartbeat and 30-second limit are present, with no end-to-end deadline guarantee under finding 03. An older stream's late disconnect cannot clear the newer row. The three link drafts match the checked-in Protocol Buffers files byte for byte. The generated Go contract exposes `Welcome.state`, `last_event_number`, `server_time`, `EventAck.through`, three command-result fields and `WatchClientsResponse.position`. The shapes line up. Findings 02, 09 and 10 concern behavioral differences. The waiting report policy, transport decision and website restart handoff remain open in the contract plan. Evidence is in `.plans/plans/go-s3-server-machines/plan.md:337`, `.plans/plans/go-s3-server-machines/plan.md:541`, `src/contracts/gen/go/lgtm/link/v1/link.pb.go:762`, `src/contracts/gen/go/lgtm/link/v1/commands.pb.go:354`, `src/contracts/gen/go/lgtm/v1/clients.pb.go:449` and `.plans/plans/go-s0-contract/plan.md:120`.

## Post-build checks

- **PB1. Enrollment credentials and proof on the deployed route.** Run the contracted Connect and Google Remote Procedure Call (gRPC) clients through the real proxy. Check that an unintended listener receives no credential under the chosen trust policy and that an unexpected certificate or signing key yields no enrollment or admitted stream. Check that an old proof fails against a fresh challenge. Inspect token-bearing response cache headers, installer arguments, logs, errors, database rows and feed rows using test credentials. Expect only the selected credential sinks to contain the raw value.
- **PB2. Token and session races.** Race same-key and different-key join attempts across expiry and revocation. Require one waiting record, the original reply for an eligible same-key replay and the documented refusal for other attempts. With an open Machines watch, sign out or replace the password while publishing a machine change. Require no update authorized after the session revocation and verify that an unlisted web origin is refused before dispatch.
- **PB3. Admission, removal and presence.** Hold the older handler after admission, let a replacement sign in and disconnect, and release the older one. Expect a supersession refusal and no stale welcome. Remove a machine while the hub feed is behind and expect the documented removal reason. Stall writes and fail the first cleanup after a missed heartbeat. Observe the actual Machines watch going offline within 30 seconds and returning online after both fresh reports. Require an older stream's late cleanup to leave the newer one intact.
- **PB4. Command ownership and retries.** Present a result for a different machine's command and then present a result on a replacement stream before the command is claimed there. Require no outcome change. Drop a legitimate result, then restart the server or client with the same durable stores. Require the next attempt to close once with the recorded outcome or the documented interruption, with no second action. Verify the server retry cutoff and retained receipts near expiry plus 24 hours, including with a skewed client wall clock.
- **PB5. Event durability and replay.** Fail the database commit and require no acknowledgement for that event. Commit the event and drop its acknowledgement, then reconnect after restarting each process in turn. Require the durable mark to recover the committed prefix and each effect to appear once in order. Include a decoded report that cannot be represented downstream and a later normal report to verify the agreed consume rule.
- **PB6. Waiting and projected values.** Send the reports, heartbeats and results that the chosen waiting policy covers. Require no unauthorized facts, harnesses, connection token or work. Approve on the original stream and require joining followed by online. Confirm that forged forwarded values from an untrusted peer are ignored, and that machine-supplied text is displayed as text.
