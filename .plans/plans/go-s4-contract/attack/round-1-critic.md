REVISE

The planner, test writers, builders, and this reviewer all use OpenAI. The review is from the same vendor.

**Top finding.** The proposed admission refusal can leave a machine with a rolled-back event buffer retrying indefinitely without showing the owner how to recover it.

## Findings

### critic-r1 1. A rollback can hide the recovery message

**MAJOR · C11 · Design · Server Link and Client Folders.** Evidence by reading. Risk score 72 (severity 6 because the machine needs manual recovery, fallout 3 because the owner can recover or enroll it again, probability 4 for a rollback during a pending operation).

The plan promises a local stop for incompatible history, then requires admission to return the ordinary retryable `invalid_argument` when the new first number overlaps the server mark or a waiting watermark. The current client reaches the local history check only after Welcome. It discards unrecognized refusal details and retries ordinary invalid arguments. See `.plans/plans/go-s4-contract/plan.md:149`, `.plans/plans/go-s4-contract/plan.md:151`, `src/client/internal/link/session.go:147`, `src/client/internal/link/session.go:477`, `src/client/internal/link/conn.go:206`, `src/client/internal/link/conn.go:241`, and `src/client/internal/link/retry.go:42`.

For example, the server has applied event 10 and holds a result waiting for 12. The owner restores a structurally valid client backup whose next number is 11. The server detects the conflict, but the client receives no Welcome and cannot derive it locally. The owner sees an offline machine and folder requests that keep timing out.

Define a distinguishable, authenticated history-conflict refusal after proof. Have the client route that refusal to the local recovery message and retain ordinary retry for other invalid arguments. Pin the refusal in the contract, the name table, and the two dependent plans. Test mark 10, waiting watermark 12, and announced first number 11. Expect one recovery message, no command admission, and no change to the result or mark. Then test restoration of the real prefix and, separately, removal.

### critic-r1 2. Add to a machine has no agreed remote comparison

**MAJOR · R6 · Design · Contract and Server Projects.** Evidence by reading. Risk score 108 (severity 6 because an allowed attachment can fail until the owner changes configuration, fallout 3 because the owner can adjust the remote, probability 6 for attaching a checkout configured independently).

The design requires one normal form for two present remotes. The plan repeats that requirement and defines when the first commit may be used, but it does not specify the normal form or identify a normative implementation. A test writer cannot derive an expected result when two sanitized origins differ only in the case of a host name, or when one URL ends in `.git`. Projects could make either decision and the item's descriptor tests would pass. See `docs/specs/2026-11-27-running-an-agent-design.md:204`, `docs/specs/2026-11-27-running-an-agent-design.md:292`, `.plans/plans/go-s4-contract/plan.md:199`, `.plans/plans/go-s4-contract/plan.md:225`, and `.foundry/go-rewrite/results/plan-go-s4-contract.md:42`.

Give Projects an exact comparison rule and examples before the handoff. State which parts of the origin are significant, which Git address spellings compare equal, and what happens to an unparseable address. Put at least one equivalent pair and one different pair with the same first commit in the Projects test handoff. Derive the expected attach or refusal from this comparison.

### critic-r1 4. Retried state commands need an explicit receipt rule

**MINOR · R6 · Design · Contract and Client Folders.** Evidence by reading. Risk score 36 (severity 6 because the wrong fence can hold a state command, fallout 3 because it is confined to the machine, probability 2 because this case combines a lost reply and newer buffered events).

The plan preserves the `SetState` expiry exception and says all results replay their saved watermark. The built client applies `SetState` and replies before reaching the receipt path. If the first state reply at watermark 9 is lost and watermark 10 is buffered before a resend, retaining the existing fast path can recompute the result at 10. That makes a previously completed state command depend on a later event. See `.plans/plans/go-s4-contract/plan.md:139`, `.plans/plans/go-s4-contract/plan.md:145`, `src/client/internal/link/commands.go:141`, and `src/client/internal/link/commands.go:179`.

State whether `SetState` persists a revision 2 result watermark or has a separate explicit rule. Under the design's all-result rule, require the saved watermark and keep the expiry exception. Add the lost-reply case to the client handoff and check that the second attempt carries the original watermark.
