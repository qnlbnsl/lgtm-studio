# Decisions — go-hist-server

| id | question | decision | rationale | status | date |
|---|---|---|---|---|---|
| 1 | How is this plan sized? | Use tier M and four Server work items. | The bounded Server assignment of 2026-11-28 calls for two to six work items and tier M when there is more than one. | closed | 2026-11-28 |
| 2 | Which changes belong in the Server plan? | Build admission and mark reconciliation, command and folder settlement, failed-request publication, and warning removal inside `src/server/`. Contract owns generated types. Client owns its disk and replay. Website owns the bell, field 19 reservation and paired history tests. | The owner approved the split in the history design on 2026-11-28. The task and the shared names table fix the order and owners. | closed | 2026-11-28 |
| 3 | Which run checks apply? | Assume that existing supersession and immutable-pair checks still apply. For an unseen run, keep the existing staged and pending fences in the fit case when its first number exceeds the mark. Bypass those fences for an unseen first at or below the mark and while applying either reconciliation branch. A run becomes ready when the mark covers first minus one. | The history design admits unseen runs at or below the mark and explicitly drops the old pending fence on reset. It otherwise preserves replay and the run's own ordering. This reading gives both mismatch branches a path and retains the existing normal-path fence controls. | unanswered | 2026-11-28 |
| 4 | What value range can the server store? | Assume that first is between 1 and 2^63 inclusive and acknowledged and last are between 0 and 2^63−1 inclusive. Use first minus one to check the relation to last. Keep the old nonwrapping limit. | The revision 2 boundary in `link.proto`, the event and result checks, and the PostgreSQL bigint mark agree on these bounds. The new history numbers describe stored events. | unanswered | 2026-11-28 |
| 5 | What counts as handoff when the transport and database disagree? | Assume the earliest durable evidence of possible transport handoff counts. Commit one sticky bit just before the first eligible send and recheck the send fence before calling transport. Treat the gap between that marker and a definitive send as uncertain. A claim alone is insufficient. | The server can lose the dispatch commit after transport wrote the frame. Reassignment also clears the latest dispatch flag. A second execution, especially a restart, is more harmful than a reported failure where the started handoff could not be confirmed. | unanswered | 2026-11-28 |
| 6 | How are command results selected and ordered? | In the reset, first settle staged results with their original outcome and watermark in watermark and sequence order. Then settle handed-over, pending, unstaged non-standing commands in command sequence order. Keep result-free SetState and never-handed commands pending. In a raise, settle the stages at or below the new mark, and leave the other stages and commands pending. | The owner decided the included and excluded command classes on 2026-11-28 in the history design, under both server reconciliation sections. The order within those classes follows existing Link settlement and removal patterns. | closed | 2026-11-28 |
| 7 | Where does reconciliation run and where is it logged? | Assume that settlement follows connection storage and precedes admission and ready callbacks in the same write. Log once for each successfully confirmed reconciliation admission, before attempting its Welcome. Leave ambiguous commits on the existing Hub error path. | Settlement and callbacks must share the write. This order lets a callback observe the new connection and settled ledger. A process can confirm neither the log nor the write when a commit reply disappears. | unanswered | 2026-11-28 |
| 8 | What does the website call see for a lost folder report? | Assume that a history-restored folder command maps to the existing stored `no_answer` failure and its fixed Connect error. Keep original outcome mappings for staged results. The open-state predicate keeps applied replies and the never-handed command remains available to finish its call. | The design requires a caller-visible failure and leaves the error wording to the server. The missing-report error already reaches both folder call paths. | unanswered | 2026-11-28 |
| 9 | How does the list leave the watch? | Assume a nullable deadline belongs to the existing command record. Set it for a reset-failed scan or restart. Clear it on a later committed enqueue of the same kind, on machine removal, or at expiry. A request queued before the failure and a replayed request key leave it alone. Use actual database time for the list and a one-second publication poll. | This keeps the list and its deadline reconstructible after restart. Clearing a deadline makes departure publication repeatable and keeps the terminal ledger outcome for the normal retention period. | unanswered | 2026-11-28 |
| 10 | Where is the schema changed? | Put the new command fields and the warning removal in numbered schema change 0003. Preserve the revision 1 files. Use the new schema for fresh databases, with no backfill or dual-read path. | The owner specified in the bounded 2026-11-28 history assignment that these files have not shipped and that database changes are plain schema edits. | closed | 2026-11-28 |
| 11 | How are the standalone and paired gates staged? | Assume the standalone whole-tree Go gate runs with the database variable unset, plus a separate all-Server PostgreSQL pass. Run the full PostgreSQL Go gate when the Website plan has replaced its old-rule paired tests. | The earlier paired tests directly query the removed column, send old Hello ranges, and depend on the prior client rule. Both owners' server and client outputs are needed for the paired proofs. | unanswered | 2026-11-28 |
| 12 | Who supplies the seats? | Use one vendor for the planner, test writers, builders and code reviewers of this plan. | The 2026-11-28 bounded task gives this allocation for the history plans. Its per-plan rule supersedes the older epic allocation. | closed | 2026-11-28 |
| 13 | How are equal failure times ordered and is the lifetime testable? | Assume newest failure first, with descending command sequence for ties. Store the deadline on the command using the same clock sample as its finish. Make duration a private State setting initialized before workers start, with ten minutes as the default. | The contract carries one entry per command and does not prescribe order. The existing State offers a construction boundary for a deterministic test setting. | unanswered | 2026-11-28 |
