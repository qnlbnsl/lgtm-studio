REVISE

The Projects and Link plans specify incompatible callback interfaces, so the startup wiring for folder reports, settlement, and machine removal cannot compile as written.

The planner, test writers, builders, and this reviewer are all OpenAI workers. The evidence below is from the plans and source read at commit `2611b0bd`.

## Findings

### threat-r1 01 — BLOCKER — The Link registration contracts disagree

**Statement** R3, the foundation rule for Go interfaces. **Category** Design. **Evidence status** Confirmed by reading. **Owner** Server Link and Projects. **Risk score** Required build gate.

The Projects handoff proposes a `RegisterPart` with no return value, a callback that receives a `FolderSeen` message, and a settlement callback with three strings. Link item 1 defines `RegisterPart(PartHooks) error`, routes reports by kind with a full `Event`, and routes command settlement with a typed `Settlement`. The enqueue and machine-removal argument lists agree. See `.foundry/go-rewrite/results/plan-go-s4-server-projects.md:43–58`, `.plans/plans/go-s4-server-projects/plan.md:112`, `.plans/plans/go-s4-server-projects/plan.md:209`, and `.plans/plans/go-s4-server-link/plan.md:78–128`.

When startup instantiates the Projects handoff literal against Link's `PartHooks`, the named fields and two callback types fail to compile. Changing Link to the proposed Projects shape would invalidate Link's frozen registration assertions for keyed routes, duplicate rejection, and registration errors.

Use Link's keyed `ReportApplied` and `CommandSettled` maps and `MachineRemoved` field. In Projects, unwrap the folder arm from the `Event` and take the machine, stored command identifier, and typed outcome from `Settlement`. Propagate registration errors before any worker or listener starts. Freeze the adapter and actual startup tests against the same published signatures.

### threat-r1 02 — BLOCKER — Held receipts need a Store build item and a frozen migration test decision

**Statement** R7, the foundation rule for durable state. **Category** Design and integrity. **Evidence status** Confirmed by reading. **Owner** Server Store through the orchestrator. **Risk score** Required build gate.

The Projects result specifies `WriteOnceRetained`, `RetireReceipt`, and `0002_held_receipts.sql`, with ownership left to the orchestrator. Items 2 and 3 assume those methods exist. Store currently supplies `WriteOnce` and ordinary pruning. Its startup automatically loads every built-in migration, and existing tests assert that the resulting Store ledger equals version 1. See `.foundry/go-rewrite/results/plan-go-s4-server-projects.md:22–39`, `.plans/plans/go-s4-server-projects/plan.md:91–108`, `src/server/internal/store/receipts.go:41–48`, `src/server/internal/store/prune.go:63–77`, `src/server/internal/store/migrate.go:63–69`, and `src/server/internal/store/migrate_test.go:173`, `:233`, `:367`, `:381`, and `:441`.

If Projects starts without Store, the two work items lack their required methods. If Store adds the requested migration as written, its mandatory migration suite reads Store version 2 and fails the frozen version 1 assertions.

Assign and review a Store work item before dispatching Projects items 2 and 3. Include the two methods, the additive migration, and the precise existing assertions that need a reviewed fixture change. Preserve the concurrency and rollback assertions. Prove that a version 1 database upgrades to version 2 with its ordinary receipts intact. Freeze separate Store cases for shared key conflicts, held pruning, and the compare-and-delete rollback.

### threat-r1 03 — MAJOR — Large machine removals always roll back

**Statement** R4, the foundation rule for transactional writes and change references. **Category** Integrity and design. **Evidence status** Confirmed by reading. **Owner** Projects and Store. **Risk score** 120, schedule. Severity 6 for a core removal that stays broken, fallout 5 for repair requiring support, and probability 4 for an unusually large saved set.

Item 6 emits one Projects feed reference per affected repository inside the same removal write. Store rejects the 257th reference and rolls back the entire write even if the callback ignores the error. Machines contributes its own reference. Link's plan flags the cap, and the Projects handoff gives it no mechanism. See `.plans/plans/go-s4-server-projects/plan.md:165–169`, `.plans/plans/go-s4-server-link/plan.md:254`, `src/server/internal/machines/store.go:222–224`, and `src/server/internal/store/feed.go:70–87` and `:110–118`.

A machine can accumulate 257 separate saved repositories through successful adds. Removal then fails on every retry with the same membership. Its registry and folder rows remain. An operation held by a staged result with missing history can also stay open, because removal is its remaining recovery action. See `.plans/plans/go-s4-server-link/plan.md:230–232`.

Give Store and Projects an explicit bulk recording path that commits all removal changes and their feed references together in commit order. Preserve the existing limit for ordinary `Tx.Record`. Freeze a PostgreSQL removal test above that limit, with sole and shared repositories and an open operation. Require successful cleanup and the committed watch changes. Keep the test that rolls back everything on an injected storage failure. See `src/server/internal/store/feed_test.go:405–444`.

### threat-r1 04 — MAJOR — Client-side credential filtering runs after raw typed-path storage

**Statement** R9, the foundation rule for secret handling. **Category** Confidentiality. **Evidence status** Confirmed by reading for the ordering. **Owner** Projects, Server Link, and the paired-program owner. **Risk score** 28, record. Severity 4 for temporary recoverable credential material in the live ledger, fallout 7 if a copy exposes it, and probability 1 for a matching credential in the input combined with access to the store.

Projects puts the exact website path in the persisted Link command before any client check. Client Folders screens the typed and expanded paths after receipt. The reviewed contract asks the joint check to assert that planted credentials in paths do not appear in server records. The foundation puts server secrets outside ordinary application tables. See `.plans/plans/go-s4-server-projects/plan.md:87` and `:94–99`, `.plans/plans/go-s4-client-folders/plan.md:198–204`, `.plans/plans/go-s4-contract/plan.md:300`, `docs/specs/2026-11-25-go-rewrite-foundation-design.md:215–227`, and `src/server/internal/link/outbox.go:21–42`.

If an owner submits a checkout path containing a value the client recognizes as a credential, the pending command already contains the value when the client refuses it. The value can persist across restart or while a result is staged. Removing the active payload at settlement leaves the earlier storage window. See `.plans/plans/go-s4-server-link/plan.md:230–231` and `src/server/internal/link/outbox_result.go:26–35`.

Specify protection for the durable typed path before the command commits, with decryption inside Link for delivery and key material kept outside the application database. Preserve exact path bytes at delivery and clear the protected payload on settlement or removal. Assign the joint credential proof to a named paired test. Use a synthetic known value in the typed path and then in a resolved-path alias case. Inspect the pending ledger before delivery, the terminal operation, client and server logs, and the website reply. If plaintext command storage is an accepted boundary, record that decision and narrow the reviewed no-credential assertion explicitly before freezing tests.

### threat-r1 06 — MAJOR — The watch-lag fixture cannot commit

**Statement** R5, the foundation rule for shared watches. **Category** Design. **Evidence status** Confirmed by reading. **Owner** Projects watch test writer. **Risk score** Required test gate.

`TestProjectWatchLagAndReopen` requires more than 2,048 committed references in one Store write. Store allows 256 per write. The follower cuts off a subscriber at 2,048 unacknowledged references. See `.plans/plans/go-s4-server-projects/plan.md:203`, `src/server/internal/store/feed.go:13–17` and `:70–87`, and `src/server/internal/store/follow.go:10–11` and `:196–202`.

The fixture's first over-limit write rolls back. The watch never moves 2,048 positions behind, so the required closure assertion cannot pass on a correct implementation.

Keep the send barrier and commit the references in several legal writes through Store. Observe the follower at 2,047 positions without lag closure, then commit one more reference and require `aborted`. Reopen and check a positioned replacement snapshot. Keep the ordinary Store limit test intact.

### threat-r1 07 — MINOR — The new website handlers have no pre-decode body budget

**Statement** `plan`. **Category** Availability and design. **Evidence status** Confirmed by reading. **Owner** Projects router. **Risk score** 24, record. Severity 4 for transient resource pressure, fallout 3 for recovery by the application or operator, and probability 2 for an unusually large signed-in submission.

The plan checks the 4,096-byte path only after request decoding. Its registration lists the protocol, session gate, redaction codec, and write deadline. The pinned Connect version defaults to an unlimited message size, and the current application limits the time to read headers. Existing Session and Link handlers already set a per-message cap. See `.plans/plans/go-s4-server-projects/plan.md:94` and `:205–211`, `go.mod:11`, `src/server/internal/api/server.go:129–159`, and `src/server/internal/app/start.go:292–304`.

An oversized body from a signed-in client can use server memory before the path validation or fixed malformed-body response runs. A path limit in the method leaves that allocation unbounded.

Set a Projects transport read cap before decoding, large enough for a maximum-length legal path represented as escaped JavaScript Object Notation (JSON). Freeze tests for over-cap plain and compressed bodies and for a maximum-length valid path. Verify the oversized transport refusal creates no operation or command and retains the existing origin and session precedence.

## Answers to the attack questions

1. The website supplies its session cookie, request key, machine, typed path, and optional target. The origin gate, session gate, request validation, and retained receipt protect that boundary. Link checks the signed current stream and approval, and Projects checks both correlation identifiers, field presence, text budgets, and remote form. PostgreSQL supplies the durable rows and the clock. Projects assumes the Store transaction and private deployment boundaries. Findings 02, 04, and 07 cover the gaps.
2. Projects introduces no credential issuer or credential file. Auth makes the cookie token, sends it to the browser, stores its verifier and password binding, and passes only the verifier to the watch in memory.
