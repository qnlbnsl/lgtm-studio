| 7 | What does a credential-returning call do with a request key? | Assume that SignIn refuses a present `Lgtm-Request-Key` with `invalid_argument`. The same rule is proposed for the later join-token issue call. After a lost SignIn reply, the owner signs in again and the earlier session can expire or be evicted. Assume that SignOut refuses a key after authenticating the caller, because replay loses the credential needed for authorization. GetServer ignores a request key. | The assignment supplies the orchestrator's provisional reading. The password, token and password-derived material stay out of receipts. | unanswered | 2026-11-26 |
| 8 | How does a session fit the existing store? | Assume one `auth` migration with the four columns the design names. The verifier is the row key. Store only a one-way, domain-separated reference in the feed. Serialize auth mutations with a transaction-scoped lock on the auth table. Read verified sessions from the primary database. | The foundation design approved on 2026-11-25 specifies verifier-only session rows and store-owned transactions. The lock prevents a ninth active row and makes insertion order deterministic under contention. | unanswered | 2026-11-26 |
| 9 | Which sessions does a credential change or removal end? | A change removes the stored web sessions together. Missing, empty or invalid `LGTM_WEB_PASSWORD` clears the same set before returning a startup error if PostgreSQL is reachable. The deletion covers web sessions only. The auth feed, migration ledger, machine records, join tokens, retry receipts and OpenBao data have their own retention or management rules. Assume a failed cleanup is reported explicitly and that the operator retries removal with PostgreSQL available before restoring the former password. | The owner approved restart persistence and revocation on change or removal on 2026-11-25 in the foundation design. A process that cannot write to PostgreSQL cannot durably record password removal. The design keeps durable state in PostgreSQL. | unanswered | 2026-11-26 |
| 10 | How are the password and row binding represented? | Assume a password has 1 to 4096 UTF-8 bytes and is used exactly as supplied. Compare fixed digests in constant time. Use an independent salt and the design's scrypt parameters to authenticate the row's verifier and creation time. Encode new tokens as unpadded URL-safe base64 of 32 random bytes. Use a 720-hour lifetime from database time. | The old engine supplies an input bound and a salted memory-hard binding. The 2026-11-25 design rules out import, so the Go code has its own byte layout and does not copy source. | unanswered | 2026-11-26 |
| 11 | Which origins and cookies does the transport accept? | Assume a configured public origin and an exact list of additional origins. Same-site comparison uses scheme and registrable domain, or an exact host when there is no registrable domain. Use the configured public scheme for `Secure`. Use a host-only `lgtm_session` cookie. Require HTTPS on both sides of a cross-site request. Native requests with no browser origin can use the public-origin policy. | The design of 2026-11-25 requires a credentialed allowlist and different cookie modes. Site comparison needs a public suffix list. Browser policy can still suppress a cross-site cookie. | unanswered | 2026-11-26 |
| 12 | What are the startup and listener contracts? | Assume one process serves at a time. Use the configuration names and defaults in item 1, a private listener under the Stack proxy, one empty `GET /healthz` response on readiness, and a bounded startup that exits nonzero on prerequisite failure. Reconcile sessions before approaching OpenBao or opening the listener. | This provides the Stack team's missing settings and meets the startup ordering in the brief. The proxy is the public issuer of the browser's origin and scheme. | unanswered | 2026-11-26 |
| 13 | How does the vault client handle initialization and errors? | Assume strict reading of the mounted credential, one lease-aware AppRole client, create-only compare-and-set, and a final read of the persisted seed before using it. The process exits when the key cannot be read or confirmed. Assume the public log fingerprint is lowercase hexadecimal SHA-256 of the raw Ed25519 public key. | This preserves the key across startup and competing first calls. The Stack plan supplies the path, seed field, credential layout and lease. C13 observes the public fingerprint. | unanswered | 2026-11-26 |
| 14 | How does a Go test start and restart the server? | Assume the exact `servertest` surface in item 9. Use real PostgreSQL.
