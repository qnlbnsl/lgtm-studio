| 13 | How is a file written so that a crash leaves no half-written file? | A temporary file in the same folder is written and synced, then renamed over the final name, then the folder is synced. | 14 | What does the outbox do when it is full (point 1 of the brief)? | It refuses the new event with `ErrOutboxFull` and changes nothing. It never drops an old event. | The design says that no event is lost. Dropping the oldest would lose an event and leave a gap in the numbers. | 15 | How much may the outbox hold, and how often is it flushed (point 2 of the brief)? | At most 10,000 events and 64 mebibytes of payload, and at most 1 mebibyte for one event. The limits are the planner's assumption and are options of `OpenOutbox`. | unanswered | 2026-11-26 |
| 16 | How does the outbox store its events? | One file for each event, named by its number, and one file `acked` that holds the highest acknowledged number. | Each file is written by the safe method of row 13, so a crash leaves each event whole or absent. | 17 | What does an acknowledgement mean? | It is cumulative: `Ack(n)` acknowledges every event up to `n`. An acknowledgement beyond the next number moves the counter, so the next event gets `n + 1`. | The design says the server remembers the last number it applied. If a client lost its outbox folder, the server's number lets it continue without having its new events dropped. This is a request to the Contract team, written in the result file. | closed | 2026-11-26 |
| 18 | Does every message that travels up go through the outbox? | No. The outbox holds opaque bytes, and plan `go-s3-client-link` decides which messages are events. Heartbeats are live state and are not buffered. | The outbox then needs no generated contract code, so this plan depends on plan `go-s0-contract` only for `go.mod`, as the task says. | closed | 2026-11-26 |
| 19 | What does "runs once" mean when the client stops in the middle of a command? | At most once. A receipt marked `started` is written to disk before the command runs. After a restart, every `started` receipt becomes `interrupted`, and the command is not run again. | The design says that a command that arrives twice runs once. Running it again after a crash could run it twice. The server can send a new command with a new identifier. | closed | 2026-11-26 |
| 20 | How long is a receipt kept? | Until 24 hours after the latest of its expiry, its start and its finish. | A command past its expiry is never run, so a later copy needs no receipt. The margin covers a server whose clock is ahead of the client's. Assumption: 24 hours is enough. | unanswered | 2026-11-26 |
| 21 | Which clock decides that a command is past its expiry? | The client's clock, through a function that `OpenReceipts` takes as an option. | The design does not say. The server sets the expiry, so a client clock that is far behind would run a command late. Assumption: plan `go-s3-client-link` sets expiries with a margin, and it may pass a clock corrected by the server's time. | unanswered | 2026-11-26 |
| 22 | What identifier of a command does the client accept? | Only the canonical lowercase text of a universally unique identifier (UUID), 36 characters. | 23 | How is the load of the processor read on macOS without a shell command (point 3 of the brief)? | Through `syscall.Sysctl("vm.loadavg")`. Memory on macOS is `100 - kern.memorystatus_level`. | The design asks for the load and gives no formula. macOS gives no busy time of the processor without a system library call that needs C. Assumption: the formula is close enough for the Machines page, and it is checked on a Mac before sprint 3 ends. | unanswered | 2026-11-26 |
| 24 | Does this plan need a module outside the standard library? | No. Everything it needs is in the standard library of Go. | `go.mod` belongs to the Contract team. A new module would be a request to that team and a wait. | closed | 2026-11-26 |
| 25 | Where do the receipts of commands live (point 4 of the brief)? | In `src/client/internal/link/receipts.go`. | 40 | What may an acknowledgement and a number from the server do? | `Ack(n)` acknowledges only numbers the outbox handed out, and returns `ErrAckAhead` above them. `Reconcile(n)` checks the server's last applied number once on each connection: below the mark it gives `ErrServerBehind`, inside the pending range it acknowledges, and above it gives `ErrServerAhead`.
