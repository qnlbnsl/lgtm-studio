# Decisions — go-s1-client-local

A row therefore gives the date and the source of a decision of the owner, without the words.

|---|---|---|---|---|---|
| 1 | Which process tier fits this plan? | Tier M. This is the orchestrator's first reading, and the planner confirms it. | It is one program with no network yet. Two items are risky: the private key, and a record that must survive a crash. | closed | 2026-11-25 |
| 2 | What does this plan cover? | The work items of the brief. They are a slice of waves 0 and 1 of the design. | The owner approved the design on 2026-11-25, in the planning session. The owner asked the same day for separate plans for the server and the client, and for smaller work items. | closed | 2026-11-25 |
| 3 | Which process runs this plan? | The build loop in `docs/specs/2026-11-05-build-loop-design.md`. | Decided by the owner on 2026-11-25, in the planning session. | closed | 2026-11-25 |
| 4 | Which harnesses build and review? | A mix of Codex and Claude, and Cursor with Grok as well. | Decided by the owner on 2026-11-25, in the planning session. | closed | 2026-11-25 |
| 5 | Is the cut of wave 1 into three sprints confirmed? | Not yet. The orchestrator made the cut. | It gives each sprint an end that a person can observe. The owner has not ruled on it. | open | 2026-11-25 |
| 6 | Does tier M still fit after scouting? | Yes. Tier M is confirmed. | The plan has eight small work items in one team folder, no screen and no network. Five items are risky, and each has a named mutation. | closed | 2026-11-26 |
| 7 | How are the brief's six work items cut? | Into eight items. The safe writing of files and the state folder become item 2. The outbox is split into its file format (item 6) and its queue (item 7). | The rule of 2026-11-25 asks that a high item first be tried as medium ones. Every item is now medium or low, and each has its own tests. | closed | 2026-11-26 |
| 8 | Where is the state folder when the design's default does not apply? | `LGTM_CLIENT_STATE_DIR` when set, then `$XDG_STATE_HOME/lgtm-client` when that is an absolute path (XDG is the X Desktop Group, whose folder rule this follows), then `$HOME/.local/state/lgtm-client`. The same rule holds on macOS. | The design names only `~/.local/state/lgtm-client/`. The variable lets a test or a second client use another folder. Assumption: the owner accepts the variable and the XDG rule. | unanswered | 2026-11-26 |
| 9 | What files does the state folder hold? | `lock`, `settings.json`, `machine.key`, `server.json`, `outbox/` and `receipts/`. Every file is mode 0600 and every folder is mode 0700. The plan gives each format. `server.json` is reserved for plan `go-s3-client-link`, which owns its fields. | The task asks this plan to fix the layout that `go-s3-client-link` reads. One mode for every file is simpler to check than a mode for each file. | closed | 2026-11-26 |
| 10 | Where do the settings of the client live? | In `settings.json` inside the state folder. A missing file means the defaults. Unknown fields are refused. | The design names one folder for the client. A second folder under `~/.config` would give the installer and a later service user two places to set up. Assumption: one folder is acceptable. | unanswered | 2026-11-26 |
| 11 | What are the default folder for repositories and the default agent limit? | `~/.local/share/lgtm-client/repositories`, and 4 agents. | The design says the facts carry both and gives no value. Clones are data, so the folder sits under the XDG data folder. Assumption: the owner changes them in `settings.json` when needed. | unanswered | 2026-11-26 |
| 12 | Can two clients use one state folder at once? | No. The client holds an exclusive lock on the file `lock` while it runs. A second client refuses to start. | Two writers of one outbox would hand out the same event number twice, and the server would drop one of the two events. | closed | 2026-11-26 |
| 13 | How is a file written so that a crash leaves no half-written file? | A temporary file in the same folder is written and synced, then renamed over the final name, then the folder is synced. A file that must never be replaced, such as the key, is linked to its final name instead of renamed, which fails when the name exists. | A rename and a link are atomic on Linux and macOS. The sync of the file before the rename and of the folder after it make the result survive a loss of power. | closed | 2026-11-26 |
| 14 | What does the outbox do when it is full (point 1 of the brief)? | It refuses the new event with `ErrOutboxFull` and changes nothing. It never drops an old event. | The design says that no event is lost. Dropping the oldest would lose an event and leave a gap in the numbers. The producer of the event decides what to do. | closed | 2026-11-26 |
| 15 | How much may the outbox hold, and how often is it flushed (point 2 of the brief)? | At most 10,000 events and 64 mebibytes of payload, and at most 1 mebibyte for one event. Every event is synced to disk before `Append` returns its number. | An event must be durable before it is sent. Otherwise a crash could hand its number to another event, and the server would drop that event as a repeat. The limits are the planner's assumption and are options of `OpenOutbox`. | unanswered | 2026-11-26 |
| 16 | How does the outbox store its events? | One file for each event, named by its number, and one file `acked` that holds the highest acknowledged number. | Each file is written by the safe method of row 13, so a crash leaves each event whole or absent. A log of segments would be faster and needs recovery of a torn tail. Wave 2 may replace the storage behind the same interface if the rate of events needs it. | closed | 2026-11-26 |
| 17 | What does an acknowledgement mean? | It is cumulative: `Ack(n)` acknowledges every event up to `n`. An acknowledgement beyond the next number moves the counter, so the next event gets `n + 1`. | The design says the server remembers the last number it applied. If a client lost its outbox folder, the server's number lets it continue without having its new events dropped. This is a request to the Contract team, written in the result file. | closed | 2026-11-26 |
| 18 | Does every message that travels up go through the outbox? | No. The outbox holds opaque bytes, and plan `go-s3-client-link` decides which messages are events. Heartbeats are live state and are not buffered. | The outbox then needs no generated contract code, so this plan depends on plan `go-s0-contract` only for `go.mod`, as the task says. | closed | 2026-11-26 |
| 19 | What does "runs once" mean when the client stops in the middle of a command? | At most once. A receipt marked `started` is written to disk before the command runs. After a restart, every `started` receipt becomes `interrupted`, and the command is not run again. | The design says that a command that arrives twice runs once. Running it again after a crash could run it twice. The server can send a new command with a new identifier. | closed | 2026-11-26 |
| 20 | How long is a receipt kept? | Until 24 hours after the latest of its expiry, its start and its finish. | A command past its expiry is never run, so a later copy needs no receipt. The margin covers a server whose clock is ahead of the client's. Assumption: 24 hours is enough. | unanswered | 2026-11-26 |
| 21 | Which clock decides that a command is past its expiry? | The client's clock, through a function that `OpenReceipts` takes as an option. | The design does not say. The server sets the expiry, so a client clock that is far behind would run a command late. Assumption: plan `go-s3-client-link` sets expiries with a margin, and it may pass a clock corrected by the server's time. | unanswered | 2026-11-26 |
| 22 | What identifier of a command does the client accept? | Only the canonical lowercase text of a universally unique identifier (UUID), 36 characters. Anything else is refused with `ErrInvalidCommand`. | The identifier becomes a file name. Rule 9 treats text from outside as data, so a name such as `../machine.key` must never reach the file system. | closed | 2026-11-26 |
| 23 | How is the load of the processor read on macOS without a shell command (point 3 of the brief)? | Through `syscall.Sysctl("vm.loadavg")`. The percentage is the load of the last minute divided by the number of cores, times 100, capped at 100. Linux uses the same formula on `/proc/loadavg`. Memory on macOS is `100 - kern.memorystatus_level`. | The design asks for the load and gives no formula. macOS gives no busy time of the processor without a system library call that needs C. One formula on both systems keeps the website's numbers comparable. Assumption: the formula is close enough for the Machines page, and it is checked on a Mac before sprint 3 ends. | unanswered | 2026-11-26 |
| 24 | Does this plan need a module outside the standard library? | No. Everything it needs is in the standard library of Go. | `go.mod` belongs to the Contract team. A new module would be a request to that team and a wait. | closed | 2026-11-26 |
| 25 | Where do the receipts of commands live (point 4 of the brief)? | In `src/client/internal/link/receipts.go`. The file `commands.go` of the blueprint stays for plan `go-s3-client-link`, which handles the commands. | Keeping the record apart from the handling lets two builders work at the same time, one on each file. | closed | 2026-11-26 |
| 26 | Which programs does the harness scan look for, and when is a harness installed? | `claude`, `codex`, `gemini`, and for Cursor `cursor-agent` and then `agent`. A harness counts as installed only when a program answers `--version` with a version that matches the harness. Only the matched version text is kept. | The old engine used these names. The name `agent` is common, so Cursor's pattern of a date-like version guards against another program of that name. Keeping only the version text keeps any other output, which may hold a secret, out of every report. | closed | 2026-11-26 |
| 27 | How does the scan run a program? | Directly, never through a shell, with the one argument `--version`. The search path holds only absolute folders. The child gets only `PATH`, `HOME` and `LANG=C`. Each program has 3 seconds, and the four harnesses are scanned at the same time. | A shell would read the folder name as code. A relative folder could run a program from the current folder. A child that inherits the client's variables could print a secret. | closed | 2026-11-26 |
| 28 | How does a test fake the installed programs? | It writes small scripts into a temporary folder and passes that folder as the search path. `Scan` reads only the search path it is given, never the real `PATH`. | The tests then never run or change a real harness on the machine. One test proves that an empty search path finds nothing. | closed | 2026-11-26 |
| 29 | Which tests prove that the outbox and the receipts survive a crash in the middle of a write? | Three kinds. A child process of the test is stopped with `SIGKILL` at random moments, and the parent checks the records on disk. A test hook stops a child at each step of a safe write. A recording of the sync calls proves that each file is synced before it is renamed. | A killed process is a real crash. The step hook makes each crash point certain instead of likely. A loss of power cannot be caused in a test, so the order of the syncs is checked instead. | closed | 2026-11-26 |
| 30 | How is "builds for Linux and macOS" checked? | By a Go test in `src/client/cmd/lgtm-client/` that builds the client for Linux and macOS on both processor families, with C turned off. | `scripts/` belongs to the Contract team. A test in the client's folder runs with `go test ./src/client/...` and catches a macOS file that no longer compiles. | closed | 2026-11-26 |
| 31 | What do the program's commands do in sprint 1? | `version` prints the version and exits 0. `join` and `run` print one sentence that says they are not built yet and exit 1. Anything else prints the usage and exits 2. | The brief asks that `join` and `run` are named and answer that they are not built yet. Plan `go-s3-client-link` replaces both. | closed | 2026-11-26 |
| 32 | How is the machine's key stored, and what is its fingerprint? | The private key is a PEM (Privacy-Enhanced Mail) block of type `PRIVATE KEY` in PKCS #8 (Public-Key Cryptography Standards number 8) form. The fingerprint is `SHA256:` followed by the unpadded base64 of the SHA-256 (Secure Hash Algorithm, 256 bits) hash of the 32-byte public key. | Both are standard forms that Go reads and writes without help. Assumption: plan `go-s0-contract` may choose another form for the server's fingerprint, and the machine's own fingerprint is for display only. | unanswered | 2026-11-26 |
| 33 | May the plan name the four harnesses? | Only as data that the program looks for. The plan assigns no model and no harness to any seat. | The rule for planners forbids assigning a model or a harness. The scan must know the program names to find them. | closed | 2026-11-26 |
| 34 | Does this plan depend on row 5, the cut of wave 1 into sprints? | It builds on the cut as written. Assumption: the cut stands. If it changes, only the sprint number of this plan changes. | Row 5 is open, and only the owner can close it. | unanswered | 2026-11-26 |
| 35 | Where does the code for the state folder live? | In a new package `src/client/internal/state/`, not in `config`. `config` only reads the settings and finds the folder. | The key, the outbox and the receipts all need the same safe write and the same checks of the folder. A package of its own keeps that in one place, and `config` stays a reader of settings. | closed | 2026-11-26 |
