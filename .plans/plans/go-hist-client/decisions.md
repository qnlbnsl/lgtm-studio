# Decisions for the client history plan

| id | question | decision | rationale | status | date |
|---|---|---|---|---|---|
| 1 | How large is the plan? | Use tier M and four work items. | The assignment sets tier M for more than one item. The announcement, store transaction, stream and startup have separate proofs. | closed | 2026-11-28 |
| 2 | What does the Client team own? | Send the two Hello numbers, apply the three Welcome cases, make a missing history file after enrollment verification, and prove receipt and fresh report behavior. | The owner decided on 2026-11-28 that the client takes the server's mark and reports current state. See “How the work is cut” in the history design and points 1 to 5 of the assignment. | closed | 2026-11-28 |
| 3 | What does adoption discard? | Include numbered rows in the events bucket when the server mark is above the local last number. Exclude the receipts bucket, saved key, saved identity, settings and process boundary. Preserve the normal replay path for required rows above an in-range mark. | The owner decided on 2026-11-28 to drop the numbered events the server has already passed. See “Decisions”, “How the two sides compare their numbers” and “What the client stops doing” in the history design. | closed | 2026-11-28 |
| 4 | Who owns the other parts and older revisions? | Leave the wire definition to Contract, admission and command settlement to Server, and the bell and paired proofs to Website. Keep the sprint 4 revision 1 paths and add no upgrade or data migration. Keep the service definitions and process status mapping. | The owner decided on 2026-11-28 to amend revision 2 in place. See “What changes in the contract text”, “How the work is cut” and “What is left out” in the history design, as well as the assignment's team and platform limits. | closed | 2026-11-28 |
| 5 | Where do the two Hello numbers come from? | Assume a locked snapshot of the store's committed counters per attempt is enough. Keep the run identifier and boundary in the existing immutable process announcement. | Opening the store reconstructs the counters and its transactions update them under the same lock. A second file read would add no durable information. | unanswered | 2026-11-28 |
| 6 | Which numbers does the client compare at Welcome if an outage write occurred after Hello? | Assume Hello states the bounds at send preparation. Apply Welcome against the committed local bounds after joining the outage worker. Retain any suffix now above the mark and run the normal checks on it. | A report committed during the handshake can already own a number above the mark. Reusing or discarding that number would break the event order. Admission on the server still uses the announced sample. | unanswered | 2026-11-28 |
| 7 | How is a higher mark written? | Assume adoption uses one existing store transaction to empty the events bucket and put the new next number. Publish the cached counters only after commit. Validate the mark against the existing event ceiling before arithmetic. | The file already encodes the floor with the count and next number. One transaction prevents a partially adopted mark and needs no file format change. | unanswered | 2026-11-28 |
| 8 | What happens after an unusable Welcome or live acknowledgement? | Assume a Welcome below the current acknowledgement or above the event ceiling closes that attempt and uses the existing failed-connect delay. Assume a live acknowledgement above the handoff ceiling also closes its stream as an invalid frame. Keep the live arrival-time ceiling and remove the old diagnostic. | The failed-connect delay prevents a peer that repeats the same unusable Welcome from causing a tight loop. The design defines the below-floor Welcome as retryable and removes `impossible_ack`. The signed event domain supplies the upper bound. Only an authenticated, valid Welcome can authorize adoption. | unanswered | 2026-11-28 |
| 9 | What is the receipt number after adoption? | Assume saved terminal numbers stay byte for byte. Seal an inherited revision 2 start at the process boundary minus one. Record new results at the durable last number at completion, as before. | The number records the prior durable event barrier. The adopted mark covers that barrier. It cannot prove that a discarded event's effect was applied. The prior process could not have used a number introduced by the adoption. | unanswered | 2026-11-28 |
| 10 | What if the report queue holds an older snapshot in memory? | Assume a successful adoption clears pre-adoption pending Facts and HarnessesFound snapshots. Let the existing approved Welcome path sample again. | Those snapshots have no durable event numbers. Clearing the two pending slots prevents the first report above the new mark from describing the older view. | unanswered | 2026-11-28 |
| 11 | Which open failure gets exit status zero? | Use exit status zero with one `link_stopped` line for an unreadable existing history or damage. Assume a verified read failure keeps the plain `store_failed` text. Keep the existing operational failure status for a readable file that cannot be opened for writing, an unsafe file path, a lock conflict or a failed write. | The owner's design of 2026-11-28 explicitly includes unreadable history in the clean stop. Sprint 4 returns status 1 for actual read failure. The assignment's instruction to keep stopped-client exit status is read as preserving the process mapping and exit codes outside the precise new rule. | closed | 2026-11-28 |
| 12 | How do the gates fit the build order? | Use the Go gate without the optional paired database at the client-only merge. Run the real PostgreSQL suite after the paired tests change with the Website build. Run the client tests on native Linux and macOS under an ordinary user. | The assignment gives H1 to H8 to Website. Two current paired cases assert the old client behavior and the paired harness enters only when a real database is supplied. | closed | 2026-11-28 |
| 13 | How are workers assigned? | Assume four test writers, four builders, four post-build reviews and up to five plan-review seats. Use one vendor for every role and defer launches until its allowance covers them. | The assignment requires a single vendor. The bounded planner has no live account allowance reading. | unanswered | 2026-11-28 |
