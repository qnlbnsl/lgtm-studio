REVISE

The first-start job cannot atomically rename the staged server credential across its two Docker bind mounts, so it can revoke the initial administrator token and still fail to hand a credential to the server.

## Findings

### logic2-r1 1 · BLOCKER · D10

The setup job mounts `/state/admin` and `/state/server` separately and stages the only credential to be published in the first mount. Revocation precedes the final rename into the second mount. On first start, Linux rejects that rename with `EXDEV` even when both host directories share a filesystem. A `mv` that falls back to copying cannot provide the specified atomic publication. Keep the private journal where it is. After confirming revocation, copy the validated object to a private temporary file inside `/state/server`, apply the final ownership and mode, flush the file, rename within `/state/server`, and flush that directory. Test the real two-mount layout. Evidence by reading `.plans/plans/go-s1-stack-vault/plan.md:200`, `.plans/plans/go-s1-stack-vault/plan.md:204` and `docs/specs/2026-11-25-go-rewrite-foundation-design.md:224`. [Linux rename manual](https://man7.org/linux/man-pages/man2/rename.2.html#ERRORS)

### logic2-r1 2 · MAJOR · D9

The plan revokes its only administrative token and grants the runtime credential access to one signing-key path. It then says an administrator can replace that credential with the retained recovery share. With the planned listener and OpenBao 2.7.3 defaults, the legacy unauthenticated root-generation endpoint is disabled and the current root-generation command uses an authenticated endpoint. After a lost file or a revoked SecretID, the plan supplies no operator identity that can perform the replacement. Specify a local operator identity scoped to managing the server's AppRole SecretIDs and keep it out of the runtime containers. Document how the operator verifies the new credential, atomically installs the file, recreates the server container, and revokes the superseded SecretID. Exercise replacement after revoking the initial root token and verify that the signing key is unchanged. Evidence by reading `.plans/plans/go-s1-stack-vault/plan.md:141`, `.plans/plans/go-s1-stack-vault/plan.md:187`, `.plans/plans/go-s1-stack-vault/plan.md:204` and `.plans/plans/go-s1-stack-vault/plan.md:206`. [OpenBao root generation command](https://openbao.org/docs/commands/operator/generate-root/) and [legacy endpoint defaults](https://openbao.org/docs/api/system/generate-root/).

### logic2-r1 3 · MAJOR · D4

The database health probe uses loopback and relies on `POSTGRES_HOST_AUTH_METHOD=scram-sha-256`. The image appends that rule after the rules created by `initdb`, which defaults to trust for loopback connections. PostgreSQL applies the first match. A well-formed but wrong application password can therefore pass the health probe while the future server is denied on the Docker network. Disabling an entire login, as the test proposes, would fail even under trust. Set `POSTGRES_INITDB_ARGS=--auth-host=scram-sha-256` for fresh clusters and test each probe against a deliberately incorrect password while keeping the login enabled. SCRAM stands for Salted Challenge Response Authentication Mechanism. Evidence by reading `.plans/plans/go-s1-stack-vault/plan.md:125` and `.plans/plans/go-s1-stack-vault/plan.md:130`. [PostgreSQL image entrypoint](https://github.com/docker-library/postgres/blob/ac9627dcf544a8454f212a12ddeebfcdc0803d3e/16/alpine3.24/docker-entrypoint.sh#L245-L262), [PostgreSQL 16 initialization](https://www.postgresql.org/docs/16/app-initdb.html), and [first matching authentication rule](https://www.postgresql.org/docs/16/auth-pg-hba-conf.html).

### logic2-r1 4 · MAJOR · D4

The image writes `PG_VERSION` before running the initialization files and skips those files on later starts. If the first container dies after creating `lgtm_app` and before creating `lgtm_bao`, the next launch retains the passwords, skips the missing database creation and times out waiting for health. The setup never advances on a normal retry. Record PostgreSQL bootstrap completion separately from `PG_VERSION`. Specify an idempotent repair step using the existing administrator credential to reconcile missing roles, databases and grants without replacing the volume or rotating passwords. Freeze a test that kills initial setup between the two database creations, then reruns the launcher against the same volume. Evidence by reading `.plans/plans/go-s1-stack-vault/plan.md:115`, `.plans/plans/go-s1-stack-vault/plan.md:125`, `.plans/plans/go-s1-stack-vault/plan.md:130` and `.plans/plans/go-s1-stack-vault/plan.md:223`. [PostgreSQL image initialization branch](https://github.com/docker-library/postgres/blob/ac9627dcf544a8454f212a12ddeebfcdc0803d3e/16/alpine3.24/docker-entrypoint.sh#L317-L347)

### logic2-r1 5 · MAJOR · D10

The publication paragraph calls for removing temporary bootstrap credentials without specifying that cleanup follows durable publication. A process killed after deleting the pending credential and before publishing the final file leaves an initialized vault with a revoked administrator and no resumable credential. Require the recovery record, verified revocation marker and staged credential to remain until the final file and its directory are durable. On a crash after publication, validate the completed file and finish local cleanup without provisioning or logging in again. Add interruption assertions immediately before and after durable publication in addition to the existing revocation-boundary test. Evidence by reading `.plans/plans/go-s1-stack-vault/plan.md:202`, `.plans/plans/go-s1-stack-vault/plan.md:204` and `.plans/plans/go-s1-stack-vault/plan.md:212–215`.

### logic2-r1 6 · MAJOR · D10

The lock is keyed by the state directory while the Docker services and PostgreSQL volume are keyed by Compose project. Two launches on one Docker daemon with the same project and two different empty state directories can each pass the local check and acquire different locks. They can then target the same containers and database volume with different password or key files, causing one launch to disrupt the other's service. Serialize by Compose project on the selected daemon and persist an installation identifier on the PostgreSQL volume alongside the local identifier. Check the binding before changing service mounts. Test sequential and overlapping launches with one project and two state roots. The second root must be refused and the first installation must retain service and its secret. Evidence by reading `.plans/plans/go-s1-stack-vault/plan.md:115`, `.plans/plans/go-s1-stack-vault/plan.md:221` and `.plans/plans/go-s1-stack-vault/plan.md:231`.

### logic2-r1 7 · MINOR · C13

The job waits for the initialization endpoint, which reports whether storage is initialized. A restarted vault can answer that probe while still sealed. A resume can then attempt provisioning or login during automatic unseal and fail a launch that would succeed moments later. Use initialization status to select the branch. Before provisioning or validating a pending login, wait within a bounded deadline for an initialized, unsealed and active vault, including immediately after successful initialization. Give each request a timeout within the same deadline. Exercise an initially sealed response followed by an active response. Evidence by reading `.plans/plans/go-s1-stack-vault/plan.md:202–204` and `.plans/plans/go-s1-stack-vault/plan.md:223`. [OpenBao initialization client](https://github.com/openbao/openbao/blob/v2.7.3/api/sys_init.go#L14-L27) and [OpenBao health statuses](https://openbao.org/docs/api/system/health/).

The proof records digests, but the implementation names only image tags for the daemons, the PostgreSQL preparation job and the OpenBao helper base. If a tag is republished between the proof and a clean-host build, the stack can run a different image and still appear to have satisfied the proof gate. ## Answers to the attack questions

1. The plan has no application-owned sequence or wrapping counter. The launcher orders setup under a directory lock and uses 60-second waits. The secret identifier has unlimited uses and no expiry, and each login gets a separate nonrenewable 15-minute token. The signing-key create uses compare-and-set with a winner read on conflict. The missing ordering cases are a delayed unseal and two state roots targeting the same project. Evidence by reading `.plans/plans/go-s1-stack-vault/plan.md:187`, `.plans/plans/go-s1-stack-vault/plan.md:206–208` and `.plans/plans/go-s1-stack-vault/plan.md:221–223`.
2. A failed database query denies key generation. A database startup timeout stops the launcher. Duplicate registration is reconciled by looking up the staged identifier, and expiry is handled by logging in again using the returned lease. A local deadline should use elapsed time. Response loss during initialization, revocation timeouts and cleanup boundaries need explicit retry states. Evidence by reading `.plans/plans/go-s1-stack-vault/plan.md:137`, `.plans/plans/go-s1-stack-vault/plan.md:187`, `.plans/plans/go-s1-stack-vault/plan.md:202–206` and `.plans/plans/go-s1-stack-vault/plan.md:223`.
3. The seal-key cases are present and valid, preserve it. Present and malformed, deny. Absent with empty storage and no local history, create it. Absent with storage rows, history, or an unreadable database, deny. For initialization, fresh storage with no local record initializes, initialized storage with trusted material resumes, initialized storage with a complete credential short-circuits, and initialized storage with no usable material denies. The plan leaves fresh storage with stale local material, a malformed published file beside a valid pending record, completed publication with leftover journal files, and a live but sealed vault during resume without explicit transitions.
